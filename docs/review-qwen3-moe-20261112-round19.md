## 二、修改建议

### 问题1（高）: A路GEMM的pimir语义未绑定，导致代价可伪造
　　**问题说明**：design §十.4 规定条目类别「`op_type == GEMM` 的条目走 A 路（分块 GEMM）」，「B 路编译单位的唯一真源是该条目引用的 pimir 实产」；implement §8.3 把「pimir 分块来自 FlagTree 实测」「trace 可逐专家追溯」列为验收不变式。实际严格契约只把 **B 路**单位绑定到 pimir：`run_full_pipeline._bpath_unit_contract_problems`（`scripts/run_full_pipeline.py:1073-1075`）对 GEMM 直接 `continue`，`_pimir_unit_problems`（`:1001-1040`）只被 B 路调用；`check_sidecar_entries`（`:495-565`）对 GEMM 只查分片/角色/分块字段，从不解析 pimir；GeneSim 的 `_require_pimir_unit`（`genesim/src/scheduler/gene_sim_scheduler.py:822-823`）对 GEMM 返回 `None`，`_validate_pimir_unit`（`:856-860`）随即返回，`_assert_pimir_operator_kind`（`:1809-1823`）只覆盖逐元素类型，`fused_kernels_missing_act_spec` 只在 `step_bcd_export` 里执行。于是把 1557 条 GEMM 的 `pimir_path` 全部指向一份 `pim.gather` 产物后，编译器五入口（导出、skip-simulation、freshness、仿真 IR、trace）与直接 GeneSim 全部接受，trace 仍标 `pimir`，`total_time_s` 从 60.785 降到 **1.696**（35.8×），`tokens/s` 升到 468.735，summary 仍声明 `dynamic_dispatch`；只替换 op152 时 trace 指令数由 14 变 3。`kernel_tile_n` 同样没有被共享验证器核对，删掉后条目仍被接受，GeneSim 会退回 conf 的 tile 常量 32。
　　**根本原因**：round18 问题 2 只把「B 路编译单位」绑定到 pimir，没有把对称的「A 路编译单位」定义出来：A 路此刻只绑定了 `pimir_path` 与哈希，没有绑定「这份产物必须是该 GEMM 的实测分块 GEMM」这一语义与形状。两仓因此各自缺一个 A 路产物解析点：编译器侧不解析、GeneSim 侧在 `unit is None` 时提前返回；严格的「完整产物」测试夹具（`tests/test_genesim_simulation.py::_contract_case`）也把一份 LUT pimir 同时挂在 GEMM 与 B 路条目上并断言通过，说明测试只证明了自洽，未证明 A 路产物语义。这与 round17 问题 3（新证据只接 trace 消费点）、round18 问题 1（分类取自被验对象自报）是同一复发模式：证据只接到 B 路/单一消费点，没有在共享验证器的对称位置统一。同一根因还使 `kernel_tile_n`、融合激活的 `act_spec` 与 GEMM 分片宽度都没有以 pimir 实产为真源；替换任意一份同哈希产物即可改代价而不触发任何入口。
　　**涉及文件**：`scripts/run_full_pipeline.py:1001-1102,2043-2184`；`genesim/src/scheduler/gene_sim_scheduler.py:813-970,1809-1823`；`genesim_bridge/placement_export.py`（A 路 pimir 生成）；`scripts/run_full_pipeline.py:1240-1262`（`fused_kernels_missing_act_spec` 仅导出步骤调用）；`tests/test_genesim_simulation.py:1395-1500`（`_contract_case` 把同一份 `pim.lut` pimir 同时给 GEMM 与 B 路条目，`test_full_contract_accepts_a_complete_sidecar` 据此断言「完整产物」通过——测试夹具本身固化了 A 路语义缺口）；证据 `/tmp/r19-probes/tampered_allgemm.json`、`/tmp/r19-probes/tampered_notile.json`、`/tmp/r19-probes/genesim-allgemm.log`、`/tmp/r19-probes/pim_traces_gemm`。
　　**修改思路**：定义与 B 路对称的「A 路编译单位」：对每个源 IR GEMM（非 host/豁免/吸收），按路径只解析一次其 pimir，要求（a）产物是分块 GEMM 原语（`tt.dot`/`pim.matmul`，且不得带 `pim.traceTokens`/phase 链）；（b）`tt.dot` 的 M/K/N 与 sidecar 分片的 `local_in_features`/`local_out_features`、`kernel_tile_n` 一致；（c）融合角色在 `fused_activations` 里时产物带 act_spec。把这份检查放进 `audit_sidecar_coverage`（导出、skip-simulation、freshness、仿真 IR、trace 自动继承），GeneSim 在 `_validate_pimir_source_coverage` 与 `_validate_pimir_unit` 用同一规则（两仓不互相 import，规则同步写入 design §十.4），并在导出步骤复用。补「单 GEMM/全部 GEMM 换成 B 路产物」「GEMM pimir 换成另一分片宽度」「删 `kernel_tile_n`」「融合 GEMM 缺 act_spec」正反例，确认五入口与直接 GeneSim 同判；用 4L/48L 真实 GEMM pimir（含 `tt.dot`）做正例守护。

### 问题2（高）: host自报跳过A路检查，导致GEMM元数据缺失
　　**问题说明**：design §十.4 规定 host GEMM 必须用独立的 `host_gemms` 条目，带 `device_hint`/角色/权重身份证据；非 GEMM host 由**源 IR** 的 `device_hint=cpu` 证明，「同一算子的 `operators` 条目若带 PIM 分片、`pimir_path` 或 `device_hint=pim`，就不能再按 host 免掉 pimir」。实际 `run_full_pipeline._entry_is_host`（`:460-463`）只读被验条目自己的 `device_hint`，`_entry_class_problems`（`:487`）与 `check_sidecar_entries`（`:559`）据此跳过 GEMM 缺分片检查与全部分片/角色/分块核对；`_assert_placement_matches_run`（`:1677-1680`）同样只看条目；GeneSim `_validate_entry_classes`（`:1129-1135`）与 `_load_compiler_placement`（`:573-588`）沿用同一自报。把 lm_head op3679 改成 `device_hint=cpu` 并删掉 `shards`/`semantic_role`/`kernel_tile_n` 后，freshness、仿真 IR 与 skip-simulation 接受；GeneSim 不再展开该 TP 算子（16373 vs 16376 算子、10902 vs 10906 trace），直接以 45.895 s（正常 60.785 s）跑完并声明 `dynamic_dispatch`。把同一改法用于 q_proj 时，编译器入口接受而 GeneSim 只因 attention TP 组不完整拒绝，说明两侧判定已分叉。真实侧车里 `operators` 条目的 `device_hint=cpu` 数量为 0（host 算子都在 `pimir_exempt_ops`），且 `host_gemms` 为空，因此这条自报没有任何同源证据。
　　**根本原因**：round18 问题 1 的根因是「被验产物的自报字段决定校验分支」，当时只把 `shards` 从分类依据里删除；`device_hint` 仍是自由自报。A 路分类没有完成：host 应是「源 IR 的 `device_hint=cpu` + `pimir_exempt_ops`/`host_gemms` 证据」共同证明的结论，而不是条目里的一个布尔开关。同一根因还使 `_assert_placement_matches_run`、GeneSim 的 TP 展开入口和 `host_gemms` 证据链一起失真。
　　**涉及文件**：`scripts/run_full_pipeline.py:455-565,1617-1717,2338-2341`；`genesim/src/scheduler/gene_sim_scheduler.py:1111-1142,2758-2808,2523-2546`；`genesim_bridge/placement_export.py`（`host_gemms` 生成）；证据 `/tmp/r19-probes/tampered_lmhead.json`、`/tmp/r19-probes/tampered_hostgemm.json`、`/tmp/r19-probes/genesim-lmhead.log`。
　　**修改思路**：把 host 判定收成与豁免相同的一份证据规则：仅当源 IR 该算子 `device_hint=cpu`、该编号在 `pimir_exempt_ops` 中、且（GEMM 时）`host_gemms` 的角色/权重身份匹配时，`operators` 条目才可按 host 跳过 A 路检查；否则严格产物中设备 GEMM 必须有分片、角色与分块，任何 `operators` 条目自称 host 却缺这些证据直接失败。把该谓词放到 `_entry_is_host` 的调用方（或改成接收 `ir_op`/豁免/`host_gemms`），统一用于 `check_sidecar_entries`、`_entry_class_problems`、`_assert_placement_matches_run`、GeneSim `_validate_entry_classes` 与 `_load_compiler_placement`，并在 TP 展开前核对「多分片角色组完整」。补 lm_head/router/单个 attention 投影三类 host 篡改正例与真实 host 算子正例；用 4L 真实产物确认 `operators` 中 host 条目为 0 时不会被误判。

### 问题3（中）: 条目字段未与源IR核对，导致五入口分叉
　　**问题说明**：design §十.4 与 implement §8.3 要求五入口共用同一判定，条目类别/类型以源 IR 为准；GeneSim 的 `_validate_compiler_placement`（`genesim/src/scheduler/gene_sim_scheduler.py:2792-2808`）确实逐条比较 sidecar `op_type` 与 IR。编译器侧的共享验证器从不做这项比较：`check_sidecar_entries` 的 B 路只检查 `op_type in MNEMONIC_OF`（`:535-538`），`audit_sidecar_coverage` 只按 IR 类型分类而忽略条目自报的类型；trace 入口的 `_bpath_unit_problems` 还在 `:2144` 用条目自报的 `op_type` 决定 SPLIT 与字节检查分支。把 op153（SILU）条目改成 `VECTOR_ADD` 后，freshness、仿真 IR 与 skip-simulation 接受，直接 GeneSim 在加载时 exit 1；把设备 GEMM op4 的 `semantic_role` 删掉也仍被共享验证器接受（GeneSim 要到 TP 展开时才拒绝）。同根因还覆盖「同宽同元的 SILU/GELU 互换」一类：单位与字节都可能对上，编译器入口会签发、GeneSim 的 `_assert_pimir_operator_kind` 才会拒绝。`kernel_tile_n` 的同类缺口见问题 1。
　　**根本原因**：sidecar 的 `op_type`/`semantic_role` 是冗余自报字段，编译器侧只把 `op_type` 当「mnemonic 是否认识」的弱校验，没有把它与源 IR 绑定；trace 入口还反过来用它选判据。round16/17 把 B 路单位绑定到 pimir，round18 把分类绑定到源 IR，但「条目字段」这一项没有纳入同一份源 IR 契约；与 round17 问题 3、round18 问题 1 同类，字段一致性只落在 GeneSim 一个消费点，共享验证器仍未覆盖。
　　**涉及文件**：`scripts/run_full_pipeline.py:460-492,495-565,1105-1238,2098-2184`；`genesim/src/scheduler/gene_sim_scheduler.py:2792-2808`；证据 `/tmp/r19-probes/tampered_optype.json`、`/tmp/r19-probes/genesim-optype.log`、缺失 `semantic_role` 的 `validate_sidecar_contract` 探针。
　　**修改思路**：在共享验证器里逐条（不只是豁免条目）比较 sidecar 的 `op_type`/`semantic_role` 与源 IR，不一致直接失败；设备 GEMM 的 `semantic_role` 必须是源 IR 的投影身份；trace 入口的 `_bpath_unit_problems` 改用 `ir_op["op_type"]` 选择字节判据；`check_sidecar_entries` 的 mnemonic 校验改为「与 IR 类型对应的 mnemonic」，并把同一份「op_type → mnemonic → pimir kind」表供两仓的共享验证器使用（编译器侧解析 pimir 文本核对 kind，等价于 GeneSim 的 `_assert_pimir_operator_kind`）。补 SILU→VECTOR_ADD、SILU→GELU、未知 mnemonic、删 `semantic_role` 四类探针，断言五入口与直接 GeneSim 同判。

### 问题4（中）: 主机分页注意力未落f16边界，导致回退口径不符
　　**问题说明**：`runtime/kernels.py:1488-1491` 新增注释与 implement §8.3 的不变式表都写「相位存储边界与融合内核共用同一张表：QK 点积落 f16 后乘 scale 再落 f16，每块 PV 乘积落 f16 后在 f32 里累加」。实际 `_host_paged_attention`（`:1481-1529`）把分数存进 `np.float32` 数组（`:1496`），`scores = matmul(...).astype(np.float32) * scale`（`:1500-1501`）在 scale 后不再落 f16；PV 的 `acc += matmul(...).astype(np.float32)`（`:1528`）是否落 f16 取决于 `matmul` 走编译内核（返回 f16）还是 numpy 兜底（`:822` 返回 f32）。融合内核在 `LowerPIMToEmitC.cpp`（QK 段：`roundF16(dot) * scale` 后存入 f16 `logits`；PV 段：`blockProduct = roundF16(...)`）两条边界都固定落 f16。也就是说，在工具链不在位这一正是主机回退存在的场景下，主机路径既不在 QK×scale 后取整，也不在 PV 乘积后取整，与注释/不变式不符；现有 `test_sdpa_fused_paged_attn_tracks_the_host_path` 只关掉 `_compiled_paged_attn`，`matmul` 仍走编译内核，因而没有覆盖该场景。
　　**根本原因**：主机回退把存储边界委托给 `matmul` 的实现细节，没有在自身代码里显式表达契约；测试夹具只强制了 `paged_attn` 内核不走编译路径，没有同时强制 `matmul` 回退。新增注释把「依赖 matmul 当前行为」误写成「共用同一张表」，文档/测试因此无法发现工具链缺席时的取整差。
　　**涉及文件**：`runtime/kernels.py:1481-1529,806-825`；`FlagTree/lib/Dialect/TritonPIM/Transforms/LowerPIMToEmitC.cpp`（paged_attn QK/PV 段）；`tests/test_kernels.py:413-460`；`docs/implement-qwen3-moe-20261105.md` §8.3。
　　**修改思路**：在 `_host_paged_attention` 内显式实现契约边界：QK 点积/乘 scale 后 `astype(np.float16)` 再存（分数缓冲用 f16 或存前取整），PV 每块乘积先 `astype(np.float16)` 再加进 f32 累加器；不依赖 `matmul` 的返回 dtype。补一个同时 monkeypatch `_compiled_paged_attn` 与 `_compiled_matmul` 为 `None` 的用例，与融合内核/在线参考逐元素或按既有容差对拍；按实现结果同步修正注释与 §8.3 表述（若确认不需要共享边界，则改成明确的等价性说明）。

### 问题5（低）: 容量指标跨口径配对，导致利用率读数失真
　　**问题说明**：design §十.5 与 round18 问题 5 统一要求「模型常驻按 ClusterPU 校验，KV/激活按单 TensorPU 校验」。`genesim/src/pim/capacity.py` 在 `enforce_tensor_limit_for_model=False` 时已用 `request_bytes` 判 `fits`，但仍把 `resident_bytes`（含模型权重）除以单 TensorPU 上限生成 `max_utilization`/`max_tensor_pu_utilization`（`:587-592`），`src/main.py:517-524` 又把该值作为「Peak TensorPU resident-memory utilization」打印。4L 产物因此出现 **145.23% 而 fits=True** 的自相矛盾读数；implement §1.3 与 §8.4 仍把 `max_resident_bytes=779,673,600` 标为「per-TensorPU 最大值（上限 536,870,912）」，即把超过该上限的值与上限配成一对，正是 round18 问题 5 的同类跨口径写法。
　　**根本原因**：一个字段同时承载「总量」与「按上限判定的量」两种 scope；round18 的修复只改了文档引用，没有把指标本身按 scope 拆开（`model_residency_scope` 只说明 scope，不改变分子）。
　　**涉及文件**：`genesim/src/pim/capacity.py:487-505,579-592`；`genesim/src/main.py:228-250,517-524`；`docs/implement-qwen3-moe-20261105.md:101-104,1964-1967`。
　　**修改思路**：按 scope 输出两个指标：单 TensorPU 的判定口径用 `request_bytes / limit`（与 `fits` 同源），模型常驻另给 cluster 口径；或把现有 `max_utilization` 改名为总量比并同步控制台/文档，避免与 512 MiB 上限配对。把 4L 的 `request_bytes` 利用率与集群利用率加入证据块 `facts` 或 checker 的核验项，替换正文中「per-TensorPU 最大值（上限 536,870,912）」的表述。
