## 二、修改建议
### 问题1（高）: 严格入口漏检pimir产物，导致过期产物放行
　　**问题说明**：design §十.4-5 要求 `requires_pimir` 自报或配置显式严格时，导出、skip-simulation、仿真前复核、仿真 IR 与 trace 五个入口共用同一份完整产物契约，缺项、不可读、哈希不符都必须失败。实现里 `validate_sidecar_contract`（`scripts/run_full_pipeline.py:576-597`）把产物校验做成可选参数 `check_artifacts=False`；`audit_sidecar_coverage`（同文件 `:831-936`）在 `:879` 对 `check_artifacts=False` 直接 `continue`，只检查 `pimir_path` 是否存在，不读文件、不核对 `pimir_sha256`；真正读文件的 `stale_pimir_entries`（`:1515-1528`）只被 `step_bcd_export`（`:1085`）和 `verify_sidecar_freshness`（`:1583`）调用。`verify_sim_ir_matches_sidecar`（`:1638-1639`）与 `verify_trace_provenance`（`:1804-1805`）调用共享验证器时都没有打开 `check_artifacts`。本轮用真实 4 层 sidecar 做反向探针：把某个条目的 `pimir_path` 改成不存在的文件，`freshness` 以 `FileNotFoundError` 失败，`sim_ir` 与 `trace` 均 **ACCEPTED**；把 pimir 内容改一个字、保留 sidecar 旧哈希，`freshness` 以 StepFailed 拒绝，`sim_ir` 与 `trace` 仍 **ACCEPTED**；把某个条目的 `pimir_sha256` 删掉，`sim_ir` **ACCEPTED**（`trace` 只在有 trace 指向该算子时才拒绝）。这直接违反“五个入口共用同一判定”，且 round14 问题3 的修复只覆盖了配置键、IR 文件与 sidecar 文件，没有覆盖 pimir 产物这个同类路径。
　　**根本原因**：产物校验被建模成共享验证器的可选参数，而不是严格契约的固定组成部分；三个入口各自决定是否打开，既没有统一的入口级必检输入，也没有“每个非豁免、非吸收算子都必须有可读且哈希匹配的 pimir”这一条不变式。相同根因还影响 `verify_sidecar_freshness` 的错误形态（`:1515-1528` 直接 `Path.read_bytes()`，缺失文件抛 `FileNotFoundError`，而主流程只捕 `StepFailed`）以及 `tests/test_genesim_simulation.py` 的入口矩阵（`:1921-1940` 只测配置键/IR/sidecar 文件，没有缺 pimir 文件、不可读、缺哈希、哈希不符的用例）。这不是某个探针的局部问题，而是两类入口（仿真 IR、trace）对同一份 sidecar 的产物身份没有验收。
　　**涉及文件**：`flagos-pim-compiler/scripts/run_full_pipeline.py:576-597,831-936,1515-1528,1555-1599,1638-1639,1804-1805`；`flagos-pim-compiler/tests/test_genesim_simulation.py:1921-1940`；本轮 `logs/probe-contracts-r15.log` 与 `/tmp/qwen3-review-round15/probes/{missing_pimir,stale_pimir,missing_hash2}`。
　　**修改思路**：把“产物身份”变成共享验证器的固定规则：只要 `sidecar.requires_pimir` 或调用方显式严格，`validate_sidecar_contract` 就必须逐条核对每个非豁免、非吸收算子的 `pimir_path` 可读且 `pimir_sha256` 匹配，不能再由入口传 `check_artifacts=False` 关掉；导出、skip-simulation、freshness、仿真 IR 与 trace 五个入口共用同一个入口级包装（可命名为 `verify_complete_product(genesim, config)`），由它先解析配置、再打开产物校验，任何入口都不得绕过（导出/skip 已经传 `check_artifacts=True`，三个复核入口也必须打开）；`stale_pimir_entries` 的读文件错误统一转成 `StepFailed`，给出“哪个 op、哪个路径、哪类错误”。补三入口 × {缺 pimir 路径, 路径存在但不可读, 缺哈希, 哈希不符} 的矩阵测试，并保留合法非严格旧式 sidecar 的正例。这样既修复当前三个探针，也消除未来新入口复用部分验证器的同类问题。

### 问题2（中）: trace入口可脱离配置签发，导致覆盖未核
　　**问题说明**：design §十.4 要求 trace 验收按源 IR 的应覆盖集合与实际 pimir 来源对拍，`unknown`、缺算子与非 pimir/absorbed 来源一律失败；implement §8.3 也把 `verify_trace_provenance` 列为逐条 lineage 的入口。但该函数（`scripts/run_full_pipeline.py:1713-1810`）在 `:1783-1784` 保留了“`config is None` 就返回”的旧式分支：前面只做了来源白名单，既不读源 IR、也不读 sidecar、不核对父算子/类型/哈希/覆盖集合。本轮用临时 `genesim` 根放一条 `trace_source=pimir`、`compile_signature.pimir_sha256` 被改成 64 个零的 trace，调用 `verify_trace_provenance(root)` 返回 **ACCEPTED**；现有 `tests/test_placement_export.py:1313` 还明确断言一条无 IR/无 sidecar 的 pimir trace 可以通过。也就是说，任何工具只要不传配置，就能在没有任何同源证据的情况下签发 trace 目录；主链虽然总是传配置，但入口本身的契约与文档不一致。
　　**根本原因**：严格性被设计成“调用方可选传配置”，而不是入口的必检输入；round14 问题3 的修复只处理了“传了配置但缺键/缺文件”，没有处理“完全不传配置”的最早返回。同一根因还会让未来的离线工具复用该函数时绕开覆盖/lineage；现有测试把旧式行为固化，导致修复需要同时更新测试语义，而不是只删一行。
　　**涉及文件**：`flagos-pim-compiler/scripts/run_full_pipeline.py:1713-1810`；`flagos-pim-compiler/tests/test_placement_export.py:1212-1313`；`flagos-pim-compiler/tests/test_genesim_simulation.py:1599-1607`；本轮 `/tmp/qwen3-review-round15/probes/legacy-trace-pimir`、`legacy-trace`。
　　**修改思路**：把配置和 IR/sidecar 设为 trace 验收的必需输入；无配置调用只能返回“未验收/仅诊断”而不能返回通过，或改为显式 `legacy_no_lineage=True` 的独立诊断函数并在结果里标注不可用于验收。现有只测模板/截断 trace 的用例应改为传一个最小配置 + 临时 IR/sidecar，或者断言显式 legacy 函数的非验收结果。补充“无配置 + 单条 absorbed/错误哈希 trace”反例，和“配置+完整 lineage”正例，确保修复不误伤旧工具。
