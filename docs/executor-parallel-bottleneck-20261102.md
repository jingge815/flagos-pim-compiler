# 并行执行瓶颈测量（2026-11-02）

## 目的

TODO 的 G1 假设「`_host_lock` 串行主机命令，导致 P=4 相对 P=2 没有收益」。
本次用可复现的基准脚本验证这个假设，并回答两个问题：

1. 主机锁到底占多少时间？
2. P 从 2 提到 4 的收益被什么吃掉了？

结论先说：**假设不成立**。主机锁只占墙钟 9–13%，而且每条 host 命令都跨全部 4 台 DPU，
按 DPU 分片锁没有可并行的部分。真正的上限是单进程的 Python GIL：4 台 DPU 全速运行时，
进程也只用到 1.4–1.6 个核。

## 方法

新增 `scripts/bench_parallel.py`：编译一个小 Llama，跑「预填充 + 固定步数解码」，
对每个并发窗口数 P 重复若干次取墙钟中位数，同时记录：

| 指标 | 含义 |
|---|---|
| `util` | 各 DPU 内核墙钟之和 ÷（DPU 数 × 墙钟） |
| `cores` | `time.process_time()` 增量 ÷ 墙钟，进程实际用到的核数 |
| `kernel_cpu_ratio` | 内核线程 CPU 时间 ÷ 内核墙钟时间 |
| `host_hold` | 持有 `_host_lock` 的总时长 |
| `kernels` | 内核命令条数 |

脚本对每个 P 校验生成 token 完全一致，不一致直接非零退出。

默认配置：4 DPU / 4 层 / hidden 1024 / 4 请求 × 8 解码步，tp4 策略。

```bash
source "$(python3 -c 'import json; print(json.load(open("paths.local.json"))["pytorch_env_script"])')"
python scripts/bench_parallel.py --repeat 3 --json /tmp/bench.json
```

## 结果

### 1. 小模型（hidden 1024，每组重复 3 次取中位数）

| P | 墙钟 ms | ms/步 | DPU 忙碌率 | 主机锁持有 ms | 锁占比 |
|---|---|---|---|---|---|
| 1 | 24 184 | 3 023 | 54.0% | 2 255 | 9.3% |
| 2 | 20 855 | 2 607 | 71.2% | 1 847 | 8.9% |
| 4 | 20 015 | 2 502 | 79.6% | 2 331 | 11.6% |

P=4 比 P=2 只快 4.0%，远低于 G1 定的 10%。

### 2. 进程核数（单次运行）

| P | 墙钟 ms | 进程核数 | 内核 CPU/墙钟 | 内核 CPU 总量 ms |
|---|---|---|---|---|
| 1 | 28 654 | 1.38 | 50% | 27 663 |
| 2 | 24 345 | 1.54 | 41% | 26 025 |
| 4 | 20 732 | 1.63 | 44% | 27 928 |

三点观察：

- 内核 CPU 总量恒定在 26–28 s，与 P 无关——这是真正要做的工作量。
- 进程核数从 1.38 只涨到 1.63：即使 4 台 DPU × 4 个泳道一共 16 个工作线程，
  进程也用不到 2 个核。
- 内核线程只有 41–50% 的墙钟在真正跑 CPU，其余时间在等 GIL。

### 3. 大模型（hidden 2048、intermediate 5504、4 层，单次运行）

| P | 墙钟 ms | DPU 忙碌率 |
|---|---|---|
| 1 | 39 576 | 70.2% |
| 2 | 32 638 | 88.1% |
| 4 | 35 738 | 110.3% |

放大矩阵乘法后仍然只有 P=2 有收益；P=4 的忙碌率超过 100%（同台 DPU 上多个请求交错），
但墙钟反而回升——GIL 争用随线程数增加而恶化。

### 4. 两个进程同时跑（各 P=2）

| 运行 | 墙钟 ms |
|---|---|
| 进程 A | 26 630 |
| 进程 B | 23 507 |
| 单进程基线 | 20 855 |

两个进程同时跑，各自只慢 10–20%，说明机器（152 核）有充足空余算力，
限制在**单进程内部**，不是 CPU 不够。

## 分析

### 主机锁不是瓶颈

`_host_lock` 的持有时间只占墙钟 9–13%。更关键的是：decode 计划里的 42 条 host 命令
（13 条 `host_concat`、13 条 `host_slice`、8 条 `host_reduce`、4 条 `dpu_slice`、4 条 `host_op`），
除 `host_op` 外每条都读写全部 4 台 DPU：

```text
decode 计划：{('dpu_slice', 4): 4, ('host_concat', 4): 13, ('host_reduce', 4): 8,
              ('host_slice', 4): 13, ('host_op', 0): 4}
```

按 DPU 分片锁时，每条命令都要拿全部 4 把锁，等价于原来的全局锁。**G1.2 证否**。

### 真正的上限是 GIL 与命令数

decode 计划单请求一步有 **934 条命令**，其中 152 条 `aten.mul`、116 条 `aten.linear`、
100 条 `aten.add`、72 条 `aten.to.dtype`……按 8 步 × 4 请求共 28 544 次内核调用，
内核 CPU 27.7 s，折合 **约 0.97 ms / 条**。

小模型单请求一步的真实浮点工作量远小于此（数组只有 8 token × 256 列），
说明时间花在 Python 侧的逐条调度上，而不是数学运算。四个请求并发时这些调度互相争 GIL，
所以 P 加大只是把同样的 CPU 工作挤在更多线程里。

### 对已有结论的影响

- 之前记录过的「P=1 27 557 ms → P=2 21 403 ms」是真实的（主机与内核有部分重叠），
  但「P=4 只多 2.6 个百分点」不是 host 锁造成的，而是 GIL 已经饱和。
- NumpyBackend 上的并行加速上限约为 1.4×（27 663 / 20 015），不能用来论证真硬件收益。
- 「DPU 忙碌率」在这个后端下是墙钟指标，会把 GIL 等待算成忙碌，解读时要配合 `cores`。

## 下一步选项

| 选项 | 做法 | 代价 | 适用 |
|---|---|---|---|
| A. 减少命令数 | 图级融合：把同 DPU 上的连续逐元素算子（RMSNorm 的 pow/mean/rsqrt/mul、residual add 等）合成一条内核 | 改编译器前端，行为等价性测试要重做 | 对真硬件也有价值（降低启动开销） |
| B. 进程化 DPU | 每台 DPU 一个进程，MRAM 换成共享内存 | HAL 与命令协议重写，G4/G6 的前置 | 只影响模拟后端 |
| C. 接受上限 | 并行收益留给 G4 真硬件验证，模拟器只做功能与 token 对拍 | 无 | 当前推荐 |

建议：先做 A 的一小步（只融合 RMSNorm 链与残差加法），用本脚本量化收益；
若命令数下降后 P=4 仍无明显改善，则按 C 处理，把吞吐目标移到 G4。

## 已实施的测试

`scripts/bench_parallel.py` 内置 token 一致性断言：P=1/2/4 以及重复运行的生成 token
必须逐字相同，否则返回码非零。默认配置下已经连续通过多次。

## 当前不足

- 基准脚本没有单测（与 `profile_execution.py` 等脚本一致），靠运行结果约束。
- 测量受机器负载影响：本机 load average 18–23（152 核），同一配置墙钟波动可达 ±20%，
  因此脚本默认重复 3 次取中位数。
- 只覆盖 tp4；pp 或混合策略的 host 命令可能不跨全部 DPU，需要时再量。
