# 图编译器与 GeneSim 互联实现说明

## 一、这份文档解决什么问题

大模型推理要经过三个环节：图编译器把模型切分到多台存算一体设备上，算子编译器把每个
算子编译成可执行的指令，GeneSim 模拟器估算整个系统跑起来要多长时间。这三个环节原本
是三个相对独立的系统，本次改动把它们真正连起来，做到两件事：

1. **图编译器切分的结果，能让 GeneSim 算出不一样的时间**（改动前，无论怎么切分，
   GeneSim 算出来的时间都完全一样，切分等于白切）。
2. **GeneSim 能提前指定一种切分方案，约束图编译器按这个方案去切**（改动前，这个方向
   完全不存在，只能图编译器自己决定切分）。

涉及两个代码仓库：图编译器仓库（`flagos-pim-compiler`）和模拟器仓库（`genesim`）。

## 二、总体流程

一次完整的运行分五个阶段，前四个阶段方向一致（从模型到模拟器），第五个阶段方向相反
（从模拟器到图编译器）：

```
第〇阶段  GeneSim 给出切分方案
  ├─ 输入：要切成几段流水、每段内张量并行几路
  ├─ 处理：按存算一体设备的容量和链路带宽，挑选具体用哪些物理单元
  └─ 输出：一份切分方案文件（PartitionPlan）

第一阶段  模型加载与图编译
  ├─ 输入：Llama2-7B 模型权重 + 第〇阶段的切分方案（没有方案就用命令行参数）
  ├─ 处理：按方案把权重和计算图切分到多台设备上
  └─ 输出：带切分标注的计算图

第二阶段  算子编译
  ├─ 输入：第一阶段切出来的每个算子的本地形状（切分之后，一台设备实际要算多大的矩阵乘）
  ├─ 处理：调用算子编译器，为这个形状生成可执行代码，同时产出中间表示文件
  └─ 输出：可执行文件 + 中间表示文件 + 这次编译选定的实际分块大小

第三阶段  导出给 GeneSim 的说明文件
  ├─ 输入：第一、二阶段的全部产出
  └─ 输出：一份说明文件，逐个算子记录切分后的形状、分块大小、中间表示文件路径等

第四阶段  GeneSim 模拟
  ├─ 输入：第三阶段的说明文件
  ├─ 处理：不再用"猜出来的"参数模拟每个算子的执行时间，而是用第二阶段真实编译产出的
  │        中间表示，还原出真实的指令序列
  └─ 输出：模拟得到的总耗时、吞吐量等指标
```

第〇阶段是本次新增的反向接口，第一到第四阶段在此前的工作里已经把"接口通不通"解决了，
本次改动解决的是"通了之后，切分对结果到底有没有影响"。

## 三、改动前的问题：接口通了，但不起作用

改动之前，上述链路里有三段看起来是通的，但实际不影响模拟结果：

| 环节 | 看起来做了什么 | 实际问题 |
| --- | --- | --- |
| 算子编译产出的浮点运算量传给 GeneSim | 把算子编译中间表示里的运算量、数据量算出来，填进 GeneSim 的模型描述文件 | GeneSim 计算耗时的代码根本不看这两个数字，这条通道白写了 |
| 图编译器切分后的本地形状 | 每台设备切完之后，实际计算的矩阵大小变小了 | GeneSim 加载模型描述文件时，仍然用切分前的全局大小去估算耗时，切分等于没发生 |
| GeneSim 到图编译器 | 不存在 | GeneSim 无法预先指定一种切分方案给图编译器，只能图编译器自己决定 |

GeneSim 计算一个矩阵乘算子的耗时，走的是这样一条路：

```
算子的形状（多大的矩阵乘）
   │
   ▼
手写的固定模板：按配置文件里写死的"分块大小"和"并行宽度"，
拼出一段固定套路的指令序列（先搬数据，然后若干次乘加，再搬回结果）
   │
   ▼
把这段指令序列在模拟器里跑一遍，得到一个耗时数字
```

这条路径从头到尾都没有用到"这个算子编译之后运算量是多少"这个信息，所以第一个问题
（浮点运算量白传）是必然的：传的信息压根没被用上。

第二个问题的原因不同：GeneSim 加载的模型描述文件里，每个算子的形状是按"整个模型、
不考虑切分"的口径写的。图编译器算出的"切分后每台设备实际要算多大"从未被写回这份
描述文件，所以即使模板换了参数，喂给模板的形状仍然是没切分过的那个大小。

## 四、改动做了什么：四步 + 一个反向接口

### 第一步：让算子的身份匹配更可靠

**问题**：GeneSim 描述文件里判断"这个矩阵乘算子是模型里的哪个权重"（比如是
注意力层的 Q 投影还是 MLP 的门控投影），原来靠解析权重的命名字符串。这个命名规则
是模拟器那边自己定的，图编译器这边猜错一次就全错，且没有任何报错提示。

**改动**：让 GeneSim 的模型描述文件直接标注"这是哪个投影"这个身份信息（一个明确的
标签字段），图编译器改成直接读这个标签，不再猜测命名规则。同时补上了七种投影里
之前遗漏没打标签的四种（原来只有三种打了标签）。

**修改的文件**：

| 文件 | 修改内容 |
| --- | --- |
| `genesim/src/ir/model_ir.py` | 生成模型描述时，给全部七种投影都打上身份标签 |
| `flagos-pim-compiler/genesim_bridge/placement_export.py` | 改成读身份标签来匹配算子，不再解析命名字符串；读不到标签或标签不认识时，明确报错并指出是哪个算子 |

### 第二步：让切分后的形状真正传到模拟器里

**问题**：如上所述，模拟器算耗时用的形状，是模型级别的全局形状，不是切分后一台
设备实际要算的形状。

**改动**：给模拟器的算子描述结构新增两个字段，专门记录"切分之后，这台设备实际要
算的形状"，原有的字段仍然记录"整个模型的全局形状"，两者不冲突。计算耗时的代码
改成：如果有切分后的形状就用它，没有就退回用全局形状（保证不影响没有切分场景的
已有测试）。

**修改的文件**：

| 文件 | 修改内容 |
| --- | --- |
| `genesim/src/ir/model_ir.py` | 算子描述新增"本地输入形状"和"本地输出形状"字段 |
| `genesim/src/vpu/vpu.py` | 计算耗时和循环次数时，优先用本地形状 |
| `genesim/src/pim/pim_compiler.py` | 生成指令序列时，优先用本地形状 |
| `genesim/src/scheduler/gene_sim_scheduler.py` | 加载图编译器产出的说明文件时，把里面记录的本地形状写进模型描述里 |

**验证结果**：把同一个模型、同一份切分方案，分别用"全局形状"和"本地形状"跑一遍
模拟，只改这一个变量，其余完全一样。张量并行宽度是 2（即每台设备只算一半），
两次模拟的总耗时比值应该接近 0.5。

| 场景 | 总耗时（秒） | 与全局形状场景的比值 |
| --- | ---: | ---: |
| 全局形状 | 2630.51 | 1.0000 |
| 本地形状 | 1324.91 | **0.5037** |

比值接近 0.5，说明切分确实影响了模拟结果，这是改动前完全做不到的（改动前两次模拟
结果逐位相同）。

### 第三步：把算子编译器实际选用的分块大小传给模拟器

**背景**：矩阵乘算子在存算一体设备上执行时，不是一次算完整个矩阵，而是分成若干小块
轮流搬进片上缓存去算。"一块有多大"（下称分块大小）由算子编译器根据片上缓存容量和
硬件带宽等约束真实算出来，跟片上缓存的大小、矩阵形状都有关。

**问题**：GeneSim 手写模板里的分块大小是配置文件里的一个固定常量，跟真实编译时选用
的分块大小无关。而且更深一层的问题是：这个固定模板对分块大小根本不敏感——模板的
逻辑是"每块处理固定大小的输出、外层再循环若干次覆盖整个矩阵"，这两个量相乘正好抵消，
换分块大小几乎不改变算出来的总耗时。

**改动**：

1. 算子编译流程改成分两步生成中间表示（原来是一条命令链直接生成到最终的可执行代码
   格式，中间产物被丢弃了），第一步产出的中间表示带有真实选定的分块大小，把它保留
   下来。
2. 算子编译的结果结构增加两个字段，分别是这份中间表示的文本内容和它的落盘路径。
3. 给算子描述结构增加一个"编译器实测分块大小"字段，模拟器计算耗时时优先用这个值，
   没有才用配置文件里的固定常量。
4. 导出说明文件时新增一个开关，打开后会对每一种切分后的形状真正跑一次算子编译，
   把测出来的分块大小写进说明文件。

**修改的文件**：

| 文件 | 修改内容 |
| --- | --- |
| `flagos-pim-compiler/opcompiler_bridge/driver.py` | 编译流程拆成两步，保留中间表示文本；同时命中缓存时也能把中间表示读回来，不用重新编译 |
| `flagos-pim-compiler/contracts/op_contract.py` | 编译结果结构新增中间表示文本和落盘路径两个字段 |
| `flagos-pim-compiler/genesim_bridge/placement_export.py` | 新增"实测分块大小"开关，编译每种本地形状一次，缓存结果避免重复编译 |
| `genesim/src/ir/model_ir.py` | 算子描述新增"编译器实测分块大小"字段 |
| `genesim/src/vpu/vpu.py` | 计算耗时时优先用这个字段 |
| `genesim/src/scheduler/gene_sim_scheduler.py` | 生成指令序列的分块参数、缓存判断的依据都改成读这个字段，两处必须读同一个值 |

**撞上的一个自己引入的问题（已修复）**：第一版改动只把生成指令序列这一侧改成了用
实测分块大小，但计算循环次数那一侧还在读固定常量。指令序列里"每块处理多大的输出"
和外层"循环几次"这两个数字必须匹配才对，改了一半导致总运算量被算大了十六倍
（tp2_pp4 场景总耗时从 1325 秒涨到 15311 秒）。定位到问题后统一改成两处都读同一个
字段，问题消除。这个教训直接催生了后面新加的一条测试用例，专门检查两处是否读到
同一个值。

**验证结果与一个诚实的结论**：把真实分块大小接进固定模板之后，总耗时几乎没有变化
（1324.57 秒对比 1324.91 秒，差 0.03%）。原因如前所述，是固定模板对分块大小不敏感，
这个通道打通了，但价值有限，真正要让分块大小影响耗时，需要第四步。

### 第四步：不再用固定模板拼指令，改成照着算子编译器产出的中间表示生成指令

**这是本次改动里对模拟结果影响最实质的一步。**

**做法**：新增一个专门的转换程序，输入是算子编译器产出的中间表示文本，输出是模拟器
可以执行的指令序列。转换程序会读出中间表示里真实的循环嵌套结构、真实的数据搬运
描述，逐条翻译成对应的指令，而不是套用固定公式去猜。

模拟器的调度逻辑改成：如果这个算子有对应的中间表示文件，就用新的转换程序生成指令；
没有就退回原来的固定模板（保证没有该文件的场景行为不变）。

**修改与新增的文件**：

| 文件 | 内容 |
| --- | --- |
| `genesim/src/pim/pimir_trace.py`（新增） | 转换程序本体：解析中间表示，生成指令序列 |
| `genesim/src/scheduler/gene_sim_scheduler.py` | 生成指令时优先调用这个转换程序 |
| `genesim/tests/sim/test_pimir_trace.py`（新增） | 13 个单元测试 |

**转换程序开发中发现并修复的三个问题**（都是靠"用理论公式核对总量"这个方法发现的，
不是靠跑起来没报错就算过）：

1. **乘加运算次数少算了几百倍**：矩阵乘的运算量应该等于三个维度的乘积除以一次能
   并行处理的宽度，第一版实现漏乘了一个维度，导致算出来的运算次数系统性偏小。
2. **数据搬运量多算了几倍**：正确的做法是"每一轮循环搬一次数据，搬完立刻用",
   第一版实现把数据搬运指令错放进了更内层的循环，导致同一份数据被重复搬运多次。
3. **总耗时只算出了四分之一**：矩阵乘外层要循环若干次才能覆盖整个输出，这个循环
   次数应该在运行时才能确定（因为跟具体请求的序列长度有关），第一版实现把它写成了
   固定次数的循环，导致总循环次数被写死成了 1，模拟器只算出了一轮的耗时。

**验证结果**：

- **一致性检查**：同一个算子形状、同样的硬件预算，两种生成方式算出的耗时相差
  0.09%，说明转换程序描述的确实是同一个计算过程，翻译没有走样。
- **敏感性检查（价值所在）**：收紧片上缓存预算，算子编译器会被迫选用更小的分块，
  新方式算出的耗时会相应上升，固定模板则完全无感：

  | 片上缓存预算 | 编译器选用的分块大小 | 新方式算出的耗时 | 固定模板算出的耗时 |
  | --- | ---: | ---: | ---: |
  | 64 KB | 512 | 3175891（周期数） | 3178667（不变） |
  | 16 KB | 128 | 3215983（+1.17%） | 3178667（不变） |
  | 8 KB | 64 | 3285823（+3.37%） | 3178667（不变） |

- **真实模型上的覆盖率**：对 Llama2-7B 的全部 224 个矩阵乘算子导出说明文件，
  仿真时全部 224 个都成功用上了新方式生成指令，没有一个退回固定模板。

### 第五步（反向接口）：GeneSim 提前指定一种切分方案，约束图编译器

**这是此前完全不存在的一段接口，本次新增。**

**要解决的核心矛盾**：图编译器和 GeneSim 描述"一台计算单元"用的是不同的粒度，
不能简单地把 GeneSim 的编号直接交给图编译器使用。

| | 图编译器眼中的"一台设备" | GeneSim 眼中的"一个处理单元" |
| --- | --- | --- |
| 容量 | 要装下整段流水线的全部权重（Llama2-7B 一段大约 1.5 GB） | 512 MB |
| 对应关系 | 一个"处理单元集群"（16 个处理单元合计 8 GB） | 集群里的一个处理单元 |
| 编号方式 | 从 0 开始连续编号，图编译器内部很多逻辑假设编号连续 | 全系统统一编号，与图编译器的编号是两套完全不同的数字空间 |

也就是说，图编译器的"一台设备"实际对应 GeneSim 的一整个"处理单元集群"（十六分之
一台物理集群更准确的说法是：一个集群刚好能塞下一台图编译器意义上的"设备"）。如果
不做区分，直接把 GeneSim 的处理单元编号塞进图编译器，会导致两个问题：一是概念上把
"一台设备"错误地等同成了"一个处理单元"；二是图编译器内部有多处代码假设设备编号是
从 0 开始连续的，直接传入不连续的大编号会在执行阶段报错崩溃。

**解决方式**：图编译器内部继续使用自己原有的连续编号，新增一份"逻辑设备编号 →
物理处理单元集群编号"的映射说明，双向都使用同一份映射：GeneSim 生成方案时写下这份
映射，图编译器编译时读它、并把它原样写回导出的说明文件，GeneSim 加载说明文件时再
按这份映射去分配资源，不再靠"编号取余数"这种碰运气的旧算法。

**挑选映射时考虑的两个物理约束**：

1. **通信带宽**：同一个处理单元集群内部的通信带宽是跨集群通信带宽的 4 倍。张量
   并行场景下，一段流水线内部的多台设备之间通信非常频繁，应该尽量让它们落在同一个
   集群里。
2. **容量限制**：如果要求"一段流水线内部的全部设备共用一个集群"，前提是这些设备
   的权重总量不能超过一个集群的总容量（8 GB）。按 Llama2-7B 实测，张量并行宽度到
   8（即整个模型都做纯张量并行、不做流水线切分）时，一段的权重总量达到 12 GB，
   超过单个集群的容量，这种情况下只能退而让这些设备分别使用不同的集群（此时段内
   通信必然要走较慢的跨集群带宽，这是硬件容量决定的，不是算法选择的结果）。

**新增和修改的文件**：

| 文件 | 内容 |
| --- | --- |
| `flagos-pim-compiler/contracts/partition_plan.py`（新增） | 定义"切分方案"这份文件的格式：流水线段数、张量并行宽度、逻辑设备到物理集群的映射等 |
| `flagos-pim-compiler/graph/strategy.py` | 新增一个转换函数，把切分方案转换成图编译器内部使用的切分策略对象 |
| `flagos-pim-compiler/scripts/export_pp_placement.py` | 新增命令行选项，可以选择"读一份切分方案文件"或"直接给流水线段数"两种方式之一来驱动图编译 |
| `flagos-pim-compiler/genesim_bridge/placement_export.py` | 导出说明文件时，把切分方案里的映射关系原样写进说明文件的顶层 |
| `genesim/scripts/export_fixed_pu_mapping.py`（新增） | GeneSim 侧生成固定切分方案的工具：按上述两个物理约束挑选处理单元集群 |
| `genesim/src/scheduler/gene_sim_scheduler.py` | 加载说明文件时读取映射关系，按它分配处理单元集群；文件里没有这个信息时，退回原有的取余数算法，保证不影响已有场景 |

**验证结果**：

1. **等价性检查（最关键的一条）**：用"读切分方案文件"和"直接给流水线段数"两种
   方式分别跑一次图编译，产出的说明文件除了新增的映射字段外，逐字段完全一致
   （224 个算子、九类字段全部相同）。这证明新增这条接口没有改变原有的切分逻辑，
   只是多了一条可选的输入来源。
2. **映射生效检查**：跑一次完整模拟，检查全部 224 个被指定了处理单元集群的算子，
   实际落位是不是都符合方案里声明的映射。结果是 224 个全部符合，零个例外。
3. **模拟结果**：这次验证用的场景恰好是"按旧算法取余数也能碰巧分对"的情况，所以
   模拟总耗时与旧算法结果一致（1331.79 秒），差异体现在别的场景——旧算法在有些
   配置下会把本该同属一段的设备分到不同集群，新方式能保证按声明的映射精确分配，
   不再依赖运气，配置变化时如果映射失效还会主动报错，不会静默算错。

## 五、修复的两个与本次主线相关的既有缺陷

开发第三步时，为了验证不同切分后的形状都能正常编译，发现算子编译流程原来有两个跟
"分块必须是二的整数次幂"这条硬件约束相关的缺陷：

**缺陷一**：判断一个数能不能拆成合适的二的整数次幂分块时，原来的算法在某些取值下
会直接返回一个不满足"二的整数次幂"要求的分块大小，导致后续编译报错。Llama2-7B 里
MLP 层的中间维度（11008）正好会触发这个问题——它不是二的整数次幂，任何切分方式下
都不是，原算法在这种输入下会算错。

**缺陷二**：算子编译入口处的形状检查过严，要求参与矩阵乘的三个维度都必须整体是
二的整数次幂，但实际只有其中一个维度有这个硬性要求，另外两个维度只需要"存在一种
拆分方式使得每一小块是二的整数次幂"即可。过严的检查把 Llama2-7B 的 MLP 层直接
挡在了门外，而且原代码里的注释错误地断言"真实模型的所有维度都满足二的整数次幂
要求"——这个断言与 Llama2-7B 的真实参数不符。

两处都已修复，并用真实数据验证过对拍结果：多组切分后的形状分别跑真实编译，与
标准数值计算结果对比，最大相对误差在千万分之二级别。

**修改的文件**：`flagos-pim-compiler/opcompiler_bridge/kernel_src.py`、
`flagos-pim-compiler/opcompiler_bridge/driver.py`。

### 权重容量口径的修正

除了前面四步之外，还发现并修复了一个容量统计口径的问题：图编译器算出"切分后每台
设备实际负责哪部分权重"之后，这个信息原来没有同步反映到 GeneSim 的容量检查逻辑
里——容量检查仍然按"整个模型的全部权重"去算，而不是按"这台设备实际负责的那一份"
去算。修复后，容量占用统计精确减半（张量并行宽度为 2 的场景下），跟切分比例完全
对应。这一项不影响模拟总耗时（因为权重加载耗时在热启动场景下本来就不计入总耗时），
只影响容量是否超限的判断，但这个判断关系到大流水线段数场景下是否会被错误地判定为
"容量不足"。

## 七、清理的冗余内容

开发过程中生成过一份用于验证 A/B 对比效果的配置文件，验证完成后发现原计划里为
另外三种切分策略各生成两份配置文件（共六份）超出了实际需要——A/B 对比只需要针对
一种典型策略验证清楚方法是否可靠，其余策略只需要能正常跑模拟，不需要各自的对比
变体。最终保留了三份策略配置加一份对比配置，删除了多余的三份。

另外，第五步反向接口在开发过程中先写了一版脚本（读取一份已经放置好的模型描述，
反推出切分方案），后来发现这种反推方式在有张量并行的场景下存在歧义（无法区分
"一个算子被拆成多份分别处理"和"多个独立算子各自处理"这两种情况），改为直接生成
固定方案的新脚本。旧脚本没有被删除，但也没有被任何其他脚本调用，是一份未清理的
遗留文件。

## 八、遗留问题

### 遗留问题一：GeneSim 目前只能生成固定方案，不能把自动搜索的结果转换成切分方案

GeneSim 内部有一套自动搜索最优放置方案的机制，但那套搜索机制描述的是"每一个算子
分别放在哪个处理单元上"，是逐个算子独立决定的，没有"一段流水线内部要不要做张量
并行、并行宽度是多少"这个更高层的概念。要把自动搜索的结果转换成本次新增的切分方案
格式，必须先解决"如何从每个算子各自的放置结果里，反推出统一的张量并行宽度"这个
问题，而这个反推在数学上是有歧义的（无法区分"算子被拆开的并行执行"和"多个独立算子
恰好被放到相邻的处理单元"）。

这个限制不是接口格式的问题——本次新增的切分方案格式本身预留了来源标记字段，未来
换成自动搜索的结果时格式不需要改动，需要改动的是 GeneSim 内部搜索机制的粒度，
这是一项独立的、工作量更大的改动，本次没有涉及。

### 遗留问题二：硬件参数存在四处独立定义，尚未统一

同一份硬件参数（单台设备的存储容量、并行处理单元数、地址对齐要求等），目前分别在
图编译器仓库的三个位置和 GeneSim 仓库的一个位置各自写了一遍，其中已经发现三处
数值互不相同：

| 参数 | 图编译器默认配置 | 图编译器实际调用时传入的值 |
| --- | ---: | ---: |
| 单台设备存储容量 | 8 GB | 4 GB |
| 并行处理单元数 | 16 | 4 |
| 地址对齐字节数 | 8 | 64 |

目前没有出问题，只是因为实际调用时传入的值覆盖了默认配置，但默认配置本身已经是
一个不会被自动发现的隐患——如果未来某处代码忘记显式传参，就会悄悄用错的默认值去
编译，而不会有任何报错提示。

另外，用于测试的模拟执行后端（不依赖真实存算一体硬件、用普通数值计算模拟执行
过程的那一层）目前只在测试代码里被构造，每个测试各自写一遍容量参数，从未与生产
链路实际使用的参数做过比对。

建议的解决方向是把这些参数集中定义在一个地方，图编译器和 GeneSim 各自需要多少
就从这个统一定义换算，而不是分别硬编码。图编译器的"一台设备"和 GeneSim 的
"一个处理单元"本来就不是同一个粒度（前者对应后者的一整个集群），所以不是要求
两边写同一个数字，而是要求两边的数字之间存在明确的、可以自动核对的换算关系，
并且这个换算关系应该由一条自动化测试保证——只要两边参数不一致，测试就会报错，
而不是靠人工记忆去维持一致。

这一项改动涉及图编译器仓库十四个测试文件里参数的来源，建议作为独立的后续任务
推进，本次没有实施。
