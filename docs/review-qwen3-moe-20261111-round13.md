## 二、修改建议
### 问题1（严重）: PV未按相位取整，导致数值偏离契约
　　**问题说明**：request §2.1 P0-1/P0-4/P0-5 与 design §1.2 要求执行结果与 HF 对齐；`PIMOps.td` 进一步明确每个块的 value product 必须先落 fp16 再加入 fp32 输出。`LowerPIMToEmitC.cpp:3027-3064` 却在块内以 fp32 累加 `dot` 后，直接计算 `acc * alpha + dot`，没有调用 lowering 已有的 `roundF16`；主机 `matmul` 正常编译路径在 `runtime/kernels.py:824-827` 返回 fp16，二者存储边界不同。多出的精度不是等价优化：每次 RNE 取整都会改变后续累加输入，块数增加时还会继续传播。合法块表探针中，编译输出与未取整参考逐元素相同，但与契约参考有 16 个元素不同、最大差 0.00048828125，证明这是有效执行路径上的实际偏差，而非只存在文字差异。
　　**根本原因**：相位实现没有由统一的存储边界契约驱动，PV 这一处漏掉取整；`test_paged_attn_matches_the_online_reference` 又在 `tests/test_opcompiler_ops.py:1512-1517` 手写了同样未取整的参考，使实现和测试共享错误假设。现有用例只覆盖一个有效块，既不能发现该偏差，也没有覆盖多块重标定后的传播。前几轮修复独立 HF 参考时只替换了 MoE 真值来源，没有排查这个算子级自证参考。
　　**涉及文件**：`flagOS-installers/FlagTree/lib/Dialect/TritonPIM/Transforms/LowerPIMToEmitC.cpp:2813-2816,3027-3064`；`flagOS-installers/FlagTree/include/triton/Dialect/TritonPIM/IR/PIMOps.td:1636-1639`；`flagos-pim-compiler/runtime/kernels.py:806-827`；`flagos-pim-compiler/tests/test_opcompiler_ops.py:1451-1520`；本轮 `logs/paged_attn_emitc.cpp`、`logs/probe-paged-attn.log`。
　　**修改思路**：以一份相位存储边界表统一 lowering、主机参考和测试，按已声明契约在块 PV 写回 fp32 累加器前完成 fp16 取整，并逐相核对 QK、掩码、指数、求和、PV 与最终输出，避免只修当前一个算子。测试参考必须独立于被测 lowering，覆盖单块、多块、尾块与会产生不同 RNE 的数值，既做逐元素对拍，也在 lit 中约束对应取整调用；若确要改成 fp32 PV 语义，应先回设计确认并同步修改算子契约与主机路径，不能继续用当前自洽测试代替确认。
### 问题2（严重）: 负槽号直接寻址，导致缓存越界
　　**问题说明**：分页注意力的正确性依赖块表项指向合法物理槽，非法项不能与槽 0 混同。`LowerPIMToEmitC.cpp:2889-2900` 的注释声称尾部 `-1` 会夹到槽 0，实际仅判断有符号 `slot < poolSlots`，没有 `slot >= 0`；实际 EmitC 对 `slot=-1` 得到条件为真，随后计算 `kOff/vOff + (-1) * slotElems`，在默认偏移下落到缓存之前，既可读错数据也可造成内存故障。大于等于 `poolSlots` 的项又被静默换成槽 0，同样会把非法输入算成另一物理槽。主机 `_iter_kv_blocks` 在 `runtime/kernels.py:1553-1555` 对负项明确报“未分配”，两条执行路径语义不一致。
　　**根本原因**：块表有效性只做了上界判断，注释、主机校验和设备 lowering 没有共享一份契约；测试 `test_paged_attn_matches_the_online_reference` 只使用合法的 `[1,3]` 乱序块表，未覆盖负值、上界及未分配项。相同根因同时影响 K/V 两个基址与任意负块号，不是单个 `-1` 探针的局部问题；槽 0 和 `poolSlots-1` 则是合法边界，不能一刀切拒绝。
　　**涉及文件**：`flagOS-installers/FlagTree/lib/Dialect/TritonPIM/Transforms/LowerPIMToEmitC.cpp:2889-2900`；`flagos-pim-compiler/runtime/kernels.py:1425-1454,1540-1557`；`flagos-pim-compiler/tests/test_opcompiler_ops.py:1451-1520`；本轮 `logs/paged_attn_emitc.cpp:153-164`、`logs/probe-paged-attn-block-table.log`。
　　**修改思路**：在主机预检与设备 lowering 间统一块表不变式 `0 <= slot < poolSlots`，所有本次历史实际读取的项都必须满足；非法项应按主机现有语义明确失败，不能用槽 0 替代，表尾不参与本次历史的哨兵则不得读取。若产品确需允许 `-1` 哨兵进入计算，先回设计统一语义，再实现与参考一致的处理。共享同一校验函数或契约生成逻辑，并补主机/编译路径的负值、上界、未分配、槽 0、最后合法槽与多块尾块测试，同时检查 K/V 地址而不只检查最终是否崩溃。
### 问题3（高）: 严格入口缺产物放行，导致复核结果失真
　　**问题说明**：design §十.4-5 要求显式严格开关或 sidecar 自报任一成立时，导出、skip-simulation、freshness、仿真 IR 与 trace 都按完整产物契约验收。`verify_sidecar_freshness` 只在 `ir_path` 存在时调用共享验证器；`verify_sim_ir_matches_sidecar` 在没有 sidecar 配置键时直接返回；`verify_trace_provenance` 在缺 IR 或 sidecar 时只检查来源白名单便返回。实测配置保持显式严格：删除 sidecar 键，三个入口均接受；sidecar 文件缺失，trace 仍接受；删除 IR 键，三个入口均接受；删除 IR 文件，freshness 也接受。于是缺了进行同源核对所需的核心输入，独立复核仍能签发通过。
　　**根本原因**：旧式“无对象可比对就跳过”的兼容分支在读取严格性上下文之前执行，round12 只把 `strict_pimir` 传入已经到达共享验证器的路径，没有收敛这些提前返回。导出与 skip-simulation 另有显式严格检查，直接 GeneSim 也会在生成 trace 前拒绝，因此本轮不把它们误判为同样可绕行；正式主链的连续预检与空 trace 目录也降低了实际漏跑概率，但不能反向证明三个独立入口的结果正确。现有测试只覆盖非严格无 sidecar 正例及删自报后的容量字段，没有缺 IR/sidecar 的严格矩阵。
　　**涉及文件**：`flagos-pim-compiler/scripts/run_full_pipeline.py:1537-1574,1577-1613,1616-1714`；`flagos-pim-compiler/tests/test_genesim_simulation.py:131-137,1569-1632`；`docs/design-qwen3-moe-20261105.md` §十.4-5；本轮 `logs/probe-round13.log`。
　　**修改思路**：把配置解析和严格性判定提到所有兼容返回之前，严格模式下 IR、sidecar 的配置键与实际文件均为必需输入，任一缺失都在 freshness、仿真 IR、trace 各自入口直接失败，再调用同一个完整验证器；只有调用方和产物都明确非严格时才允许无 sidecar 的旧式用法。按“配置严格/非严格 × sidecar 自报有/无 × IR 键/文件缺失 × sidecar 键/文件缺失”建立全入口矩阵，同时保留合法旧产物、纯放置与合法 host/边界正例，避免把兼容路径误伤。
### 问题4（高）: trace未绑定MLIR哈希，导致错产物放行
　　**问题说明**：design §十.4 要求 sidecar 的 `pimir_path/pimir_sha256` 与实际消费产物闭合，trace 验收要证明源 IR 应覆盖集合真实使用 pimir。`verify_trace_provenance` 在 `run_full_pipeline.py:1644-1662` 只读取 `trace_source`、op_id/parent_op_id 与 tile 统计，未读取 trace 已写入的 `compile_signature.pimir_sha256`，也没有与对应 sidecar 条目比对。实测正确哈希的 trace 接受后，将其中一条改成 64 个零，仍返回 ACCEPTED；缺少该字段的测试夹具同样被接受。只凭 `trace_source=pimir` 和父编号，不能证明这条 trace 是由 sidecar 指向的那份 MLIR 生成。
　　**根本原因**：round04 的覆盖修复把“来源标签 + 父算子集合”当成完整 lineage，sidecar 文件哈希与 trace 编译签名分属两条未连接的校验链；现有 trace 夹具也只写来源，未形成真实哈希正例。主链每次使用独立空 trace 目录降低了旧 trace 复用风险，本轮对 4 层 10906 条和 48 层 130806 条实际 trace 的附加审计又确认哈希全部正确，所以这是验收器缺口，不是指控当前产物已错配。
　　**涉及文件**：`flagos-pim-compiler/scripts/run_full_pipeline.py:1644-1662,1698-1714`；`genesim/src/scheduler/gene_sim_scheduler.py:2897-2899,3023-3048`；`flagos-pim-compiler/tests/test_genesim_simulation.py:1544-1563,1670-1681`；本轮 `logs/probe-trace-hash.log`、`logs/audit4l.json`、`logs/audit48l.json`。
　　**修改思路**：把 trace 验收扩展为逐条 `(parent_op_id, op_type, pimir_sha256)` 与源 IR/sidecar 的联合核对：pimir trace 必须有可解析父编号、正确类型和与 sidecar 相同的非空编译签名哈希，TP 分片回指同一源条目；absorbed 只接受已通过融合结构证明的空 trace。缺哈希、错哈希、错父编号或拿另一形状/分块产物都必须失败，并继续执行来源与应覆盖集合检查。用真实带哈希产物作正例，增加删哈希、换哈希、换分块及合法多分片反例，避免只修来源标签。
### 问题5（中）: 正文标签归属不闭合，导致错配证据放行
　　**问题说明**：round11/round12 要求建立“运行身份 → summary → 指标 → 正文语境”的绑定，并拒绝只交换正文、4 层冒充 48 层、历史冒充 current 与错误比较。`_prose_context_problems` 却允许数值属于所在块内任一前置标签，`check_document` 对必需值仍只做全篇字符串存在检查，`_check_comparisons` 也只比较两个数值大小而不核对运行身份。实测原文与本轮 summary 通过；追加“dense 与 dynamic 中，前者 88.483 s 低于后者 91.012 s”这一运行语义对调句仍通过，因为两个标签和数值关系都分别合法；只把全部必需指标放在无标签前言、正文标签后不再给值，也通过必需值检查。合法同块比较则照常放行。
　　**根本原因**：round12 用“块内前置标签集合”代替逐值归属，没有处理同块多运行的位置关系，也没有把必需值检查限定到对应运行锚点；比较器进一步丢失了左右操作数身份。新增测试只覆盖单标签块和值完全缺失，未覆盖同块对调、无标签汇集及比较身份交换，属于前一轮只让当时探针变绿而未收敛同类路径。当前实施文档已有数值经本轮 summary 复核正确，本问题是防复发机制仍可放行未来错证，不是再次宣称现有正文抄错。
