另外顺手修了两个真 bug：

- `runtime/kernels.py` 的 `_cache_key` 漏了 `out_dtype`，f16→i8 与 f16→f32 两条请求落到同一个 `.so` 上；`ctypes.CDLL` 按路径缓存句柄，第二次拿到的是第一份的代码。补进缓存键。
- `gather_kernel` 只读前两个实参，而 `aten.embedding` 在 `pad_token_id` 非空时会带 `padding_idx`，实参不止两个，直接解包报错。

## 二、运行时现在真的走到算子编译器的是哪几个

判据：给 `compile_op` 打桩，跑一次真实的 `compile_llama2` + 解码循环，数每个 mnemonic 被调了几次。

| mnemonics | 调用点 |
| --- | --- |
| `linear` | `_LINEAR` 的 A 路 |
| `eltwise` | `_compiled_eltwise`（add / mul / sub 同形状） |
| `dynamic_quant` | `_compiled_dynamic_quant` |
| `softmax` | `_compiled_softmax` |
| `mask` | `_compiled_mask`（注意力那笔加性掩码也走它） |
| `gather` | `gather_kernel` |
| `matmul` | `_compiled_matmul`（**本轮新增**，fp16 形态） |
| `convert` | `_compiled_convert`（**本轮新增**） |

未走编译器的六个：`normalize` / `rope` / `kv_cache` / `lut` 在运行时是 `kernels_pim` 的设备镜像（`transpose` / `reshape` / `split_heads` / `concat` 同）。它们仍是**设备算子**——由 `hal.submit` 提交、读写 DPU 本地地址空间，不是主机回调；缺的只是"经过算子编译器编出 `.so`"这一步。

## 三、`pim.matmul` 的 fp16 形态

矩阵单元不区分元素类型，`LowerPIMToEmitC` 的 `loadFlat` / `storeFlat` 本来就按 `FlatBuffer` 的元素类型取值（f16 走 `pim_f16_to_f32` / `pim_f32_to_f16`）。缺的只是发射侧那一种形态：

```
matmul_kernel(..., fp16=True):
    %y = pim.matmul %a, %w {datapath = #pim.datapath<nmuMode = floating_point,
                                                 scaleMode = floating_point>}
       : tensor<MxKxf16>, tensor<KxNxf16> -> tensor<MxNxf16>
```

两条约束：

- **不发 `weightBinding`**：那是描述权值侧字段的，两个激活相乘没有权值侧。
- **不发 `stationarity`**：写成 `kv`，verifier 就要求 `weightBinding` 声明 `role = activation_as_weight`，而那是 int8 权值路的说法；这两个缓冲这里是 fp16 激活，硬套一份权值绑定等于给读回侧一个不成立的事实。

已实测：4×8×4 / 1×16×16 / 3×128×4 三种形状编出的 `.so` 与 `x @ w` **逐元素相同**。

## 四、`pim.convert` 的两侧类型

上一轮评审说这个算子"构造不出合法实例"，**不成立**。实测 `triton-opt` 接受 `tensor<4x8xf16> -> tensor<4x8xi8>` 并正确降低成 `pim_f16_to_f32` + 逐元素存储。真正的问题在发射侧：

- `convert_kernel` 把源侧写死成 fp16 → `f32 → f16` 会被发成 `f16 → f16`，而 verifier 拒绝同类型。实测这条把三条策略扫描的端到端用例一起打挂。
- 目标类型写死成 `i8`，`OpCompileRequest` 里根本没有位置放它。

现在两侧都从契约取（`dtype` 是源、`out_dtype` 是目标），同类型在**发射侧**就拒绝，不留给 verifier。

## 五、三条路径的覆盖

| 路径 | 状态 |
| --- | --- |
| GML | 18 类 `op_type`（新增 `Gather`），结构自检 5/5、引用集 == 落盘集、接入算子编译器前后逐字节相同（499408 字节 / 204 节点）、砍相位反证成立。`--decode-block-only` 产物与上一轮**逐字节相同**。`Convert` 在这张图上是 0：6 个 `to.dtype` 全是恒等的 f32→f32，按"位宽真变才发"本就不该发；带 `int64→float32` 真转换的图会发 1 个 |
| numpy 假后端 | 14 个 mnemonic 都能 `compile_op` 出 `.so` 并与镜像逐元素一致；其中 8 个在运行时真的被调用 |
| genesim | B 路 sidecar 覆盖全部 14 个 mnemonic（实测：计算类 `flops > 0`，视图类 `data_bytes > 0`），桥接 6850 个算子；相位链解析不再丢相 |

### `llama2_7b` 那 8 条失败的归因

它们**不是本轮引入的**。做法是把本轮动过数值的三处全部按改动前的写法禁用——`matmul` 退回 `x @ w`、`convert` 退回 `astype`、注意力四段退回原来的三行——再跑一遍完整的那 42 条：

| 配置 | 结果 |
| --- | --- |
| 本轮改动生效 | 8 failed / 32 passed / 2 skipped |
| 三处数值改动全部禁用 | **8 failed / 32 passed / 2 skipped，失败的是同样那 8 条** |

失败清单逐条相同，所以本轮改动在 `llama2_7b` 这组上**没有引入任何新失败**。

失败信息本身也指向别处：`tp4_pp2 layer0 dpu0 head0 K 区不匹配: max diff 0.6396`，比的是**写进 KV 缓存的内容**，而那段写入代码本轮一个字都没动；前几行逐位相同、从靠后的一行起才分开，是"某个位置的 K 值写错"的形状，不是舍入。而且**只有 `tp4_pp2` 这一个策略失败**，问题在切分或 KV 布局。

上一轮文档里"本仓 Llama2 42 例通过"这句，在当前工作区上复现不出来——这 8 条是既有失败，需要单独定位，不能当成已经达标的既有事实。

## 八、当前存在的不足

1. **图级拆头没做。** 方案 1.2.4 第 246 行要求"拆头后的 QKᵀ / mask / softmax / PV / KV 全部 `hal.submit` PIM kernel"。现在这四段**各自走设备算子**了，但它们仍在一条 `sdpa` 设备命令里、图上也仍是一个 `aten.scaled_dot_product_attention` 节点。真正拆头要解决 KV：图用 `use_cache=False` 导出，decode 时注意力要读的是缓存里的历史 K/V，而图上只有当前 token 的一份，拆头后 K 操作数的形状对不上。这是 `graph/kv_dma_pass.py` 模块说明里记着的那条取舍，要用户定案。
2. **`normalize` / `rope` / `kv_cache` / `lut` 仍是设备镜像。** 让它们走编译器需要把融合后的锚点改成单节点 kernel：`fuse_pim` 只标注不删节点，链上 `pow → mean → rsqrt` 仍各算一步、每步落一次 fp16；而 `kernels_pim.normalize` 与 C 侧都在 f32 里一次算完。两者不是同一个数（PyTorch 自己的 RMSNorm 反而与后者一致），合并会改变现有对拍数值，要先定案。
3. **`subBlocks` / `broadcastSpec` / `combineMode` 三个属性有定义、无生产方。** 方案 5.16 说 `subBlocks` 是"6 个 `#pim.fpsu_spec`"，而 verifier 与 `contracts/gml_hw_constants.py::ROPE_UNITS` 按 6 个**名字**核对——两处语义已经不一致，要先定案再补生产方，不能自己挑一个。
4. **`pim.rtl-version` 仍是裸字符串跨仓传**（写侧 `oplevel_emitter.py`，读侧 `phase_source.py` 正则抠）。
5. **`--layers 1` 的节点数从 203 涨到 204**：多出来的是 `Gather`（方案 1.2.4 要求"全模型必须发"）。参考产物是 decode 块、本来就没有这个词，所以"203 / v2 的 200"这条口径要跟着改。
6. **`pim.dynamic_quant` 在 genesim 侧仍是 `QUANT` op_type**，与 GML 的 `DynamicScaling` 不是同一个名字；sidecar 里靠 `source_name` 区分。这是既有约定，不是本轮引入的。
7. **genesim 骨架一改，A 路的产物要重生成——这条依赖是隐式的。** 这一轮把 Llama2 骨架扩到 6852 个算子，旧的 `models/llama2_7b_flagtree.ir` / `llama2_7b_pimir.ir` 与新骨架对不上被删了，而 `run_full_pipeline.py` 的 [E] 步直接读 `models/llama2_7b_pimir.ir`，删掉它整条全链路就跑不起来（实测 `File not found: models/llama2_7b_pimir.ir`）。已重跑 `refine_ir_with_flagtree.py --ir-level pimir` 补回。**改骨架必须重跑这一步**，它没有写在 `run_full_pipeline.py` 的步骤里。
   另外 `--ir-level pimir` 在本机也要私有 `/dev/shm`：FlagGems 的 `LibEntry` 会建 `multiprocessing.Lock`，`/dev/shm` 满时直接 `ENOSPC`。
8. **`llama2_7b` 那 8 条失败要单独定位。** 已排除与本轮改动的关系（见上表），但它们是真失败：`test_real_llama2_7b_kv_region_matches_hf_cache_under_every_strategy` 只在 `tp4_pp2` 这一个参数下失败，比的是写进 KV 区的 K/V 与 HF 的 `past_key_values`（rtol 2e-2 / atol 3e-2），实测 max diff 0.6396；**只有这一个策略失败**说明问题在切分或 KV 布局，不在注意力的数值上。这条不属于本轮三个目标，但要挂账。
