## 一、修改概述

### 1.1 一句话

算子编译器产出的中间表示（下称 pim mlir）本该决定仿真的代价，但这条消费链路上有
五个地方会**不报错地给出偏掉的数字**。本轮把它们逐个堵住，并给每一个配上能真正
失败的回归测试。

### 1.2 五个问题的共同特征

```
              ┌─────────────────────────────────────────────┐
              │  它们都不会让仿真崩溃或报错                  │
              │  仿真照常跑完，给出一个看起来合理的总耗时     │
              │  只是那个数字是错的                          │
              └─────────────────────────────────────────────┘
```

这类问题比崩溃危险：崩溃会被立刻发现，而"跑通了但数字偏了"会被当成结论用下去。

### 1.3 五个问题一览

| 编号 | 问题 | 后果 | 现在会不会踩到 |
| --- | --- | --- | --- |
| 一 | pim mlir 路径失效后静默退回手写模板 | 分块从实测的 128/512 变回配置里的 32 | 换机器、清缓存后必然 |
| 二 | 代价缓存的签名不含 pim mlir 内容 | 换了算子编译产物仍复用旧代价 | 已有真实碰撞样本 |
| 三 | 改了指令生成语义却不提版本号 | 修复完全不生效 | 修问题四时实际发生了 |
| 四 | 外层预取按每个归约步重复计费 | 搬运量放大到 128 倍 | 当前不会，算子编译器改了就会 |
| 五 | 权重字节缩放不幂等 | 重复调用一路除下去（1/2 → 1/4 → 1/8） | 当前不会，多一处调用就会 |

问题三是修问题四时**当场撞上**的：改完发射语义跑一遍，日志显示一份都没重编，
等于改了没生效。

### 1.4 涉及的仓库

| 仓库 | 是否改动 |
| --- | --- |
| 仿真器（`genesim`） | 改动主体 |
| 图编译器（`flagos-pim-compiler`） | 导出侧记录内容哈希、全流程脚本增加核对 |
| 算子编译器（`FlagTree`） | **零改动** |

## 二、修改原理

### 2.1 这条链路本来的样子

```
算子编译器
   │  产出 pim mlir（真实的分块、真实的搬运结构、真实的循环嵌套）
   ▼
图编译器：写一份说明文件（sidecar）
   │  记下每个算子的：切分后形状、实测分块、pim mlir 的落盘路径
   ▼
仿真器：照 pim mlir 生成指令序列
   │  这一步让编译器的真实决策进入周期数
   ▼
仿真出的总耗时
```

关键在最后一步"照 pim mlir 生成"。如果这一步悄悄换成了"照手写模板生成"，
链路看起来没断，但编译器的决策完全没进去——手写模板的分块会在计算里约掉，
换分块几乎不改变结果。

### 2.2 问题一的原理：绝对路径 + 静默回退

说明文件里记的是**导出那台机器上的绝对路径**：

```
/media/disk/.../flagos-pim-compiler/.opcompiler_cache/818fc5c140a11601.pimir.mlir
```

换机器、换代码目录、或者缓存被清掉，这个路径就失效了。原来的处理是：

```
读得到  →  照 pim mlir 生成指令          ← 想要的
读不到  →  打一条警告，照手写模板生成      ← 问题所在
```

一条警告在几千行日志里等于不存在。仿真跑完、有数字、没报错，没人会去查那条警告。

**修法两条**：

一是允许配置成"必须消费成功"：

```
scheduler.require_compiler_pimir: true   →  读不到就报错，拒绝退回模板
                              false      →  保持原行为（默认，向后兼容）
```

默认保持 `false` 是因为"纯放置导出"这种用法本来就不带算子编译产物，那是合法的。
但三份 `*_globalcost.yaml` 配置全部打开了——那些配置存在的意义就是"按实测分块算
成本"，读不到产物时它们的结论根本不成立。

二是让失效路径能自己找回来：

```
        原路径                          ← 先试这个（同机器、缓存还在）
          ↓ 不存在
   配置的搜索目录 + 原文件名             ← scheduler.pimir_search_dirs
          ↓ 不存在
说明文件同级的 .opcompiler_cache/ + 文件名  ← 自动尝试，往上找几级
          ↓ 都不存在
   报错（严格模式）或警告后退回（默认）
```

按文件名找回是安全的，因为**文件名本身就是算子编译缓存的内容哈希**——同名必然是
同一份产物。

### 2.3 问题二的原理：缓存签名漏了最关键的输入

仿真器会缓存"这个算子的指令序列"，避免每次重编。判断缓存能不能用，靠一个签名：

```
改前的签名 = 配置参数 + 算子类型 + 输入形状 + 输出形状 + 分块大小
                                                   ↑
                                    pim mlir 的路径、内容、哈希
                                          一个都没有
```

后果：同形状、同分块，但 pim mlir 换了，仍然命中按旧产物编出来的缓存。

**这不是假想的风险**。算子编译缓存里就有这样一对：

| 文件 | 输出宽度 | 输入宽度 | 分块 | 内容哈希 |
| --- | ---: | ---: | ---: | --- |
| `3db3ddb67e081b5c` | 2048 | 4096 | 512 | `fc746db5` |
| `818fc5c140a11601` | 2048 | 4096 | 512 | `34d1d4ff` |

签名能看到的三项完全一样，两份文件却差 71 行：

| 属性 | 前者 | 后者 |
| --- | ---: | ---: |
| 设备数 | 1 | 8 |
| 并行执行单元数 | 1 | 4 |
| 搬运对齐字节 | 8 | 64 |
| 设备内存容量 | 8 GB | 4 GB |

并行单元划分和循环嵌套都不同，但签名认不出差别。

**修法**：签名加两个字段。

| 新字段 | 作用 |
| --- | --- |
| `pimir_sha256` | pim mlir 的内容哈希。内容变了签名就变，旧缓存自动失效 |
| `trace_source` | 记录走的是 pim mlir 还是手写模板。"上轮没产物、这轮有了"也必须重编 |

签名里放**内容哈希**而不是路径，是刻意的：路径是编译机的绝对路径，换机器就变，
放进签名会造成无谓的全量重编。

**为什么这个问题此前从未显现**：全流程脚本每轮开跑前会删掉整个代价缓存目录。

```python
# scripts/run_full_pipeline.py
traces = genesim / "pim_traces"
if traces.is_dir():
    shutil.rmtree(traces)     # 注释写的是"这一轮要确实重编过"
```

意图正当，但副作用是全流程永远从零编译，签名不完整这件事在全流程里永远暴露不出来。
只有普通用户直接跑仿真（不清目录）才会命中旧缓存。

这一点值得单独强调：前一轮工作里那些"指令来源全部是 pim mlir"的验证结论，
是在**脚本清空缓存**的前提下取得的。结论在全流程语境下成立，但当时不足以推广到
普通运行。

### 2.4 问题三的原理：签名要覆盖"翻译器自己"

修完问题四（改了指令生成语义）之后跑一次仿真，日志是：

```
Prepared 1665 PIM traces in pim_traces (0 compiled, 1665 reused)
```

**一份都没重编。** 磁盘上那 1665 份是按**旧语义**编出来的，却被当成有效缓存复用了,
改完等于没改。

原因是签名里的 `schema_version` 一直停在 6。这个字段的职责正是描述"翻译器怎么把
输入变成指令"：

```
签名的其余字段  →  描述"输入是什么"（形状、分块、配置、内容哈希）
schema_version →  描述"翻译器怎么处理输入"      ← 语义变了必须提
```

**修法**：提到 7，并在代码里写明规则"改动发射语义必须提这个版本号"。

这三个问题（二、三，加上问题一的 `trace_source`）其实是同一件事的三个面：

```
       代价缓存的签名必须覆盖影响结果的每一个因素
                        │
      ┌─────────────────┼─────────────────┐
      ▼                 ▼                 ▼
   输入是什么        怎么消费的        翻译器什么语义
 （内容哈希）    （产物还是模板）    （schema_version）
      问题二          问题一            问题三
```

缺任何一个，都会出现"改了没生效"或"换了没重算"。

### 2.5 问题四的原理：搬运位置决定计费次数

矩阵乘的指令结构是两层循环：

```
输出宽度循环（外层，跑 n_iterations 次）
    └─ 归约维循环（内层，跑 k_iterations 次）
           └─ 搬运操作数 + 若干次乘加
```

一条搬运指令放在哪一层，决定它被计费多少次：

```
放内层：计费 n_iterations × k_iterations 次
放外层：计费 n_iterations 次
```

llama2 的 4096 深投影上，`k_iterations` 是 128 —— **放错层差 128 倍**。

改前的解析代码把外层搬运合并进了内层列表：

```python
inner_loads=inner_loads + _shapes(_DMA_LOAD_RE, outer_text),   # 改前
```

而生成指令时，这个列表整个放在归约循环体内。所以外层的预取会被当成每个归约步都
搬一次：

```
正确：                          改前（错误）：
外层循环 ─┬─ 预取（1 次）        外层循环 ─── 归约循环 ─┬─ 预取（128 次！）
          └─ 归约循环 ─ 操作数                          └─ 操作数
```

**当前为什么看不出来**：算子编译器现在产出的 kernel 把两个操作数搬运都放在归约
循环内，外层没有搬运指令，所以那个列表实际上总是空的。但把预取提到外层是常见的
优化，算子编译器一旦这么做，搬运量立刻放大 128 倍。

**修法**：解析时把外层搬运单独归到新字段 `outer_loads`，生成指令时放在归约循环
**之前**。

### 2.6 问题五的原理：就地改写 + 没有幂等保护

切分之后一台设备只持有权重的一部分，所以权重字节数要按"本地面积 / 全局面积"这个
比例缩小。原实现是**就地改写**依赖边上的字节系数，且没有记录"这条边已经缩过了"：

```
调用第 1 次：393216 × 0.5 = 196608     ← 正确
调用第 2 次：196608 × 0.5 =  98304     ← 又乘了一遍
调用第 3 次： 98304 × 0.5 =  49152
```

**危害方向**：权重字节偏小 → 容量检查偏松（本该报"容量不足"的配置被放过）、
权重首次加载的搬运时间偏短。两者都不报错。

**当前为什么没出问题**：调用点只有一处。但那是调用点的巧合，不是这个函数的保证——
多一处调用（换个入口、加个对照实验、测试里连着调两次）就会踩到。

**修法**：按"（目标算子，张量身份）"记下已缩放的比例，第二次调用直接跳过。如果同一条边
被要求按**不同**比例缩放两次，说明标注流程有冲突，直接报错而不是取其中一个。

### 2.7 顺带补上的本地形状校验

本地分片形状来自说明文件，是外部输入。原来一个校验都没有，而错了同样不报错：
偏小让容量检查偏松、代价偏低，偏大让容量检查误报。

补了四类校验：

| 校验 | 拦住什么 |
| --- | --- |
| 正数 | 0 或负数会让面积比变成 0 或负值，权重字节直接归零 |
| 不超过全局 | 分片不可能比整体还宽 |
| 整除 | 切分是等分给若干台设备，除不尽说明宽度与切分数不匹配 |
| 切分方向 | 只按输入维**或**输出维切一边；两边同时变窄不是任何一种切法 |

最后一项的道理：

```
列切（按输出维）：输入宽度不变，输出宽度变窄
行切（按输入维）：输入宽度变窄，输出宽度不变
两边同时变窄  ：不是任何一种张量并行切法 ← 多半是标注时把两个算子的形状串了
```

## 四、结果

### 4.1 问题一：严格模式与路径找回

用真实说明文件双向实测（把路径改成一个不存在的目录，模拟换机器）：

| 场景 | 结果 |
| --- | --- |
| 路径失效 + 严格模式 | 报错，并提示"请确认算子编译缓存可访问，或配置 `pimir_search_dirs`" |
| 路径失效 + 配了搜索目录 | 按文件名找回成功，读到 8313 字节 |
| 路径失效 + 默认模式 | 警告后退回模板（向后兼容） |
| 说明文件压根没写这一项 + 严格模式 | 不报错（纯放置导出是合法用法） |

### 4.2 问题二三：缓存不再错误复用

**暖缓存实测**（这是全流程脚本的删目录行为此前掩盖掉的场景）：磁盘上留着上一轮
`tp8_pp1` 编出的 4416 份代价缓存，**不清空**直接跑 `tp2_pp4`：

```
Prepared 1665 PIM traces in pim_traces (1665 compiled, 0 reused)
Total time: 1418.109246 s
```

1665 份全部重编、**零复用**，而总耗时与清空缓存那轮**一致到小数位**。两件事同时
成立才说明修好了：既没有错误复用，也没有因为改动而改变正确结果。

**版本号实测**：改完问题四之后，同一批缓存：

| 版本号 | 日志 |
| --- | --- |
| 停在 6（改前） | `0 compiled, 1665 reused` ← 改了没生效 |
| 提到 7（改后） | `1665 compiled, 0 reused` ← 强制按新语义重编 |

### 4.3 问题四：外层预取的计费

造一条外层预取（1×512 的半精度 = 1024 字节）实测：

| 计费方式 | 字节数 |
| --- | ---: |
| 正确（每输出分块一次 × 4 个分块） | 4096 |
| 误按内层（再 × 128 个归约步） | 524288 |
| **实测结果** | **4096** |

### 4.4 问题五：幂等

```
原始权重字节: 393216（张量并行宽度 2，应缩到 196608）

改前：                          改后：
  第 1 次: 196608  = × 0.5        第 1 轮: 196608  = × 0.5
  第 2 次:  98304  = × 0.25       第 2 轮: 196608  = × 0.5
  第 3 次:  49152  = × 0.125      第 3 轮: 196608  = × 0.5
```

### 4.5 对既有结果的影响

| 配置 | 修复前 | 修复后 |
| --- | ---: | ---: |
| `tp2_pp4` | 1418.109 秒 | 1418.109 秒 |

数值不变是**符合预期**的：问题四的修复只在"外层有预取"时改变结果，而当前算子编译器
产出的 kernel 外层没有搬运指令。这一轮修的是**完整性**——防止将来产生偏差，而不是
纠正当前已有的偏差。唯一例外是问题五，但它当前的调用点只有一处，也没有实际触发。

## 六、不足与遗留问题

### 6.1 内容哈希只覆盖 pim mlir，不覆盖翻译器代码本身

签名里的 `schema_version` 是**手工维护**的：改了指令生成语义要记得提。问题三正是忘记
提版本号造成的，而修法仍然是"记得提"，没有机制保证。

更彻底的做法是把翻译器源码的哈希放进签名，改代码自动失效缓存。代价是任何无关改动
（改注释、改日志）都会触发全量重编，在开发过程中很烦。当前选择了手工版本号加代码
注释提醒，属于折中。

### 6.2 外层搬运的正确性只有构造测试，没有真实样本

问题四的修复用一个人工构造的"外层有预取"的 kernel 验证。当前算子编译器不产生这种
kernel，所以没有真实样本可对。等算子编译器真的把预取提到外层，应该再用真实产物核对
一遍——构造的样例可能漏掉真实产物里的某些结构（例如多条外层搬运、或者外层搬运
与内层共用缓冲区）。

### 6.3 路径找回依赖"文件名就是内容哈希"这个约定

按文件名在搜索目录里找回 pim mlir，前提是文件名唯一标识内容。当前算子编译缓存确实
用内容哈希做文件名，但这是**另一个仓库的实现细节**，没有任何机制保证它不变。如果
将来改成按序号命名，这个找回逻辑会静默地找到错的文件。

缓解办法是找回之后核对内容哈希（说明文件里现在有这个字段）。这一步还没做——当前
只在全流程脚本里核对，仿真器侧的找回路径没有核对。

### 6.4 严格模式默认关闭

`require_compiler_pimir` 默认 `false`，只有三份 `*_globalcost.yaml` 打开了。这意味着
新写的配置文件如果忘记打开，仍然会静默退回模板。

保持默认关闭是为了兼容"纯放置导出"这种合法用法（不带算子编译产物）。更好的做法是
让说明文件自己声明"我带了算子编译产物"，仿真器据此自动决定是否严格——这样就不依赖
配置文件写对。当前没做。

### 6.5 形状校验假设"只按一个维度切"

校验里拒绝"输入输出两边同时变窄"。这对当前支持的两种切法（列切、行切）是对的，
但如果将来支持二维切分（同时按输入和输出维切，把设备排成网格），这条校验会误报。
届时需要让说明文件显式声明切分方向，而不是从形状反推。

### 6.6 幂等键的第一版设计有缺陷（已修）

这一条记录一个**在本轮内部发现并修掉**的问题，因为它说明了幂等这类改动容易踩的坑。

幂等闸门第一版用"（目标算子，张量身份）"做键。这个键分不清两种情况：

```
情况甲：同一条边被调用两次        ← 应该跳过第二次
情况乙：两条不同的边共用一个身份   ← 两条都该缩放
```

后果是情况乙的第二条边被误判成"已经缩放过"，永远保持全局字节数。实测确认过：

```
两条同身份权重边，各 393216 字节，应各缩到 196608
第一版键的结果：[196608, 393216]   ← 第二条没缩
```

这不是假想情况：真实的模型描述里，同一个算子确实可能有多条同名权重边（分组查询
注意力的键值权重按 head 分成多条）。

修法：键里加上**依赖边在列表里的下标**，变成"（下标，目标算子，张量身份）"。下标在
一次调用里稳定，跨结构复制也稳定（列表顺序不变），正好区分这两种情况。

修后结果：`[196608, 196608]`，且重复调用三次仍然不变。已补回归测试
`test_duplicate_tensor_id_weight_edges_all_get_scaled`。

**教训**：给一个就地改写的函数加幂等保护时，键的选择本身就是个正确性问题——键太粗
会把"不同的东西"当成"同一个东西"跳过，这种漏改和原本要修的重复改一样是静默的。
