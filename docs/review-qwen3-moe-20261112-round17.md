## 二、修改建议

### 问题1（高）: B 路运行期重复次数仍按形状猜，导致视图/嵌入代价失真
　　**问题说明**：design §十.7 要求「当前 token 的逐元素、归一化、激活、视图类与专家乘加按 `Tq` 计费」；implement §8.3 的 B 路单位契约写明「运行期按 ceil(实际 Tq / tokens) 重复整份 trace」。实际 `genesim/src/vpu/vpu.py:566-572` 的 `_unit_repetitions` 仍用 `_runtime_repetitions`（`:625-629`）除以 trace 的 `tokens`，而 `_runtime_repetitions` 对非 GEMV 算子调用 `_extract_query_count`（`:602-622`），把输入形状除末维以外的所有维相乘当作查询行数。于是 3-D `TRANSPOSE`（输入 `[Tq,32,128]`）被算成 `Tq×32`，头数被当成了 token；rank-1 `GATHER`（输入 `[Tq]`）被算成 1，整个 prefill 的嵌入只按 1 个 token 计。本轮探针 `/tmp/r17-probes/probe_runtime_reps.py` 在 Tq=7 时得到 TRANSPOSE/头优先 SPLIT 重复 224 次、GATHER 1 次、VECTOR_MUL 7 次。4L dynamic 的 `op_1846_TRANSPOSE.pim_trace` 元数据 `tokens=1`、`total_in/out_bytes=8192`（1×32×128×2），但 prefill 的运行时输入是 `[726,32,128]`，重复 23,232 次（decode 每步 32 次），`op_type_metrics` 的 TRANSPOSE 0.1196 s 被整体放大约 32 倍；SPLIT 的 0.1206 s 中头优先的 3-D 分片同构放大（2-D 分片正确，3-D 占主要部分）；GATHER 的 prefill 726 token 只按 1 次计（4.1e-05 s）。4L 总量因此多计约 0.23 s（61.015 s 中约 0.4%），48L 同构路径同样失真；这不是数值错误，而是代价契约与文档不一致。
　　**根本原因**：round16 只把 trace 的 token 数显式写进 `pim.traceTokens`（`pimir_trace._declared_trace_tokens`），没有把「运行期实际 Tq」变成唯一的重复次数来源；`_runtime_repetitions` 仍按形状启发式推断，trace 的 `tokens` 与运行时行数成了两套口径。同一根因影响所有头/批维不在末维的视图算子（TRANSPOSE、头优先 SPLIT、CONCAT/RESHAPE 的 `loop_count`）以及 rank-1 的 GATHER；现有 `test_vector_trace_token_unit_scales_with_the_query_rows` 只用 2-D `VECTOR_MUL`，`test_explicit_trace_tokens_attribute_wins_over_shape_heuristic` 只检查 trace 元数据，不检查 VPU 的重复次数，所以 45/45 全绿没有暴露，属于 round16 问题1「TRANSPOSE 首维启发式误读 token」修复未覆盖的同类路径。
　　**涉及文件**：`genesim/src/vpu/vpu.py:566-572,602-629,456-527`；`genesim/src/scheduler/gene_sim_scheduler.py:282-343`（`_get_operator_with_runtime` 已在运行期拿到 `tq`）；`genesim/tests/sim/test_vpu.py:765-838`、`genesim/tests/sim/test_pimir_trace.py:888-903`；证据 `/tmp/r17-probes/probe_runtime_reps.py`、`/tmp/r16-pipeline/qwen3_moe_tp4_pp2_dynamic_dispatch_20261112-110453-4047537/pim_traces_pimir/op_1846_TRANSPOSE.pim_trace`、同目录 `results_pimir/op_type_metrics.json`。
　　**修改思路**：在 `_get_operator_with_runtime` 把本次请求的 `tq` 写到 runtime op（如 `op.runtime_query_tokens = tq`），`PIMVPU._runtime_repetitions` 直接返回它（GEMV 的 head 组已在 trace 内，重复次数仍是 Tq；旧 128-token trace 由 `_unit_repetitions` 的 ceil 处理），删除 `_extract_query_count` 在重复次数路径上的形状推断；视图/嵌入的 `loop_count` 也按 trace 自身的相/块结构或单位给出，不再用末维猜。补 Tq=7 的 3-D TRANSPOSE、头优先 SPLIT、rank-1 GATHER 与 PAGED_ATTN prefill/decode 用例，断言重复次数=7/实际 Tq 且总字节=7×单位字节；回归 4L dynamic/dense 的 total_time 并回填 §9.2。

### 问题2（中）: 四节点注意力被单位核验误拒
　　**问题说明**：design §十.7 与 GeneSim 的 KV 块计费要求四节点注意力（GEMV_SCORE/SOFTMAX/MASK/GEMV_CONTEXT）按历史 `Tp+Tq` 运行期绑定；compiler 的 `_pimir_unit_shapes`（`genesim_bridge/placement_export.py:338-352`）把 `Tq` 折成 1、把 `Tp+Tq` 折成一块 KV 的占位 128，sidecar 的 `local_*_shapes` 因此是 `[1,128]`。GeneSim 的 `_validate_pimir_unit`（`gene_sim_scheduler.py:745-819`）在运行时拿绑定后的 `op.exec_input_shapes()` 与这份占位逐形状比末维（`_unit_shape_conflict` `:699-715`）；MASK/SOFTMAX 的输出与 GEMV_SCORE 的分数输出末维就是 `Tp+Tq`，prefill 的 726、decode 的 KV 长度（727..794）都不等于 128，于是合法 trace 被拒：本轮探针 `/tmp/r17-probes/probe_unit_mask.py` 对 MASK `[726,726]`（prefill）与 `[1,69]`（任取一个 decode 历史）均报「末维 != 编译单位的 128」。编译器侧 `run_full_pipeline._last_dim_conflict`（`scripts/run_full_pipeline.py:1781-1793`）只比较 int 维，遇到符号 `Tp+Tq` 会跳过；本轮用 `_bpath_unit_problems('probe', MASK 条目, 符号 meta, strict=True)` 复跑返回 `[]`，同一份单位在 trace 验收 ACCEPTED、在 GeneSim REJECTED。当前 Qwen3/llama2 的 fp16 路径走融合 `PAGED_ATTN`，所以 4L 主链没有触发；但 `build_from_hf_config` 的 `fused_attention=False` 分支（bf16、sliding_window、attention_bias）和直接 parser 不带 `--execution_dtype float16` 时会走四节点路径，合法模型会在仿真启动前失败，报错还会指向「本地宽」而误导排查。
　　**根本原因**：B 路编译单位把符号维固化成具体占位（Tq→1、Tp+Tq→128），没有保留「token 维/历史维/特征维」的语义；GeneSim 用绑定后的具体形状做末维比较，编译器用符号形状做比较，两个消费方口径不同。同一根因影响所有末维为历史长度的算子（MASK/SOFTMAX/GEMV_SCORE 的输出、GEMV_CONTEXT 的输入）；现有 `TestPimirUnitContract` 只用 `[Tq,192]` 的 VECTOR_MUL，没有 MASK/SOFTMAX 用例。
　　**涉及文件**：`flagos-pim-compiler/genesim_bridge/placement_export.py:338-352`；`genesim/src/scheduler/gene_sim_scheduler.py:699-715,745-819`；`flagos-pim-compiler/scripts/run_full_pipeline.py:1781-1793,1796-1871`；`genesim/tests/sim/test_compiler_placement.py:3285` 起；证据 `/tmp/r17-probes/probe_unit_mask.py`、`_bpath_unit_problems` 对 MASK 符号 meta 返回 `[]` 的探针。
　　**修改思路**：让 sidecar 的单位形状保留 IR 的符号维（如 `["Tq",192]`、`["Tp+Tq",128]`）并标注维角色，或为 KV 块算子单独记录 `kvBlockTokens` 并声明该维不是本地宽；GeneSim 的 `_validate_pimir_unit` 只比较具体/特征维（复用编译器的 `_last_dim_conflict` 语义），历史维交给 `_block_loop_binding` 的 `loop_unit_tokens`。补 MASK/SOFTMAX/GEMV_SCORE/GEMV_CONTEXT 在 prefill 726 与 decode KV 727..794 的接受用例与错误宽度拒绝用例；4L 主链回归。

### 问题3（中）: B 路单位未进共享严格验证器
　　**问题说明**：design §十.4 要求导出、skip-simulation、仿真前复核、仿真 IR 与 trace 五个编译器入口共用同一判定；implement §8.3 的 B 路单位契约要求严格产物缺 `trace_tokens`/`local_*_shapes` 直接失败。实际 `run_full_pipeline._bpath_unit_problems`（`scripts/run_full_pipeline.py:1796-1871`）只在 `verify_trace_provenance`（调用点 `:1938`）使用，`validate_sidecar_contract`（`:635-657`）→`audit_sidecar_coverage`（`:890`）没有单位完整性检查；`--skip-simulation` 在 `:2208-2217` 调用的正是这份验证器。本轮探针 `/tmp/r17-probes/unit` 把 4L sidecar 的 1606 条 B 路条目的 4818 个单位字段全部删掉后，`verify_sidecar_freshness`/`verify_sim_ir_matches_sidecar` **ACCEPTED**，只有 `verify_trace_provenance` **REJECTED**（2630 条 trace 缺单位）；48L 旧 sidecar 同样 freshness/仿真 IR ACCEPTED、trace REJECTED（31,538 条，K16）。因此 skip-simulation 可以签发一份 GeneSim 严格入口必然拒绝的产物，五个入口的严格性分叉；同一根因在 round08 问题4/round12 问题1 已出现过（`moe_config`/`hw_budget` 逐入口补），属于同一类「新证据只接消费点、不接共享验证器」的复发。
　　**根本原因**：round16 新增的单位证据只接到 trace 入口和 GeneSim，没有接进共享验证器；五个入口的严格性不是由一份 schema 生成，而是由各入口选择调用哪些检查。同样的漏接还会影响未来任何新增的产物证据字段。
　　**涉及文件**：`flagos-pim-compiler/scripts/run_full_pipeline.py:635-657,890,1796-1871,1938,2208-2217`；`tests/test_genesim_simulation.py` 的三入口用例；证据 `/tmp/r17-probes/unit`、`/tmp/round10-fix/genesim-48l` 的 freshness/仿真 IR/trace 输出。
　　**修改思路**：把单位的「完整性 + 形状/token 一致性」抽成共享检查，挂到 `audit_sidecar_coverage` 的严格分支（导出、skip-simulation、freshness、仿真 IR 共用），trace 入口保留 trace-vs-unit 的字节/lineage 检查；严格产物缺任一字段即失败。补三入口的缺失/半缺失/错形反例与 4L 正例，回归 `--skip-simulation`；避免再按入口逐个补检查。

### 问题4（中）: 独立仿真配置指向过期 dense 产物
　　**问题说明**：`genesim/conf/sim_qwen3_moe_pimir.yaml:18` 指向 `models/qwen3_moe_pimir.ir`、`:30` 指向 `models/qwen3_moe_tp4_pp2_placement.json`；当前工作区的这两份文件是 round15 的 `dense_sim` 产物（IR 的 `moe_execution=dense_sim`，1606 条 B 路条目无 `trace_tokens/local_*_shapes`）。本轮按该配置（绝对路径指向共享产物）跑 `./run.sh --config` **exit 1**：「严格模式下，源 IR 的 pimir 覆盖不完整：1094 个 B 路算子缺编译单位」。同时，编译器 `resolve_moe_execution` 的默认是 `dynamic_dispatch`（`runtime/exec_plan_gen.py:30-33`），而这份模板的 IR/sidecar 是 `dense_sim`，独立入口的执行语义与编译器默认不一致；即使补齐单位，也会按 dense 计费。配置注释给出的 sidecar 生成命令 `export_pp_placement.py --measure-kernel-tiles` 不会产出它引用的 `qwen3_moe_pimir.ir`（A2 精化只在主链的 run 目录里做），按注释操作无法恢复该入口。主链 E（`prepare_simulation_config` 改写为本次 run 的 A2 IR + BCD sidecar）本轮 4L 通过，说明问题在模板/共享产物而不在主链。
