## 二、为什么需要它（背景）

GPU 上的 KV cache 隐含三条前提：统一地址空间、显存分配器动态增长、框架托管生命
周期。存算一体架构把三条全打破：每个 DPU 地址空间独立、没有分配器、DPU 之间无
直连。而 KV cache 是推理中**唯一跨解码步存活、只增不减、每步必读**的大块状态，
处理不当整个解码循环就转不动，所以必须自写一套。方案把它拆成四个子问题，本次
实现逐一对应：

| 子问题 | 结论 | 落在哪个函数 |
| --- | --- | --- |
| ① 怎么切 | 按 KV head 切，跟着问题 2 的 k_proj 列切走，本地驻留 | `kv_specs_from_placement` |
| ② 怎么存 | 按 `max_seq` 定长预留，编译期算死每块地址 | `KVRegionSpec` + `build_kv_layout` |
| ③ 怎么用 | 本 DPU 按 tile 分块读 + mask 盖住未填充尾部 | `read_tile` + 两个 mask 函数 |
| ④ 怎么更新 | 按编排器传入的 `valid_len` 追加，本类不自持指针 | `PIMStaticKVCache.update` |

## 四、原理

### 1. 怎么切——KV 跟着注意力头走（硬约束）

注意力每步要读全部历史 token 的 K/V。如果 KV 按序列维切、和头不对齐，每步都得
跨 DPU 收集 KV；DPU 之间无直连，每收一次就是「DPU→主机→DPU」两跳，几百步后
主机带宽爆掉。所以 KV 必须按头切、本地驻留、永不搬：

```
32 个 KV head（Llama-2-7B，8 台 DPU）
┌────────┬────────┬─────┬─────────┐
│ DPU0   │ DPU1   │ ……  │ DPU7    │
│ head 0~3│ head 4~7│    │ head 28~31│
└────────┴────────┴─────┴─────────┘
每台 DPU 同时持有【全部 32 层】中自己那 4 个 head 的 K/V
→ 每步本地追加、本地读，跨 DPU 零搬运
```

这个映射不是拍脑袋重算的，而是直接从问题 2 的产物里推：k_proj 权重按列切
`Shard(0)`，某台 DPU 拿到权重行区间 `[start, end)`，除以 `head_dim` 就是它驻留
的头。切点没对齐头的边界就直接报错——前提被破坏，不允许继续。

### 2. 怎么存——编译期一次算死的定长区

DPU 上没有分配器，KV 区当编译期定长空间一次算死。`build_kv_layout` 把 KV 区切
成一个个 `[max_seq, head_dim]` 的定长小块，按固定顺序排地址：

```
kv_base →┌───────────┬───────────┬───────────┬─────┐
         │(层0,头0,K)│(层0,头0,V)│(层0,头1,K)│ ……  │
         └───────────┴───────────┴───────────┴─────┘
         每块 max_seq×head_dim×每元素字节，块间按 DMA 对齐补填充
```

产出两个数：`kv_off`（每块绝对地址表）和 `kv_allocated_bytes`（**含对齐填充的**
真实占用）。注意 `kv_bytes()` 公式算的只是无填充下界，只供粗估——问题 8 排内存
时必须用前者，否则填充累积会让 KV 实际写入范围侵入激活区。

Llama-2-7B 手推值（8 台 DPU、每台 4 头、32 层、max_seq=256、fp16）：
`2 × 32 × 256 × 4 × 128 × 2 字节 = 16 MiB / 台`（2 = K 和 V 两份），测试逐位核对。

### 3. 整体流程（编译期一次，运行时逐步）

```
编译期（一次决策）：
  HF 模型 → torch.export → 问题1 图拆分 → 问题2 切分传播
                                              │ k_proj 的切分结果
                                              ▼
                              kv_specs_from_placement
                              （每台 DPU 一份 KVRegionSpec）
                                              ▼
                              build_kv_layout（对齐、算地址）
                                       │              │
                                       ▼              ▼（后续接问题8）
                            PIMStaticKVCache 的规格   排进三区蓝图

运行时（每个解码步，由问题 6 编排器驱动）：
  编排器持有 valid_len（唯一位置真值源，本模块不存指针）
        │
        ▼ pos = valid_len
  K/V 投影算出本步 K/V ──► cache.update(layer, pos, …)   写本 DPU 本地
        │
        ▼ read_tile 逐块读 K → 算分数 scores
        ▼ scores + decode_mask → 送回主机做 softmax（第 1 阶段 softmax 在主机）
        ▼ read_tile 逐块读 V → 按权重加权累加 → 注意力输出
        │
        ▼ 编排器 valid_len += 1，进入下一步
```

### 4. 怎么用——分块读 + mask

单头的整块 KV（如 256×128×fp16）远超单 DPU 的 WRAM，必须按 token 分块
（tile）搬进搬出，单块字节数受 `wram_budget_bytes` 校验（真机上这个值由问题 5
的桥按 WRAM 容量定）。预留区里还没填的尾部是脏数据，靠 mask 盖住：解码步分数
是 `[max_seq]` 向量，`decode_mask` 把 `valid_len` 之后的位置置为负无穷，softmax
后权重恒零，不参与计算。mask 只是数据、不改形状，所以不破坏「全程静态」。

### 5. 怎么更新——位置只有一个真值源

旧设计曾有「编排器、cache 内部指针、update 参数」三处位置真值源，不同步就会出
现「mask 按位置 N 生成、KV 却写到 N+1」的静默错误。本实现里 `PIMStaticKVCache`
**没有内部序列指针、没有 advance**：每次写哪一格由调用方（问题 6 的
`DecodeState.valid_len`）显式传入。cache 对象也不持有任何数据——数据在各 DPU
的 MRAM 里，把 cache 对象删掉重建一个，读回的值不变（有测试专门验证这一点）。

## 七、当前局限与不足

- **只支持 fp16 / fp32**（`dtype_bytes` 只认 2 和 4）；bf16、int8 量化 KV 未覆盖。
- **只认 k_proj 列切 `Shard(0)`**：其它切法（如复制、按层切给不同 DPU）直接抛错。
  第 1 阶段所有层的 KV 都在每台 DPU 上，若以后做跨 DPU 的层间流水，规格结构
  需要扩展。
- **定长预留，不回收**：按 `max_seq` 一次占满，短序列也照样占着；没有分页、没有
  动态增长。这是方案的刻意取舍（无分配器），代价是长序列下 KV 区线性膨胀。
- **预填充逐位置追加**：`update` 一次只写一格，预填充要循环 P 次。假后端验证
  够用；真机上写在投影 kernel 内完成，批量追加留待后续。
- **mask 与注意力验证在主机侧用 numpy 拼**：softmax 在主机是方案第 1 阶段的既定
  取舍，但「逐 tile 读」目前是把数据读回主机算的模拟，不等于真机 kernel 内的
  读取路径；等问题 5 的 kernel 到位后这条路径要替换。
- **WRAM 预算只是校验值**：测试里随意给了个够用的数，真实 tile 尺寸依赖问题 5。
- **尚未与问题 8 真实对接**：`kv_base` 目前测试取 0，`kv_allocated_bytes` 的消费
  方（三区规划器）还不存在，接口按方案预留、未实战。
