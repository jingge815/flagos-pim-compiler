# 自动切分策略与流水切分评审记录

日期：2026 年 8 月 30 日

## 一、先说结论

本轮改动已经把“切分策略”接入图编译、通信计划、内存规划、KV 缓存和编排器。当前支持三类策略：

| 名称 | 含义 | 八台 DPU 上的示例 |
| --- | --- | --- |
| 张量并行 | 所有层都使用全部 DPU，每层内部切权重和激活 | `tp8_pp1` |
| 流水并行 | 层按连续区间分段，每段使用一组 DPU，段内不再切分 | `tp1_pp8` |
| 混合切分 | 先按层分段，再在每段内做张量切分 | `tp4_pp2`、`tp2_pp4` |

因此，**流水切分的空间语义已经真正生效**：不同层的权重、激活和 KV 缓存只出现在所属段的 DPU 上，跨段激活会生成通信边，编排器会按依赖把数据送到下一段。

但它还不是性能意义上的完整流水线。当前命令按拓扑顺序提交，彼此无依赖的 DPU 命令仍可并发；但单个请求没有微批次，不能让不同流水段同时处理不同微批次。跨段通信实际使用主机中转的 `all_gather`，没有 `Send/Recv` 原语、段间计算通信重叠，也没有消除流水气泡的调度器。更准确的说法是：**已经实现流水并行的层划分和正确性闭环，尚未实现流水并行的吞吐优化。**

关于 Llama2 7B：测试代码确实对搜索空间中的每一种策略调用完整的“编译、装载权重、预填充、逐步解码”流程，并断言生成令牌序列逐个等于单卡 PyTorch 参考结果。测试还把 KV 区字节与参考缓存进行对拍。用户提供的实测记录显示四种策略均通过；本次审查只重新运行了秒级和小模型测试，没有重复运行约十分钟的七十亿参数测试。

## 二、策略是怎样表示的

策略的唯一数据结构是 `graph/strategy.py` 中的 `ShardStrategy`：

```text
num_dpus = num_stages × tp_width
stage s 的 DPU = dpu_ids[s×tp_width : (s+1)×tp_width]
层 l 所属的 stage = l // (num_layers / num_stages)
```

搜索空间由 `llama_strategies` 枚举 `num_stages` 的二的幂因子，并检查张量切分宽度是否能够整除注意力头数、中间层宽度和词表大小。以 Llama2 7B、八台 DPU、三十二层为例：

| 策略 | 层段 | 每段 DPU 数 | 每台 DPU 的层 | 每层权重切法 |
| --- | ---: | ---: | ---: | --- |
| `tp8_pp1` | 1 | 8 | 32 | 每层八路张量切分 |
| `tp4_pp2` | 2 | 4 | 16 | 每层四路张量切分 |
| `tp2_pp4` | 4 | 2 | 8 | 每层两路张量切分 |
| `tp1_pp8` | 8 | 1 | 4 | 整层放在一台 DPU |

Llama 权重的列切、行切配对没有改变：`q/k/v/gate/up/lm_head` 切输出维，`o/down` 切规约维。改变的是“这份切片属于哪些 DPU”。

## 三、完整数据流

```text
模型 + ShardStrategy + 硬件参数
              │
              ▼
      导出预填充图和解码图
              │
              ▼
       图分区和层号识别
              │  graph/spec_prop.py
              ▼
  按策略给权重和中间张量分配 DPU 子集
              │
              ├── 布局不一致 ──► 生成 redistribute 边
              │                    （跨段通常是主机中转 all_gather）
              ▼
       KV 区和三段内存规划
              │  memory/kv_layout.py、memory/mem_planner.py
              ▼
          生成命令依赖图
              │  runtime/exec_plan_gen.py
              ▼
       Numpy 后端按依赖执行
              │
              ├── DPU 算子：读取本地分片并写回本地 MRAM
              ├── 主机算子：执行归一化、注意力和输出处理
              └── 解码循环：更新 valid_len，采样下一个令牌
```

策略切换没有复制多套编译流水。调用方只需把另一个 `ShardStrategy` 传给 `compile_llama2`，其余步骤从 `PIMTensorSpec.shard_map` 自动得到本地 DPU 集合。

### FlagTree

FlagTree 仓本轮没有修改。图层编译器向算子编译器传递的是每台 DPU 的本地形状、数据类型、硬件参数和任务数，现有算子契约可以接收这些信息，因此策略切换可以复用已有算子编译入口。但这不等于 FlagTree 已经实现策略感知的调优，详见“当前不足”。

## 五、关键新增和修改函数

### 策略层

- `ShardStrategy.dpus_of_stage`：返回某个流水段拥有的物理 DPU。
- `ShardStrategy.stage_of_layer`、`dpus_of_layer`：把层号映射到段和 DPU 子集。
- `ShardStrategy.layers_of_dpu`：供内存和 KV 反查某台 DPU 的层范围。
- `llama_strategy`：构造一个具体策略并检查切分契约。
- `llama_strategies`：按顺序枚举合法策略，不做代价评分。

### 图编译层

- `_layer_of_node`：从 `nn_module_stack` 或权重名解析层号。
- `_dpus_of_node`：决定节点实际参与的 DPU 集合；无法解析层号的尾部节点归最后一段。
- `_weight_spec`：按策略给权重生成列切、行切或复制布局。
- `_diff_edge`：同时比较设备、布局和 DPU 集合；集合不同就不能视为“无需搬运”。
- `propagate_specs`：把上述规则传播到整张图。

### 编译和运行时

- `compile_llama2`：统一编译预填充图和解码图，并串起通信、KV、内存和命令图。
- `write_weight_shards`、`load_weights`：按照每台 DPU 的地址蓝图装载真正的权重分片。
- `kv_specs_from_strategy`：按段生成每台 DPU 的 KV 规格。
- `make_sdpa_handler`：按“层 + 头”定位 KV，写入和读取本地缓存后重算注意力。
- `build_execution_plan`：为每个实际拥有分片的 DPU 生成算子命令，并建立读写依赖。
- `run_decode_loop`：执行一次预填充和多次解码，输出采样得到的令牌列表。

## 六、各模块的实现原理

### 1. 图编译和通信

张量并行时，一个张量的 `shard_map` 覆盖所有 DPU，行为与改动前一致。流水或混合策略时，层内节点的 `shard_map` 只覆盖本 stage 的 DPU。

如果生产者在前一段、消费者在后一段，即使两边都是 `Replicate@dpu`，DPU 集合也不同，`_diff_edge` 会生成重分布边。通信计划随后把边展开成主机收集、合并或规约、再写回目标 DPU 的段列表。这样保证了数据确实跨过段边界；当前没有专门的点对点 `Send/Recv`。

### 2. 算子编译

`runtime/exec_plan_gen.py` 把每个 DPU 算子的本地输入形状写进命令。`runtime/kernels.py` 的算子编译桥会把 `arg_shapes`、数据类型、任务数和硬件参数交给 `opcompiler_bridge`；形状不满足当前内核的二的幂约束时退回 NumPy 内核。

因此“策略切换后算子仍能运行”已经实现为**本地形状随策略改变，并进入算子编译缓存键**。但是“针对每种策略重新搜索最佳 Tile、阵列位置和指令”尚未实现，FlagTree 也没有新增策略字段。

更重要的是，本轮策略测试调用 `register_all(backend)` 的默认路径，没有启用 `use_compiled_linear=True`；四种策略实际运行的是 NumPy 内核。故本轮已经验证“图编译到 NumPy 后端”的策略闭环，**尚未验证每种策略的本地形状都能通过 FlagTree 编译并执行编译产物**。

### 3. 内存管理

每台 DPU 的 MRAM 仍划为权重区、KV 区和激活区：

```text
权重区（两张图共用） → KV 区（按层和头定长分块） → 激活区（预填充/解码复用）
```

规划器只为该 DPU 的 `shard_map` 分配权重和激活，并为通信落地缓冲回填地址。激活区使用生命周期和贪心复用，复用地址会产生等待依赖，避免尚未读完的数据被覆盖。

### 4. KV 缓存

张量并行按头切 KV，流水并行按层切 KV，混合策略两者同时发生。运行时的注意力处理器先筛选拥有当前层的 DPU，再按头读取本地 KV。

需要特别注意：在本轮策略中，单台 DPU 的 KV 总字节数通常不因流水而减少。张量并行减少每台的头数，流水并行减少每台的层数，两者乘积保持不变；改变的是布局和所有权，而不是总量。

### 5. 编排器

命令图包含 DPU 启动、主机算子和重分布命令。每条命令带精确的 MRAM 读写区间和等待列表，执行器按拓扑顺序提交并等待。`DecodeState.valid_len` 是跨预填充和解码步骤的位置唯一来源，保证位置编码、KV 写入位置和注意力掩码一致。

## 七、验证和结果

### 本次重新运行的快速测试

在指定的 PyTorch 环境中运行：

```bash
pytest tests/test_strategy.py -q
pytest tests/test_strategy_sweep.py -q
```

结果：

| 测试 | 结果 |
| --- | --- |
| `tests/test_strategy.py` | 25 通过，0.03 秒 |
| `tests/test_strategy_sweep.py` | 9 通过，约 11.9 秒 |

小模型测试的关键判据包括：

- 每种策略生成的令牌列表等于单卡 PyTorch 的贪心解码结果；
- 跨段边数等于 `num_stages - 1`，张量并行时为零；
- 每台 DPU 的 KV 只包含本段层；
- 被切权重总量不随策略改变，复制权重随段内张量宽度缩小；
- 各 DPU 的权重负载保持平衡。

### 真实 Llama2 7B 测试

`tests/test_strategy_llama2_7b.py` 的代码路径是：

```text
Llama2 7B 权重
  → llama_strategies（tp8_pp1 / tp4_pp2 / tp2_pp4 / tp1_pp8）
  → compile_llama2
  → load_weights
  → NumpyBackend
  → run_decode_loop
  → 生成令牌列表
```

该文件把 `DECODE_STEPS` 固定为 8、`eos_id=-1`，因此每种策略会生成 8 个令牌；断言 `generated == ref_tokens`，不是只检查“能得到 logits”。此外还抽查第 0、15、31 层的 K/V 字节，并检查内存规划和层归属。

用户提供的实测记录为：四种策略的令牌和 KV 对拍 8 个用例通过，内存判据 4 个用例通过；全量测试 268 个用例通过。上述长测结果来自用户已经完成的运行，本次没有重复执行。

## 八、当前不足和风险

1. **流水线还没有重叠调度。** 现在是单请求、按拓扑顺序提交；独立 DPU 命令可以并发，但没有微批次、双缓冲、跨段重叠、气泡消除或吞吐指标。
2. **跨段通信不是专用流水通信。** 当前通过主机中转的 `all_gather` 完成，未实现硬件直连的 `Send/Recv`、带宽分配和通信计算重叠。
3. **搜索空间较窄。** 只枚举 `num_stages` 的二的幂因子，层必须均匀分段；没有非均匀层边界、任意切分粒度或代价模型。
4. **算子编译器没有策略级调优。** FlagTree 没有本轮改动；非二的幂的中间层宽度和词表宽度仍会退回 NumPy 内核，Tile 和阵列映射也没有依据策略自动搜索。
5. **分组查询注意力尚未覆盖。** KV 布局已经保存“一个 KV 头服务哪些查询头”的映射，但当前注意力处理器按查询头号直接索引 KV 头。Llama2 7B 的查询头数与 KV 头数同为 32，不会触发问题；换成分组查询注意力模型会越界或得到错误的头映射，必须先补实现和测试。
6. **尚未实现数据并行和序列并行。** 当前覆盖的是张量、流水以及二者混合，不应把 `ShardStrategy` 解读为通用并行策略。
7. **七十亿参数验证范围仍有限。** 测试使用固定令牌提示词和贪心解码；KV 只抽查首、中、末三层；验证后端是 Numpy 伪后端，不等同于 GeneSim 成本结果或真实硬件执行。四策略测试也没有启用 FlagTree 编译内核。
8. **层号识别依赖 Llama 导出结构。** `_layer_of_node` 依赖 `nn_module_stack` 格式或 `layers.<编号>` 权重命名，换模型结构需要新增适配和测试。
9. **物理 DPU 编号的端到端约束不一致。** 策略层允许任意非负且不重复的 `dpu_ids`，但当前命令图和 Numpy 后端要求编号落在 `0..num_dpus-1`。默认连续编号的 Llama2 7B 路径不受影响；若要支持真实硬件的不连续编号，需要增加逻辑编号到物理编号的映射。
10. **KV 并不会因为流水自动节省单台容量。** 只能改变层和头的归属；若目标是降低峰值 KV 容量，需要分页、换入换出或序列级策略。

## 九、建议的后续工作

建议按以下顺序推进：

```text
先保持当前正确性闭环
        ↓
为预填充引入微批次和双缓冲
        ↓
把跨段 all_gather 替换为可重叠的 Send/Recv 调度
        ↓
加入非均匀层边界和通信/内存代价估计
        ↓
让 FlagTree 根据本地形状和硬件预算搜索 Tile 与阵列映射
        ↓
再扩展数据并行、序列并行和真实硬件验证
```

在这些功能完成前，推荐对外把当前能力描述为“支持多策略的静态图切分和正确性验证”，不要描述为“已经实现高吞吐流水线自动调优”。
