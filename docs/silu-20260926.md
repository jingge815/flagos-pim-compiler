# SiLU 求值改回闭式（2026-09-26）

## 改了什么

整网对拍 `tests/test_executor_llama2_7b.py` 与
`tests/test_strategy_llama2_7b.py` 在 `c4e947a` 之后失败。那次提交把
`graph/partition.py` 从白名单改成黑名单，SiLU 从主机上的 torch 闭式挪到了
设备上的 31 段弦线查表。

查表与闭式在单点上差得很小，但 Llama-2-7B 有 32 层，残差逐层累积后 logits
的最大差到 1.8，均值 0.16，超过测试的 0.2 / 0.02。贪心解码因此在一个位置
选错 token，KV 区也随之对不上。

把设备求值改回闭式 `x/(1+exp(-x))` 后，logits 最大差降到 0.05 以内，三个
失败的测试全部通过。

## 为什么不修表

31 段是硬件格式的上限（Ceva-NeuPro-M 规范 4.3.3）。实测过几种修法，都不够：

| 求值方式 | logits 最大差 | 均值 | 贪心错位数 |
| --- | --- | --- | --- |
| 31 段弦线，定域 [-4, 4) | 1.86 | 0.157 | 1 |
| 域外改饱和（正侧返回 x，负侧返回 0） | 0.89 | 0.043 | 0 |
| 参考产物的真实表，按最优段取值 | 1.07 | 0.182 | 1 |
| 闭式 | 0.043 | 0.006 | 0 |

域外饱和过不了 0.2，加宽或收窄定域更差：99.7% 的门控值落在 [-2, 2]，
那里的弦线变粗比域外的误差更伤。要压到 0.2 以下需要约 480 段，硬件格式
装不下。

参考产物那张表的分段规则没能反推出来（`docs/prepare_out-域确认表-20260918.md`
的 Q14、Q22 仍是开放问题），而且即便按最优段取值也到不了 0.2。

## 改动的文件

| 文件 | 改动 |
| --- | --- |
| FlagTree `LowerPIMToEmitC.cpp` 的 `pim_lut_silu` | 查表换成闭式，`|x|` 超过 80 先夹住再算，避免 `expf` 溢出 |
| `runtime/kernels_pim.py` 的 `_apply_activation` | numpy 镜像改成同一条闭式，同样先夹住 |
| `runtime/kernels.py` | 删掉没人调用的 `_compiled_dynamic_quant`；`aten.alias` 的内核改回恒等传递；gather 的索引宽度按图上的 dtype 取 |
| `tests/test_opcompiler_ops.py`、`tests/test_quant_activations.py`、`tests/test_kernels.py`、`tests/test_runtime_compiled_coverage.py` | 断言从「必须读表」改成「必须等于闭式」 |

`contracts/gml_lut.py` 的 `synth_silu` 没动。288 B 的表仍按原样合成，并写进
GML 产物。变的只是设备求值不再读它。

## 顺便修的两个 bug

都是 `c4e947a` 带进来的，整网对拍时一起暴露：

1. `aten.alias` 被接上了 `pim.dynamic_quant`。量化把 fp16 写成 int8，再按
   fp16 的长度读回，读出来是 fp16 最大值。`alias` 在图上是视图，导出的
   Llama 图里它只出现在因果掩码和一次 `mul` 别名上，输出都是 fp16。
   改回恒等传递后，logits 最大差从 396 降到 1.8，剩下的才是 SiLU 的账。
2. gather 的索引被强制读成 int32。token id 在设备上是 int64，一个索引吃进
   相邻索引的字节，嵌入查到的全是错行。现在按图上的 dtype 取宽度。

## 还没做的

- GML 产物里的 SiLU 表与设备实际执行的公式不一致。表仍是 31 段弦线，
  设备跑的是闭式。要两者合一，得先反推出参考产物的分段规则。
- 闭式在 `|x|` 超过 80 时被夹住。SiLU 在这个范围早已饱和，夹住不改变结果，
  但与 torch 的实现路径不完全相同。
