# GeneSim 支持真正的多设备张量并行仿真

## 一、这次要解决什么问题

### 1.1 问题现象

大模型的权重太大，一台存算一体设备放不下，需要切开分给多台设备。切法有两种：

- **流水并行**：按模型层数切。比如 32 层分给 8 台设备，每台管 4 层，数据像流水线一样
  逐台往后传。
- **张量并行**：把**同一个**矩阵乘法切开。比如一个 4096×4096 的矩阵乘，切成两半，
  两台设备各算一半，同时开工，算完再把结果合起来。

本仓库用 `tp2_pp4` 这样的名字表示混合切法：`tp2` 是张量并行宽度 2（每个矩阵乘切成
两份），`pp4` 是流水段数 4，一共用 2×4 = 8 台设备。

改动之前，把切分结果交给 GeneSim（性能仿真器）去估算耗时，得到的数字是不可信的。
实测 `tp2_pp4` 的结果：

```
224 个矩阵乘的设备归属统计
  设备 0：56 个        设备 1：0 个   ← 空的
  设备 2：56 个        设备 3：0 个   ← 空的
  设备 4：56 个        设备 5：0 个   ← 空的
  设备 6：56 个        设备 7：0 个   ← 空的
```

8 台设备里有 4 台完全没有任务。但真实硬件上这 4 台明明在忙——张量并行的定义就是
它们各算一半。

### 1.2 三层根本原因

```
第一层：导出环节丢数据
  ┌──────────────────────────────────────────────────────────┐
  │ 图编译器算出的切分结果（正确的）                          │
  │   这个矩阵乘 → 设备 0 算左半边，设备 1 算右半边            │
  └───────────────────────┬──────────────────────────────────┘
                          │  导出给 GeneSim 时
                          │  只取编号最小的那一台
                          ↓
  ┌──────────────────────────────────────────────────────────┐
  │ 交给 GeneSim 的文件（残缺的）                             │
  │   这个矩阵乘 → 设备 0                                     │
  │   （设备 1 那半边的信息被丢掉了，连痕迹都没留）            │
  └──────────────────────────────────────────────────────────┘

第二层：仿真器按"一个算子只能在一台设备上"处理
  拿到残缺文件后，GeneSim 把每个矩阵乘当成不可再分的整体，
  钉死在那一台设备上，按那半边的规模算耗时。

第三层：完全没有合并结果的通信开销
  张量并行算完必须把两半结果合起来（这一步要花时间、占带宽），
  仿真器里压根没有这个环节。
```

用搬箱子打比方：两个人各搬一半，同时进行，搬完还要花时间核对清单对齐。
改动前的仿真等于说"只有一个人在搬，而且搬完不用核对"，报出来的时间自然偏低且不完整。

### 1.3 为什么纯流水并行不受影响

纯流水（`tp1_pp8`）时张量并行宽度是 1，每个矩阵乘完整放在**一台**设备上，
切分记录本来只有一条。"只取编号最小的那一台"从一条里选一条，什么也没丢。

所以这个缺陷只影响张量并行宽度大于 1 的场景，纯流水的结论不受影响。这也解释了
为什么它长期没被发现——纯流水场景一直是对的。

### 1.4 这个缺陷不影响真实执行的正确性

需要明确区分两条路径：

| 路径 | 用途 | 是否受影响 |
| --- | --- | --- |
| 真实执行路径 | 实际算出推理结果，与单卡 PyTorch 逐元素对齐 | **不受影响** |
| 仿真评估路径 | 估算"这样切分要跑多久" | 受影响，本次修复对象 |

真实执行路径（`runtime/exec_plan_gen.py`、`comm/plan.py`）本来就遍历切分记录的
**每一条**，为每台设备生成正确的执行指令，也正确生成了合并结果的通信步骤，并且
这条路径的结果一直在跟单卡 PyTorch 做逐元素比对。

丢数据只发生在"导出给仿真器"这个旁支。所以这是一个**评估结论不可信**的问题，
不是**算错结果**的问题。

### 1.5 算子编译器不需要改动

算子编译器（FlagTree 仓库）负责把单个算子编译成设备上可执行的指令。它接收的输入是
**切分之后一台设备实际要算多大的矩阵乘**，编译缓存的索引键只包含算子类型、
形状、数据类型、硬件配置：

```python
# opcompiler_bridge/driver.py 的 _cache_key
f"{request.op}:{request.arg_shapes}:{request.dtype}:"
f"{request.num_tasklets}:{request.hardware.to_payload()}"
```

里面没有"设备编号"，也没有"放置"相关的任何字段。跨设备怎么切分是图编译器的职责，
算子编译器从设计上就不关心。同一个切分组里各台设备算的规模相同，所以它们共用同一份
编译产物是正确的。

**结论：本次改动涉及两个仓库（图编译器、仿真器），算子编译器零改动。**

## 二、修改原理

### 2.1 总体思路

不去发明新的通信模型，而是把已有的信息完整传递下去，让仿真器已有的机制自然算出结果：

```
第一步：导出环节不再丢数据
  把每台参与设备都如实列出来，并标注切分方向

第二步：仿真器把一个算子在图上真正拆成多个算子
  拆完之后每台设备都有自己的算子，各自占用资源，
  仿真器原有的"一个算子钉一台设备"逻辑不用改就能正确工作

第三步：合并结果作为图上真实存在的节点
  它的入边字节数就是实际通信量，
  耗时交给仿真器已有的"按数据量和链路算传输时间"机制去算
```

### 2.2 两种切分方向的区别

矩阵乘 `输出 = 输入 × 权重`，切权重有两种方向，后续处理完全不同：

```
按输出维度切（列切）：q/k/v 投影、gate/up 投影
┌─────────────────────────────────────────────────────────┐
│  输入（每台设备都要完整读一遍）                          │
│         ↓                    ↓                          │
│  ┌───────────┐        ┌───────────┐                     │
│  │ 设备 0    │        │ 设备 1    │                     │
│  │ 权重左半  │        │ 权重右半  │                     │
│  └─────┬─────┘        └─────┬─────┘                     │
│        ↓                    ↓                           │
│   输出左半               输出右半                        │
│                                                          │
│  两半拼起来就是完整输出，不需要求和                      │
└─────────────────────────────────────────────────────────┘

按输入维度切（行切）：o 投影、down 投影
┌─────────────────────────────────────────────────────────┐
│  输入左半              输入右半                          │
│        ↓                    ↓                            │
│  ┌───────────┐        ┌───────────┐                      │
│  │ 设备 0    │        │ 设备 1    │                      │
│  │ 权重上半  │        │ 权重下半  │                      │
│  └─────┬─────┘        └─────┬─────┘                      │
│        ↓                    ↓                            │
│   部分和（全宽）        部分和（全宽）                    │
│        └────────┬───────────┘                            │
│                 ↓                                        │
│          必须逐元素相加 ← 这一步是跨设备通信              │
│                 ↓                                        │
│            完整输出                                      │
└─────────────────────────────────────────────────────────┘
```

关键差别：行切时每台设备算出的都是**覆盖完整输出宽度的部分和**，必须相加才对。
这个相加就是跨设备通信的来源。

### 2.3 真实模型的结构比预想复杂

原本设想每个矩阵乘是孤立的，拆开就行。实际读了仿真器的模型结构后发现不是——
矩阵乘之间夹着别的算子，且切分边界不对齐。这两处如果处理不当，会引入真实硬件上
不存在的通信。

#### 情况一：前馈网络块中间夹着逐元素算子

```
真实结构（一层的前馈网络部分）：

  归一化 ──→ gate 投影（列切）──→ 激活函数 ──┐
        └──→ up 投影（列切）──────────────┴──→ 逐元素相乘 ──→ down 投影（行切）──→ 残差相加
```

激活函数和逐元素相乘**必须跟着一起切**。如果只拆三个矩阵乘、把这两个留作单个节点：

```
错误做法的后果：

  设备 0 的 gate 投影 ──┐
                        ├──→ 单个激活函数节点  ← 两台设备的结果都汇聚到这里
  设备 1 的 gate 投影 ──┘        ↓                 等于插入了一次全量汇总
                              下游又要重新散开     ← 又一次全量分发

  凭空多出两趟真实硬件上不存在的搬运，
  仿真结果的通信开销反而偏高，方向也错了。
```

正确做法是让它们跟着切分同步展开，每台设备只处理自己那一段，全程不通信：

```
  设备 0：gate 左半 → 激活左半 → 相乘左半 → down 部分和 ──┐
  设备 1：gate 右半 → 激活右半 → 相乘右半 → down 部分和 ──┴→ 求和合并

  逐元素运算按同一维度切开再各自计算，
  结果与"先算完整再切"完全等价（数学性质），所以不需要通信。
```

#### 情况二：注意力块已经存在按注意力头的并行

仿真器的模型结构里，注意力部分**已经**是每个注意力头一条独立链路，而且
q/k/v 投影到每个头的连线上，数据量本来就是按单个头的宽度算的。

```
改动前的结构：

  q 投影（单个节点）──┬──→ 头 0 的注意力链路
                      ├──→ 头 1 的注意力链路
                      ├──→ 头 2 的注意力链路
                      └──→ 头 3 的注意力链路
```

所以张量并行要做的**不是**再切一遍，而是把"每条连线从哪个分片取数"改对：

```
改动后（张量并行宽度 2，4 个头分成两组）：

  q 投影分片 0（设备 0）──┬──→ 头 0    ← 头 0、1 归设备 0
                          └──→ 头 1
  q 投影分片 1（设备 1）──┬──→ 头 2    ← 头 2、3 归设备 1
                          └──→ 头 3

  每条连线的数据量一个字节都不用改（本来就是单个头的宽度），
  只是上游换成了持有这个头的那个分片。
```

如果直接套用"每个分片都连到所有下游"的通用做法，会变成每个头都要从所有分片收数据，
等价于错误地建模成"算任何一个头都要先跨设备全量同步"。

**边界对齐是有保证的**：图编译器侧已经强制张量并行宽度必须整除注意力头数，
且分组是按连续区间划分的，所以每个分片覆盖的头区间必然对应一段连续、不重叠的
键值头区间，不会出现一个键值头被劈进两个分片。

## 三、改动的文件与函数

### 3.1 图编译器仓库

| 文件 | 改动 |
| --- | --- |
| `genesim_bridge/placement_export.py` | 核心修改：不再丢弃分片信息 |
| `genesim_bridge/cost_extractor.py` | 适配新的文件格式 |
| `scripts/export_pp_placement.py` | 统计口径按分片计数 |
| `scripts/run_full_pipeline.py` | 校验项适配新格式 |
| `tests/test_placement_export.py` | 新增张量并行覆盖性测试 |

#### `placement_export.py`：交接文件的格式变更

原来每个矩阵乘只写一台设备：

```python
dpu_id = min(spec.shard_map)          # 只取编号最小的
local_out, local_in = spec.shard_map[dpu_id].local_shape
entry = {"dpu_id": dpu_id, "local_in_features": ..., "local_out_features": ...}
```

改成列出全部参与设备，并标注切分方向：

```python
dpu_ids = sorted(spec.shard_map)      # 全部设备
shards = [
    {
        "dpu_id": dpu_id,
        "local_in_features": ...,     # 这台设备实际算的输入宽度
        "local_out_features": ...,    # 这台设备实际算的输出宽度
    }
    for dpu_id in dpu_ids
]
entry = {"shards": shards, ...}
if len(shards) > 1:
    # 切分方向决定后续要不要求和合并
    entry["shard_axis"] = (
        "output_channel" if spec.placement.dim == 0 else "input_channel"
    )
```

格式版本号从 2 提到 3。`shards` 长度为 1 就是纯流水场景，行为与改动前完全等价。

切分方向不是新判断出来的，而是直接来自图编译器已有的切分记录字段，没有引入新的推断
逻辑。

### 3.2 仿真器仓库

| 文件 | 改动 |
| --- | --- |
| `src/ir/model_ir.py` | 新增切分/合并模式，新增三个图编辑操作 |
| `src/scheduler/gene_sim_scheduler.py` | 新增张量并行展开逻辑，接入放置流程 |
| `tests/sim/test_model_ir.py` | 新增 14 项测试 |
| `tests/sim/test_compiler_placement.py` | 新增 15 项测试 |

#### `model_ir.py` 新增的算子切分模式

| 模式 | 用途 | 输入宽度 | 输出宽度 | 后续是否需要合并 |
| --- | --- | --- | --- | --- |
| `output_channel`（原有） | 列切矩阵乘 | 不变 | 缩小 N 倍 | 拼接即可 |
| `input_channel`（**新增**） | 行切矩阵乘 | 缩小 N 倍 | 不变（部分和） | **必须求和** |
| `elementwise`（**新增**） | 逐元素算子跟随切分 | 缩小 N 倍 | 缩小 N 倍 | 不需要 |

#### `model_ir.py` 新增的结果合并模式

| 模式 | 产出算子类型 | 语义 |
| --- | --- | --- |
| `output_channel`（原有） | `CONCAT` | 纯数据搬运，无计算 |
| `reduce_sum`（**新增**） | `ALL_REDUCE` | 逐元素求和，有真实计算开销 |

#### `model_ir.py` 新增的三个图编辑操作

| 函数 | 作用 |
| --- | --- |
| `allocate_op_ids(count)` | 申请若干个未被占用的算子编号 |
| `add_operators(ops, before_op_id)` | 插入算子。**插入位置很重要**，见第五节 |
| `remove_operators(op_ids)` | 删除算子及其相关连线 |

#### `gene_sim_scheduler.py` 新增的展开逻辑

```
                 _expand_multi_shard_operators
                （总入口：按层扫描，按算子身份分派）
                              │
              ┌───────────────┴───────────────┐
              ↓                               ↓
  _expand_attention_             _expand_mlp_
  tensor_parallel_group          tensor_parallel_group
  （注意力块：q/k/v/o 投影）      （前馈块：gate/up/down 投影
                                   + 激活函数 + 逐元素相乘）
              │                               │
              └───────────────┬───────────────┘
                              ↓
                    _attach_reduce_node
                （行切之后插入求和合并节点）

  辅助函数：
    _rewired_dependency    复制一条连线、换端点、按比例缩放数据量
    _shard_tensor_id       给分片权重一个独立身份（见第五节说明）
```

| 函数 | 职责 |
| --- | --- |
| `_expand_multi_shard_operators` | 读交接文件，找出张量并行宽度大于 1 的算子，按层分组后分派；汇总"分片算子 → 设备编号"的对应关系 |
| `_expand_mlp_tensor_parallel_group` | 展开前馈网络块：五个算子各拆 N 份，按份串成 N 条独立链路，行切结果接求和节点。中间算子靠连线查找，不依赖算子编号的固定偏移 |
| `_expand_attention_tensor_parallel_group` | 展开注意力块：四个投影各拆 N 份；不拆注意力头链路，只把每条按头的连线改指向持有该头的分片 |
| `_attach_reduce_node` | 为行切的 N 份部分和插入求和节点，接上原下游 |

#### 接入放置流程的位置

```
run() 主流程：

  1. 标注本地分片形状
        ↓
  2. _build_adaptive_initial_placement
       ├─ 复制一份模型结构
       ├─ ★ _expand_multi_shard_operators  ← 新增，必须在这个位置
       │     （在构造"放置单元"之前展开）
       ├─ 构造放置单元
       └─ 按单元分配设备资源
        ↓
  3. 用展开后的结构构造流水段视图  ← 注意这里，见第五节
        ↓
  4. 编译各算子的执行轨迹
        ↓
  5. 跑仿真
```

展开必须早于"构造放置单元"：那套逻辑认的是"当前结构里有多少个独立算子"，
展开完成后它不需要任何改动就能把每个分片钉到各自的设备上。

求和合并节点**不**钉设备——它没有张量并行的归属性，走原有的资源分配逻辑，
落到通用计算单元上（对应"经主机归约"的物理实现）。

## 四、结果

### 4.1 设备负载分布

真实 Llama2-7B 模型，`tp2_pp4` 配置（张量并行宽度 2、流水段 4、共 8 台设备）：

| 设备编号 | 改动前 | 改动后 |
| ---: | ---: | ---: |
| 0 | 56 | 56 |
| 1 | **0** | **56** |
| 2 | 56 | 56 |
| 3 | **0** | **56** |
| 4 | 56 | 56 |
| 5 | **0** | **56** |
| 6 | 56 | 56 |
| 7 | **0** | **56** |
| 空闲设备 | **4 台** | **无** |

### 4.2 交接文件内容

```
格式版本 = 3          矩阵乘数量 = 224
切分方向标注：列切 160 个，行切 64 个
```

行切的 64 个正好是 o 投影和 down 投影（32 层 × 2 个），与预期一致。

### 4.3 仿真器实际展开结果

```
Expanded 288 tensor-parallel operators into 640 shard operators
（288 个算子展开成 640 个分片算子）
```

288 = 32 层 × 9 个算子（7 个投影 + 激活函数 + 逐元素相乘）。
640 = 288 × 2 + 64，其中 64 是求和合并节点（32 层 × 2 个行切投影）。

### 4.4 端到端流程验证

```
[A] 模型配置 → 仿真器图骨架        算子 3491 个，矩阵乘 224 个
[0] 仿真器给定切分方案             4 个流水段，每段 2 台设备
[B+C+D] 图编译 → 算子编译 → 交接文件
        放置 224 个矩阵乘，4 种本地形状
        算子编译器选出的分块：128 / 512（仿真器默认常量是 32）
[E] 仿真
        total_time_s = 1418.109
        tokens/s     = 5.701
        矩阵乘执行轨迹来源：{'pimir': 448}     ← 全部走真实算子编译产物
        分块分布：{(512,128):192, (512,64):64, (128,128):128, (512,172):64}

全流程验证通过：模型加载 → 图编译切分 → 算子编译 → 仿真代价
```

最后一行的 `{'pimir': 448}` 很关键：448 个分片全部使用算子编译器产出的真实指令序列，
退回手写模板的数量为 0。分块用的是实测的 128/512，不是配置文件里写死的 32。

### 4.5 纯流水场景回归验证

纯流水（`tp1_pp8`）是改动前唯一可信的场景，必须确认它的行为没有被这次改动影响：

```
[E] 仿真
        total_time_s = 2625.215
        tokens/s     = 3.079
        矩阵乘执行轨迹来源：{'pimir': 224}
        分块分布：{(512,128):128, (256,128):64, (512,344):32}

全流程验证通过
```

交接文件内容核对：

| 核对项 | 实测结果 | 预期 |
| --- | --- | --- |
| 每台设备分片数 | 8 台各 28 个 | 224 ÷ 8 = 28，均分 |
| `shards` 长度分布 | 全部为 1 | 纯流水没有张量并行切分 |
| 切分方向标注 | 全部为空 | 长度为 1 时不写这个字段 |
| 展开触发次数 | 0 次 | 不该走展开逻辑 |

`shards` 长度恒为 1，意味着"只取编号最小的那一台"从一条记录里选一条，什么也没丢——
这正是纯流水场景在改动前就可信的原因。展开逻辑一次都没触发，所以这条路径与改动前
完全等价。

### 4.6 纯张量并行场景验证

纯张量并行（`tp8_pp1`）是本次改动最激进的场景：不分流水段，**每个**矩阵乘都切成
8 份，展开规模是混合场景的近四倍。

```
[E] 仿真
        Expanded 288 tensor-parallel operators into 2368 shard operators
        total_time_s = 378.483
        tokens/s     = 21.359
        矩阵乘执行轨迹来源：{'pimir': 1792}
        分块分布：{(512,128):768, (512,16):256, (32,128):512, (512,43):256}

全流程验证通过
```

| 核对项 | 实测结果 |
| --- | --- |
| 每台设备分片数 | 8 台各 224 个（每台都持有全部 224 个矩阵乘的一份） |
| 空闲设备 | 无 |
| 展开规模 | 288 个算子 → 2368 个分片算子 |
| 执行轨迹来源 | 1792 个全部为真实算子编译产物（224 × 8） |

这一轮首次触发了"输出宽度恰好等于分块"的边界情况（见第五节缺陷五之二），
修好之后通过。

### 4.7 三种配置对比

| 配置 | 切法 | 总耗时 | 吞吐 | 展开后分片算子 |
| --- | --- | ---: | ---: | ---: |
| `tp1_pp8` | 纯流水 | 2625.215 秒 | 3.079 | 0（不展开） |
| `tp2_pp4` | 混合 | 1418.109 秒 | 5.701 | 640 |
| `tp8_pp1` | 纯张量并行 | 378.483 秒 | 21.359 | 2368 |

趋势符合物理直觉：张量并行宽度越大，单台设备承担的矩阵乘越窄，算得越快。
纯张量并行最快，因为 8 台设备同时算同一个矩阵乘的八分之一，没有流水线的串行深度。

需要强调两点：

1. **改动前这几个数字是不可比的**。那时张量并行场景只算了一台设备的成本、
   且完全没有通信开销，`tp8_pp1` 更是压根跑不起来。
2. **这个趋势不代表纯张量并行在真实硬件上一定最优**。当前的通信建模偏保守
   （见 8.1），而张量并行宽度越大通信占比越高，所以宽度大的配置受建模偏差的影响
   也越大。这几个数字适合看趋势，不适合当绝对预测。

## 五、修复过程中发现并解决的五个隐蔽缺陷

这些都不在最初的设计里，是实施和实测过程中暴露出来的。记录下来是因为它们都属于
"不报错、但结果静默偏掉"的类型。

### 缺陷一：符号形式的成本会被静默归零

仿真器有两套成本表示：具体数值字段，和**符号系数字典**（按请求长度动态求值）。
真实模型用的是后者，具体数值字段保持默认的 0。

最初的切分实现只缩放具体数值字段。对真实模型的后果是：每个分片的系数字典是空的、
数值字段也是 0，**整组算子的成本静默变成 0**。

修法：系数字典也一并缩放/求和。

### 缺陷二：矩阵乘的数据量系数不能简单按份数缩放

矩阵乘的数据量系数把**输入数据量和输出数据量加在同一个数里**：

```
系数 = (输入宽度 + 输出宽度) × 单元素字节数
```

列切只缩小输出宽度、行切只缩小输入宽度，都是**非对称**的。统一除以份数会算错：

| 切分方向 | 正确结果 | 简单除以 N 的错误结果 |
| --- | --- | --- |
| 列切 | `(输入 + 输出/N) × 字节数` | `(输入 + 输出) × 字节数 / N` |
| 行切 | `(输入/N + 输出) × 字节数` | 同上，同样偏小 |

修法：新增 `gemm_asymmetric_tq_bytes`，从原系数反解出单元素字节数，
再按切分后的非对称形状精确重算。

计算量系数和权重数据量系数不受影响——它们是纯乘积项，切哪一维都是精确的按份数缩放。

### 缺陷三：算子插入位置影响执行顺序判定

仿真器判断每层算子的先后顺序，靠的是算子在列表里的**下标**，不是依赖关系。
把分片算子追加到列表末尾，会让它们排到消费它们的下游之后，触发顺序检查失败：

```
Initial placement units are not in topological order: operator 28->5
```

修法：`add_operators` 增加插入位置参数，按被替换算子的原位置就地插入。

### 缺陷四：流水段视图与展开后的结构不一致

**这一个是单元测试全部通过、实跑才暴露的。**

```
Stage graph must cover the placed ModelIR exactly: missing=[3491, 3492, ...]
```

原因：构造流水段视图的函数读的是**未展开**的原始结构（3491 个算子），
而仿真执行时校验的是**已展开**的结构（多出全部分片算子和合并节点），两边算子集合
不一致。展开只作用于放置流程复制的那一份，流水段视图是另一条独立路径。

修法：构造流水段视图的函数增加可选参数，主流程传入展开后的结构。

自动搜索放置方案的路径不受影响——它只置换算子的设备归属，不增删算子。

### 缺陷五之二：输出宽度恰好等于分块时，循环层数变化

**这一个不是本次改动引入的，是算子编译器与仿真器之间接口的既有边界情况，被纯张量
并行场景第一次触发。**

跑纯张量并行（`tp8_pp1`）时报错：

```
PimirTraceError: 只支持两层 scf.for 的线性算子（外层 N、内层 K），实际有 1 层
```

原因：切成 8 份后出现了新的本地形状 `4096 × 512`，输出宽度 512 **恰好等于分块大小
tile-n=512**。此时外层遍历输出宽度的循环只需迭代一次，算子编译器把它整个优化掉了，
只留下内层的归约循环：

```
输出宽度 4096、分块 512  →  外层跑 8 次，两层循环都在
    scf.for %arg3 = 0 to 4096 step 512     ← 外层：输出宽度
    scf.for %arg4 = 0 to  512 step  32     ← 内层：归约维

输出宽度  512、分块 512  →  外层只跑 1 次，被消掉
    scf.for %arg3 = 0 to 4096 step  32     ← 只剩归约维
```

而仿真器解析这份中间表示的代码写死了"必须两层"（`src/pim/pimir_trace.py`）。

**为什么之前没触发**：本地输出宽度取决于切分宽度。`tp1_pp8` 的本地宽度是 4096/11008，
`tp2_pp4` 是 2048/5504，都远大于分块 512；只有切到 8 份时 `4096 ÷ 8 = 512` 才正好
撞上。缓存里另有一份分块 64、输出宽度 64 的算子也是一层循环，说明这个模式早就存在，
只是此前的配置从未产生这种形状。

修法：解析器接受一层循环的情形。判定不靠层数猜，而是看这层循环的**步长**——等于
分块 tile-k 就是归约维循环，此时输出宽度只有一个分块，迭代次数为 1；步长是别的值
则仍然报错，不做静默兜底。

补了三条测试：接受折叠形式并核对各项计数、折叠形式的总计算量与等价稠密矩阵乘一致
（防止把归约循环误当成输出宽度循环，那会让代价差出一个分块的倍数）、以及"单层但步长
不是分块"必须仍然报错。同时把原有那条断言"单层必须拒绝"的测试改成了断言新行为。

### 缺陷五：分片丢失算子编译产物

**这一个最隐蔽：仿真照常跑完、给出看起来合理的数字，只有专门的校验才能发现。**

```
矩阵乘执行轨迹来源：{'template': 448}
失败：448 个矩阵乘退回了手写模板；算子编译器的分块没有进入代价链。
```

448 = 224 × 2，正好是每一个展开出来的分片。两层原因：

1. 算子编译产物（指令序列文件路径、实测分块）是按交接文件里的**原算子编号**登记的，
   分片拿到的是新分配的编号，自然查不到。
2. 更根本的是，最初为"多分片条目交给展开逻辑处理"写的跳过分支，把这类条目
   **整个跳过**了，连编译产物都没登记，压根没有东西可继承。

后果是分块用配置文件里写死的 32 而不是实测的 128/512，代价链静默偏掉一个倍数。

修法两处：登记环节对多分片条目"不写形状、但照常登记编译产物"；
展开环节把原算子的编译产物继承给每个分片（同组各设备算的规模相同，共用一份是正确的），
求和合并节点不继承——它不是矩阵乘。

本仓库已有的 `verify_trace_provenance` 校验正是为防这一类"跑通了但其实走的是
手写模板"而设的，这次它起了作用。

## 八、不足与遗留问题

### 8.1 通信耗时用的是点对点传输模型，不是集合通信模型

求和合并节点的入边数据量是准确的（每台设备的部分和都是完整输出宽度），
耗时由仿真器已有的"按数据量和链路算传输时间"机制计算。但这本质上是把一次
集合通信当成 N 条独立的点对点传输来算。

真实的集合通信实现（例如环形归约、树形归约）有更优的通信模式，总耗时通常低于
N 条独立传输的简单相加，而且多条传输之间存在带宽竞争。当前模型两个效应都没有建模，
方向上偏保守（倾向于高估通信开销）。

要做准确需要引入拓扑感知的集合通信模型，是一项独立的改动。

### 8.2 求和合并节点的计算开销是估算值

求和的计算量按"N 份部分和需要 N−1 次逐元素相加"折算，作为一个固定项计入。
这个量级相对矩阵乘很小，但它没有经过真实硬件测量，也没有对应的算子编译产物——
求和不是矩阵乘，算子编译器没有为它生成指令序列。

### 8.3 仅覆盖 Llama 结构的两类张量并行组

展开逻辑按算子的语义身份（q/k/v/o 投影、gate/up/down 投影）识别张量并行组，
这些身份来自仿真器的模型结构生成环节。换成其他结构的模型（例如专家混合模型，
或注意力与前馈网络融合的结构），需要新增对应的识别和展开规则。

当前实现在结构不符合预期时会**明确报错**而不是静默出错，例如：

- 同一层出现两个相同身份的多分片算子
- 张量并行组里只有部分算子被标记为多分片（整组的切分方向是配套的）
- 组内各算子的分片数不一致
- 前馈链路的结构不符合"gate 投影 → 激活函数 → 逐元素相乘 → down 投影"

### 8.4 张量并行宽度必须整除注意力头数

按头区间路由分片依赖这个前提。图编译器侧已经强制校验，但仿真器侧的展开逻辑也
独立检查一遍并报错，不做静默兜底。

对于键值头数少于查询头数的分组注意力，还要求张量并行宽度整除键值头数。极端情况
（例如所有查询头共享一个键值头、而张量并行宽度大于 1）当前不支持——那种情况下
键值投影无法按设备切开，需要改成复制到每台设备，是另一种切分策略。

### 8.5 中间宽度配置未做端到端实测

三种端点配置都已实测：纯流水 `tp1_pp8`、混合 `tp2_pp4`、纯张量并行 `tp8_pp1`
（宽度 1、2、8）。中间宽度 `tp4_pp2` 没有跑过。

展开逻辑对宽度没有特殊假设，宽度 8 已经是最激进的情形（2368 个分片算子），宽度 4
在它与宽度 2 之间，从代码路径上看不出会有新的分支。但本次有三个缺陷都是实跑才暴露的
（第五节的缺陷四、五，以及被纯张量并行触发的缺陷五之二），所以这一条按"未验证"记录，
不写成"预期没问题"。

特别值得注意的是缺陷五之二的触发条件——本地输出宽度恰好等于分块大小。这取决于
`原始宽度 ÷ 切分宽度` 是否正好落在某个分块值上，是**非单调**的：宽度 2 和宽度 8
都测过，不能推断宽度 4 一定不触发新的形状组合。`tp4_pp2` 的本地宽度是 1024/2752，
分块搜索结果未知，值得实跑一次确认。

### 8.6 结论的适用范围

修复之后可以说的：

- 张量并行组内每台设备都有实际计算任务，各自占用资源
- 行切之后的求和合并在图上真实存在，其数据量是准确的
- 每台设备使用算子编译器实测的分块，不是配置文件里的默认常量
- 纯流水场景的结论与改动前等价，没有回退
- 三种端点配置（纯流水、混合、纯张量并行）都能端到端跑通

**仍然不能说的**：混合切分和纯张量并行的绝对耗时数字是准确的。原因是 8.1 和 8.2
两项——集合通信按点对点传输近似、求和开销是估算值。当前的数字适合用于**同类配置
之间的相对比较**（例如比较不同切分方案的优劣），不适合当成绝对性能预测。

要支撑"绝对准确"这个说法，还需要拓扑感知的集合通信模型，以及求和算子在真实硬件上
的测量数据。
