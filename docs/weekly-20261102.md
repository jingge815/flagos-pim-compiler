## 2. 让 vLLM 这一侧真的能用

### 2.1 生成方式：从「只选最大的词」到完整的采样

以前只会取分数最高的词。现在温度、top-p、重复惩罚、随机种子、候选词概率都按 vLLM 的
语义生效。做法是把选词留在主机，设备只负责算分数，代码在 `backend/sampling.py`：

```python
scores = raw.clone()
self._apply_penalties(scores, prompt_ids, output_ids)

if self.config.temperature < _SAMPLING_EPS:
    token = int(torch.argmax(scores))
else:
    scores = scores / self.config.temperature
    scores = self._apply_top_k_top_p(scores)
    probs = torch.softmax(scores, dim=-1)
    q = torch.empty_like(probs).exponential_(generator=self._generator)
    token = int(torch.argmax(probs / q))
```

三件事：先按重复/频率/出现惩罚调整分数；温度低于阈值时退回取最大值（与 vLLM 的处理一致）；
否则按温度缩放、截断 top-k/top-p，再用指数分布做的随机抽样挑一个词。随机数状态跟着请求
走，给定种子后结果可以复现。候选词概率在**惩罚和温度之前**的原始分数上算，
这与 vLLM 默认的 `raw_logprobs` 口径一致。

### 2.2 启动检查：不支持的能力先报错，不跑到一半才炸

启动时把张量并行、流水线并行、LoRA、投机解码、量化、数据类型、模型结构逐项检查一遍。
每个错误消息固定包含四样东西：参数名、当前值、支持什么、怎么办：

```python
def _unsupported(param: str, current, supported: str, advice: str) -> ValueError:
```

`scripts/serve_pim.py` 里另有一道容量预检，把四类问题一次列全，并给出可以直接复制的参数：

```python
f"建议加 --pim-prefill-seq-len {max_model_len}"
f"--pim-kv-pool-slots {blocks_per_request * num_request_slots + 1}，"
```

### 2.3 按输入长度选模板：短问题不再付最长问题的代价

编译时为几种长度各准备一份计算模板（比如 128、512、2048），运行时挑最小的能放下的那份：

```python
def prefill_bucket(compiled, n_tokens: int) -> int:
    for length in getattr(compiled, "prefill_seq_lens", ()):
        if n_tokens <= length:
            return length
```

以前所有输入都按最长模板算。100 个词的输入耗时从 7 675 毫秒降到 3 103 毫秒，省了六成。

### 2.4 长输入分块，以及「相同开头不重算」是怎么实现的

这两件事共用同一段代码：`prefill_chunk` 从任意位置 `pos` 开始算一段。

```python
seq_len = prefill_bucket(compiled, length)          # 按本段长度选模板
ids = list(token_ids) + [pad_id] * (seq_len - length)   # 右侧补空，不参与计算
...
"position_ids": torch.arange(pos, pos + seq_len, dtype=torch.long).unsqueeze(0),
...
slot.valid_len = pos + length
```

关键在 `pos`：这一段 token 写进缓存的位置从 `pos` 开始，注意力按绝对位置去读之前已经算好的
那部分历史。所以「从中间接着算」本身就是支持的——分块 prefill 是新输入分几次算，
前缀复用是旧缓存接着用，机制是同一个。

前缀命中的长度由 vLLM 告诉我们，新请求进来时直接写成已算长度：

```python
slot.valid_len = int(req.num_computed_tokens)   # 这段 KV 已经在共享块里
```

之后每一步再按 vLLM 的最新数字校正，命中的部分只读不写：

```python
computed = cached.num_computed_tokens[index]
resumed = req_id in cached.resumed_req_ids
if resumed or computed < slot.valid_len:
    slot.reset(list(cached.all_token_ids[req_id]), computed)
```

`computed` 比本地已算长度短，说明 vLLM 认定前面这段可以从缓存里直接拿，于是把本地计数退回
`computed`，从这里往后接着写；否则会覆盖别的请求正在用的块。

实测两个相同开头的请求，三步变两步，耗时从 2 909 毫秒降到 2 537 毫秒。

### 2.5 内存不够时让位

内存紧张时 vLLM 会收走某个请求占的内存，之后再让这个请求补算。代码里只看一个标志：

```python
new_blocks = cached.new_block_ids[index]
if new_blocks:
    slot.blocks.adopt(list(new_blocks[0]), replace=resumed)
```

`resumed` 为真，表示 vLLM 重新分配了块，于是把本地块表整体替换成新的一套；为假则是正常的
追加。我们不做自己的回收决策，避免两边记账对不上。

块表只做三件事（`runtime/executor.py` 的 `KVBlockTable`）：`ensure` 补齐未分配的位置、
`adopt` 采用 vLLM 给的块号、`release` 归还。写入时整段覆盖：

```python
def _write_block_table(compiled, hal, slot: RequestSlot, slot_index: int = 0) -> None:
    """把本请求的块表写进每台 DPU 的第 `slot_index` 份块表缓冲。"""
    for spec in compiled.kv_specs.values():
        write_block_table(spec, hal, slot.blocks.slots, slot_index)
```

整段覆盖是必须的：短请求不能继承上一个长请求留在表尾的块号。

## 3. 并行到底能快多少：先把旧假设推翻

10-26 的说法是「快在设备计算填满了主机等待的空档」。这一周先测这个假设，结论是错的：

- 主机那段串行执行的锁只占全部时间的 9%–13%，不是瓶颈。
- 主机上有 42 条操作，其中 38 条要同时读写全部 4 台计算单元，拆开也没法并行。
- 真正的瓶颈是 Python 的全局解释器锁：同一时刻只有一个线程能执行 Python 代码。
  开了 16 个线程，进程实际只用掉 1.4–1.6 个 CPU 核心。

所以这周换了方向：不再拆锁，而是减少「每一步要下发的命令条数」。

### 3.1 把六条命令压成一条

模型里每层都有一段固定的归一化计算：平方、求均值、加常数、开方、再乘回去。
以前这五步各下发一条命令，现在合成一条。识别方式是把这串固定顺序的算子写成常量：

```python
RMS_NORM_CHAIN = (
    torch.ops.aten.pow.Tensor_Scalar,
    torch.ops.aten.mean.dim,
    torch.ops.aten.add.Tensor,
    torch.ops.aten.rsqrt.default,
    torch.ops.aten.mul.Tensor,
)
```

匹配到之后不删节点，而是给链首打一个标记，并记下真正要读的两个输入——链的入口张量和
缩放权重：

```python
flat_args = ([fusion.eaten[0].args[0], fusion.weight_node]
             if fusion is not None else _flatten_node_args(node.args))
```

生成执行计划时按这两个真实输入记读写，被吃掉的中间节点不再出现在依赖图里。
单请求每生成一个词，命令数从 934 条降到 718 条，少了 23%，生成结果一个字都没变。

### 3.2 把结论固定成自动检查

新增两个基准脚本：一个测多个请求并发，一个测调度参数（批大小、块大小、前缀缓存、分块）
的影响；再加一个检查脚本，把结果和记录的基线对比，超出范围就失败。判断规则很短：

```python
if tolerance == 0:                 # 计数类指标：必须完全相等
    ok = actual == expected
else:                              # 耗时类指标：看相对偏差
    deviation = (actual - expected) / expected if expected else actual
    ok = abs(deviation) <= tolerance
```

计数（内核调用数、最大并发数）不随机器变化，容差是 0；实际耗时受机器影响，容差 50%。
这个检查只在手动运行时执行（约 3 分钟），平时跑测试不受影响。我们故意改坏过两次
（让命令数变多、让并发退化成串行），检查都能报出来并指出是哪一项。

## 4. 支持第二种模型时，发现并修掉一个隐藏错误

Qwen2 和 Llama 结构几乎一样，只多三个偏置项。接入时发现一个更严重的问题：当一个模型里
「查询头」比「键值头」多时（分组查询注意力，现在的大模型基本都用），缓存被写到错误位置。
原因是记录注意力信息时，把键值头的编号当成了查询头的编号：

```python
for q_head in spec.q_heads_by_kv[head]:
    heads.append({"head": int(q_head), "kv_head": int(head), ...})
```

现在每个查询头单独一条记录，并带上它对应的键值头。写缓存时再按「这个键值头属于哪台计算
单元」去重，保证一个键值头只写一次：

```python
group = (entry["kv_head"], owner)
if group in written:
    continue
written.add(group)
```

修好后与 Hugging Face 的参考实现对比，分数偏差从 0.55 降到 0.0004，逐字生成的词完全一致。
这个错误在之前只用 Llama 的配置下看不出来。

目前支持 Llama 和 Qwen2 两类结构。其他结构、位置编码缩放、真正启用的滑动窗口注意力，
仍在启动时明确拒绝。

## 5. 编译时自动定容：按剩余内存决定并发数

并发数、缓存槽位这些参数仍是编译时定死，但不再需要人工猜。编译时先用最小的槽池试算一次
几何，装不下就把并发数往下调；槽池本身按「满并发容量」和「实际能装下多少」取小：

```python
if auto_parallel:
    while parallel_slots > 1 and _max_slots(probe) < blocks_per_request:
        parallel_slots -= 1
if kv_pool_slots is None:
    request_capacity = num_request_slots * blocks_per_request + 1   # vLLM 要留一个空块
    kv_pool_slots = min(request_capacity, _max_slots(probe))
```

装不下时会直接报错，并说明需要多少、当前能放多少、可以调哪个参数。
这样做的好处是把「跑到一半内存不够」提前成「启动时就报错」。

## 7. 仿真侧：让融合后的注意力也能被计价

10-26 只在运行时有融合注意力的实现，仿真器不知道该怎么给它计时。这一周补齐了三层：

- 计算模板里支持「按缓存块数循环」：读到 `perBlock` 标记就按块数跑一遍，块数在运行时绑定；
- 融合注意力在中间表示里成为一个节点（`PAGED_ATTN`），不再拆成四个；
- 四个节点的老写法也改成按块计费，两边用同一套口径。

```python
per_block = params.get("perBlock", "false") == "true"
```

### 7.1 复现命令（`genesim/README.md` 第 9 节）

两条路共用同一条输入轨迹 `traces/llama2_7b.trace`（10 个请求、8 084 个 token）、同一套
TP2×PP4 切分和同一份硬件配置，差别只在模型中间表示和放置文件：融合版用
`models/llama2_7b_tp2_pp4_local.ir`，四节点版用 `models/llama2_7b_tp2_pp4_legacy_local.ir`

|---|---|---|---|
| 总时间 | 2 654.04 秒 | 2 519.34 秒 | −5.1% |

| 算子类型 | 四节点 | 融合 |
|---|---|---|
| 矩阵乘（GEMM） | 12 620 秒（77.2%） | 12 620 秒（77.8%） |

前面算得快了，同时在跑的请求变多，每个词的平均间隔就被拉长。本次数字与 10-30、10-31
的记录完全一致，说明仿真对同一输入是确定的。

## 9. 还没解决的问题

1. 没有真硬件。现在的并发结论全部建立在软件模拟上，只能当上限看。
2. 并发数、缓存槽位在编译时定死，改一次要重新编译；运行中不会自动伸缩。
3. 内存占用随并发数成倍增长。7B 模型上可能只够开一个并发，那并行收益就没了。
4. 滑动窗口注意力模型（如 Mistral）还不支持。它改变的是「每个词能看到哪些前文」，
   和现在的固定规则冲突，要先决定由谁来说明这个语义。
5. 只能单进程运行。改成多进程后，现在的线程排队模型要重新验证。
