# 主机编排器（问题 6）——20260824

本次改动实现了技术方案「问题 6：主机编排器」的全部内容，并在真实
Llama-2-7B 权重、NumpyBackend 假硬件上跑通了完整的 prefill + 多步 decode
推理流程，逐 token 验证与单卡 PyTorch 一致。一句话概括：**编译期把标注图
+ 通信计划表 + 内存蓝图翻译成一份带精确依赖的命令清单，运行时按依赖关系
把命令发给 8 台 DPU 并发执行，再用一个 KV 感知的 attention 补丁把"自回归
解码"这件事接进去。**

## 一、这次实现了什么（概述）

编排器是全仓的枢纽——它不自己做任何切分或调度决策，只是把问题 1（图拆分）、
问题 2（DPU 映射）、问题 3（通信库）、问题 7（KV cache）、问题 8（内存
管理）已经算好的结果，翻译成一份可以直接执行的命令清单，然后照着清单跑。
分三块：

1. **编译期**（`runtime/exec_plan_gen.py`）：把一张标注图（比如 Llama 的
   计算图）转换成一份`ExecutionPlan`——一串命令，每条命令都清楚地写着"我要
   等哪些别的命令先完成"。
2. **数值执行**（`runtime/kernels.py`）：4 个 DPU 白名单算子（矩阵乘法、
   加法、乘法、tanh）的 NumPy 版本实现，真正拿真实数据计算。
3. **运行时**（`runtime/executor.py`）：把命令清单交给 NumpyBackend 真正
   执行，并且实现了"先算完提示词、再一个字一个字往后生成"的解码循环，
   包括让 attention 正确读写 KV cache 这件事。

在开发过程中，为了让整条链路真正跑通，还回头修了问题 8（内存管理）里
3 处遗留的地址计算问题，属于问题 8 和问题 6 联调时才暴露出来的真实缺陷。

## 四、整体流程图

### 4.1 编译期：一张图变成一份命令清单

```
标注图（问题1/2产物）
   │  每个节点：算子类型、在哪个DPU、要不要搬数据
   ▼
build_execution_plan 逐节点扫一遍
   │
   ├─ 节点是 DPU 计算（矩乘/加/乘/tanh）？
   │     → 生成一条 launch 命令，记下它要读哪些地址、写哪些地址
   │
   ├─ 节点的输入需要跨设备搬运（比如 all_reduce）？
   │     → 生成一条 host_reduce / host_concat / host_permute / host_slice 命令
   │
   └─ 节点是普通 host 计算（比如 RMSNorm 的开方）？
         → 生成一条 host_op 命令
   │
   ▼
每条命令都带着 waits 列表：
   "读后写"依赖（我要读的地方，之前谁写过 —— overlap 检测地址重叠）
   "写后读"依赖（我要写的地方，之前有没有还没读完的旧读者 —— 见下文 4.2）
   ▼
CompiledPlan（一份 ExecutionPlan + 图输出对应哪条命令）
```

### 4.2 内存复用带来的"写后读"依赖——这次修复的核心问题

内存是有限的，同一块地址用完就会被后面的张量复用（`greedy_reuse` 决定
谁跟谁共用）。共用没问题，但**顺序不能错**：

```
时间轴 ──────────────────────────────────────────▶

  张量A产生    A被读者甲读     A被读者乙读     张量B写入（复用A的地址）
     │             │               │                 │
     ▼             ▼               ▼                 ▼
  ┌─────┐      ┌──────┐        ┌──────┐          ┌─────────┐
  │写地址X│ ───▶│读地址X│───────▶│读地址X│ ────────▶│写地址X（B）│
  └─────┘      └──────┘        └──────┘          └─────────┘
                （甲）           （乙）          必须等甲、乙都读完
                                                  才能覆盖，否则甲/乙
                                                  读到的就是张量B的数据
```

问题 8 会算出"这个地址被复用前，还有哪些读者没读完"（`pending_readers`），
问题 6 的编排器要把这份"读者名单"翻译成"命令编号"，再塞进新命令的 `waits`
里——这是`_war_waits` 函数干的事。

**修复前的真实 bug**：`_war_waits` 查表时用的是"读者节点的名字"去查，但
登记表 `register_reader` 之前错误地按"被读的那个张量的名字"来记账，两边
的名字方向完全反了，导致查表 100% 查不到——`waits` 里少了这条依赖，等于
没等。串行执行时大部分情况恰好没出问题（因为命令本来就是按顺序发出去
的），但 8 台 DPU 真正并发执行时，就可能出现"张量B的写命令先跑完了，
甲/乙还没来得及读，结果读到的是错误数据"，具体表现是 decode 循环跑到
某个随机步数后输出全部变成 0（`<unk>`），而且同样的输入多跑几次结果还
不一样。

**修复方法**：把登记表改成按"读者自己的名字"记账，跟查表用的名字对上；
另外通信搬运命令（比如 all_reduce）自己也要登记一份"我是谁的读者"，
因为之前这类命令完全没有登记过自己。修复后专门写了一条测试直接检查
"查表能不能查到"，不再靠端到端跑数值去碰运气。

### 4.3 运行时：命令清单怎么被执行

```
execute_plan(plan, backend, 输入值, 位置)
   │
   ├─ 把这一轮的输入值和位置记到 backend 里
   │
   ├─ 按命令清单顺序，逐条：
   │     for cmd in 命令清单:
   │         等 cmd.waits 里列的每条前置命令完成
   │         把 cmd 交给 backend 执行（DPU 命令走线程池并发，
   │           无依赖的命令会真正同时跑）
   │
   └─ 等清单里全部命令（不只是跟最终输出有关的那些）都跑完才返回
        （这一步也是本次修复新增的，原因见下文 4.4）
```

8 台 DPU 各有自己的一条执行线程，没有依赖关系的命令会被同时扔给这
8 条线程——`tests/test_concurrency_llama2_7b.py` 专门验证了这一点：同一层
里 8 台 DPU 各自算矩乘的命令，执行时间窗口确实互相重叠，而不是排队等着
一个一个跑。

### 4.4 自回归解码循环

```
run_decode_loop
   │
   ├─ 第一步：execute_plan(prefill_plan, 整段提示词)
   │     → 拿到提示词最后一个位置的 logits，贪心采样出第一个新 token
   │     → valid_len = 提示词长度
   │
   └─ 循环，每步：
        execute_plan(decode_plan, 上一步采样出的 token, 位置=valid_len)
           │
           ├─ SDPA（attention）节点走专用的 KV 感知计算函数：
           │     1. 把这一步新算出的 K/V 写入 KV cache 的真实内存地址
           │     2. 从 KV cache 读出到目前为止全部历史的 K/V
           │     3. 用 host 端 NumPy 算 attention（QK 点乘 → mask → softmax → 乘 V）
           │
           ├─ 拿到这一步的 logits，贪心采样出下一个 token
           └─ valid_len += 1
```

**为什么 attention 需要专用处理**：Llama 真实模型导出后，attention 是
一个融合在一起的算子（不是拆开的矩乘+softmax），而且它的位置编码信息
（RoPE）在只有一个新 token 的时候，图本身没法表达"要读多长的历史"这件事
——`torch.export`导出时会把位置固定成常量。所以专门写了一个"KV 感知"的
计算函数替换掉图里原本的 attention 计算：图里算出来的新 token 的 Q/K/V
是真实的，直接拿来用；但 attention 的结果不用图里算的（那是错的，位置
不对），而是拿 Q 去跟 KV cache 里存的全部历史 K/V 重新算一遍。

## 六、明确实现了什么功能，哪些没做，还有什么问题

### 已实现

- 编译期把标注图 + 通信计划表 + 内存蓝图翻译成带精确依赖的命令清单。
- 运行时按依赖关系执行命令清单，8 台 DPU 真实并发。
- KV cache 感知的 attention，支持完整的 prefill + 多步自回归解码。
- 4 个 DPU 白名单算子的真实数值计算（NumPy 实现）。
- 输入真实提示词、输出正常可读文本这条完整链路。
- 修复了问题 8 内存分配里 3 处地址计算遗留问题（其中一处是本次编排器
  联调才暴露出来的写后读依赖丢失问题）。

### 没有实现（按之前跟用户确认过的边界）

- **不加载 FlagTree 真实编译出的 kernel 二进制**：FlagTree 的 pim mlir
  目前只到 MLIR 文本这一层，没有真正下降到可执行的二进制。数值计算全部
  走本仓自己写的 NumPy 版本（`runtime/kernels.py`），不是真实硬件指令。
- **不接 genesim 的性能仿真**：genesim 只做离线的时延/成本估算，不做真实
  数值计算，跟本次的执行链路没有对接。
- **不改问题 1 的 DPU 白名单去拆解 attention**：真实模型导出后 attention
  是一个融合算子，没有拆成矩乘+softmax 塞进 DPU 白名单，而是在执行器层面
  用专用函数处理（见第四节 4.4）。
- **不做序列变长、算子融合、异步调度**等第二/三阶段特性。

### 已知的局限和风险点

- 数值精度依赖限制 BLAS 库内部线程数为 1（`runtime/kernels.py` 导入时
  自动做），如果换了运行环境（比如不同的 NumPy 编译方式）导致这个限制
  没生效，理论上还是可能出现和线程调度相关的浮点误差累积，只是概率
  很低，不影响正确性只影响数值精度的微小抖动。
- decode 步数、序列长度都是测试规模（16 步、16 个 token 的提示词），
  不代表生产环境的实际规模，没有做过更大规模的压力测试。
- 写后读依赖修复后有专门的探测式回归测试，但没有做过长时间、大量重复
  的压力测试来彻底排除还存在其它类似遗留问题的可能性——目前的信心来自
  连续 4 次完整套件通过，加上对依赖表命中率做过量化核实（每次 152 条测试
  的实际检测覆盖足够充分），但不是数学上的完全证明。
