## 二、修改建议

### 问题1（高）：分批重导混用标定值，导致缓存数值错误
**问题说明**：需求 P0-3、设计 §4.1 要求 KV 进出使用一致的标定参数，实施 H5/H6 也按整模型标定向各图传递 scale。`export_ceva_bundle` 读取旧清单后，无条件更新整包的标定结果和编译版本，却只替换本次目标图，最后仅按阶段、层号集合判断完整。更改标定策略或 checkpoint 后向原包只重导 decode，会保留旧 prefill；根据 `generated_io` 与写盘器的 scale 传递逻辑，prefill 写 cache 与 decode 读 cache 将使用不同数值口径。临时目录复现替换了单图导出函数，用小文件记录传入的 scale，保留真实的清单合并和完整性判断：首次为 `[0.1, 0.2]`，第二次仅重导 decode 为 `[0.3, 0.4]`，最终 `complete=true`，prefill 文件仍是前者，清单只声明后者。该复现证明包管理缺少一致性约束；没有实际运行混合包的 GC 或仿真，不宣称已观测到硬件输出错误。

**涉及文件**：`gml_bridge/ceva.py:947–974`（`export_ceva_bundle`），`tests/test_ceva_export.py:1359`（现有测试只覆盖一次导出时的参数传递）。

**修改思路**：复用旧图前校验 checkpoint、标定结果和影响生成的编译配置是否一致；不一致时拒绝局部续导，或使依赖旧配置的图失效并重新生成。至少新增“完整包更换标定值后局部重导”的回归，确保同层 prefill/decode 不会混用 scale，也不会错误恢复完整标记。

### 问题2（中）：清单校验缺少引用核对，导致自检漏报
**问题说明**：需求 P0-1/P0-3、设计 §4.1/§7.3 要求覆盖 GML 引用的全部 bin，并满足厂商对应文件尺寸约束。`check_ceva_manifest` 只遍历清单列出的条目，将落盘尺寸、摘要与同一清单比较；没有解析 GML 核对引用集，没有要求 GML/IO_info 必须登记，也没有对照参考图检查对应文件尺寸。已直接调用真实检查器复现：空 `graphs` 返回成功；一份 GML 引用了不存在的 `missing.bin`，只把 GML 登记为 generated 且摘要正确，也返回成功。不过正常 `export_ceva_graph` 在写盘结束时已核对引用集与落盘集，清单中已登记文件被删除也能被检查器发现，后续 GC 还可能拒绝缺文件的图。因此本项限定为独立验收器的覆盖缺口，降为中；不能从这个负例推断现有包缺文件或整个 CEVA 流程会假通过。`130/130` 仅证明已登记条目自洽，不能替代参考尺寸检查。

**涉及文件**：`scripts/verify_gml_artifact.py:949–970`（`check_ceva_manifest`）；`tests/test_ceva_export.py:979`（仅测试角色和摘要错误）。

**修改思路**：拒绝空包和空图条目，逐图要求 GML、IO_info 存在并登记，解析 GML 后核对引用集、清单集与落盘集；按节点与字段对应参考文件校验尺寸，不能只比较清单自己声明的尺寸。保留合法的单层调试包支持，完整包另外核对预期图集合。新增缺少被引用 bin、漏登记文件、自洽但尺寸错误的负例。

### 问题3（中）：动态缓冲口径未统一，导致验收依据矛盾
**问题说明**：需求 P0-3 要求动态缓冲只按尺寸分配，不得用标定样本冒充实际计算；设计 §4.7 仍规定写零并标记 runtime，但 11-01 更新的 §4.1 已规定全部 generated、复用原有相位写盘规则。当前 CEVA 路径调用共享 `write_runtime_files`，中间激活使用源码内的标定激活，KV 权重通路使用按节点号生成的随机值，DQ/Softmax 相位缓冲也按样例激活计算。临时目录验证中，128 元素的中间激活缓冲和 KV 权重通路缓冲均有 128 个非零元素。实施 §3.3 又记录 GC 探针确认运行时缓冲内容不进 Registry，因此“文件非零”本身不足以认定使用假计算，原报告直接建议全部改零不够审慎；可以确认的是新旧设计与实际生成规则尚未统一，实施 A6 的“按尺寸写零”也不能作为当前状态的证明。

**涉及文件**：`gml_bridge/ceva.py:236`（新 CEVA 写盘入口）；`gml_bridge/export.py:579–586、770–778、787–800`（样例相位和中间缓冲写盘）；`docs/design-ceva-llama2-7b-20261028.md` §4.1/§4.7；`docs/implement-ceva-llama2-7b-20261029.md` A6、§3.3、§8.2。

**修改思路**：先明确每类文件是静态参数还是运行时缓冲，并用当前生成链做内容扰动验证，确认改变动态缓冲的占位内容不改变 Registry 和实际单层输出。如果继续执行 §4.7，则只对已确认的动态缓冲按尺寸写零；如果保留新版样例生成策略，则在设计和实施文档中记录替代关系与验证证据，明确样例不参与实际计算。不要把 LUT、FPSU 常量、静态标定 scale 或 prefill cos/sin 一并清零；来源标记按最新版使用 generated。

### 问题4（中）：告警档仍宣称一致，导致验收结论失真
**问题说明**：需求 P0-5、实施 H9 明确区分严格 token 对拍与告警档：告警档允许 token 分叉，只证明必要运行检查通过。`ceva_verdict` 允许包含 WARN 的 PASS 报告返回，`main` 随后无条件输出“token 与厂商基线一致”。本次用临时报告写入 token `[13, 42]` 对 `[13, 29902]` 的 WARN 和总判定 PASS，调用真实 `ceva_verdict`，再替换耗时运行函数进入真实 `main`，确实得到退出码 0 和“token 与厂商基线一致”的摘要。本项是告警场景的报告错误，不否定 `own_bins_e2e` 现有四个 token 实际相同。

**涉及文件**：`scripts/run_full_pipeline.py:684–691、755–760`（`ceva_verdict`、`main`）。

**修改思路**：从判定报告保留 token 检查的实际状态，最终摘要分别报告仿真通过和 token 对拍通过或告警。新增“WARN + 总结 PASS”的输入用例，确保不会输出 token 一致。
