## 二、修改建议
### 问题1（高）: 直接仿真容量可抬高，导致16GiB违规放行
　　**问题说明**：request §2.1 P0-3 与用户确认的口径要求 8 DPU × 8 GiB 硬约束；design §十.5 要求导出、仿真前复核与直接 GeneSim 使用同一容量规则，任一值偏离即失败。GeneSim `_validate_hw_budget` 却把期望值取为 `self._pim_capacity_limits()["cluster_capacity_bytes"]`（`genesim/src/scheduler/gene_sim_scheduler.py:687-711`），该值可由 `pim.cluster_memory_capacity_gb` 任意配置（`genesim/src/pim/capacity.py:57-68,98-125`）；`_validate_pimir_hardware_contract` 又用同一可配置值核对真实 MLIR 的 `pim.mram-bytes`（同文件 1161-1200 行）。本轮实际探针结果为：默认 8 GiB 配置接受 8 GiB sidecar、拒绝 16 GiB sidecar，但**配置与 sidecar 同时为 16 GiB 时直接 GeneSim 明确 ACCEPTED**（`/tmp/qwen3-review-round11/probe-capacity.log`）。这把“产物与当前配置一致”误当成“符合需求硬约束”，直接仿真可绕过 8 GiB 验收。
　　**根本原因**：前几轮容量修复只消除了主链、真实测试与 GeneSim 默认值之间的 4/8/16 GiB 分歧，没有把需求常量作为严格产物的独立上限；两个校验器都从运行配置推导期望值，配置和产物同步改大后仍自洽。现有 `TestHwBudgetContract`（`genesim/tests/sim/test_compiler_placement.py:3226-3320`）只在默认 8 GiB 配置下改 sidecar，未覆盖两侧同步改值。相同根因同时影响 sidecar 三字段与每份 MLIR 属性核验；编译器主链的 `validate_sidecar_contract` 固定取 `default_hw_budget()`，不受这一条直接 GeneSim 旁路影响，不能据主链通过而认为直接入口也已关闭。
　　**涉及文件**：`genesim/src/pim/capacity.py:17-26,29-126`；`genesim/src/scheduler/gene_sim_scheduler.py:663-717,1161-1200`；`genesim/tests/sim/test_compiler_placement.py:3226-3320`；`flagos-pim-compiler/docs/design-qwen3-moe-20261105.md` §十.5。
　　**修改思路**：在 GeneSim 容量契约中显式定义与编译器对应的 `DPU_MRAM_BYTES=8 GiB`，严格 compiler-placement/pimir 路径同时断言“sidecar 值 == 需求常量”和“本次有效配置 == 需求常量”，真实 MLIR 属性也固定对应该常量，不再从可配置容量反推验收标准。仅对明确标识的旧式非严格产物保留其它硬件容量的兼容行为，避免误伤合法通用仿真。补直接 GeneSim 在配置与 sidecar 同时为 4/16 GiB、仅一侧偏离、默认 8 GiB 正例及非严格旧产物正例，并将同一常量贯穿 MLIR 属性检查，不能只给当前 16 GiB 探针加特判。
### 问题2（高）: 运行产物共享并删除，导致跨任务互相覆盖
　　**问题说明**：design §十.4 要求“运行与结果目录按架构与策略派生，禁止跨任务删除共享固定目录”；实施 F39 声称该问题已修复。当前 `run_directory` 只隔离日志和结果副本（`scripts/run_full_pipeline.py:1156-1161`），`step_e_simulate` 仍对共享的 `genesim/pim_traces` 执行 `shutil.rmtree`（1354-1357 行），随后从共享的 `genesim/results/summary.json` 读取并复制结果（1365-1381 行）；`prepare_simulation_config` 只改写请求数和 sidecar，没有为本次运行设置独立的 trace/results 输出目录（1114-1142 行，GeneSim 默认输出见 `genesim/src/main.py:817-818`）。A/A2/BCD 的模型 IR、精化 IR 与同策略 sidecar 也仍使用固定文件名。本轮在实际 `step_e_simulate` 中预置另一任务的 trace 与 summary，调用后哨兵 trace 被删除、共享 summary 被替换（`/tmp/qwen3-review-round11/probe-shared-output.log`）。因此不同策略或 dense/dynamic 任务共用 GeneSim 根时会互删、互覆盖，退出码 0 与后续 trace 审计可能指向另一任务的产物。
　　**根本原因**：round08 的修复只把“本次 sidecar 选择”和“日志副本命名”绑定到策略，没有建立覆盖 A/A2/BCD/E 的完整运行身份与输出命名空间；为保证重编而清缓存的动作仍作用于全局目录，验证器也硬编码读取同一全局位置。`test_run_directory_is_derived_from_artifact_and_strategy`（`tests/test_genesim_simulation.py:1110-1118`）只比较两个日志路径字符串，fake 仿真用例继续复现共享写入，没有哨兵保留或并发/交错运行断言。相反路径已复核：本轮使用独立 GeneSim 根的顺序 dynamic/dense 主链均正确，说明问题是共享根下的隔离缺口，而不是合法顺序执行或“本轮必须重编 trace”的需求有误。
　　**涉及文件**：`flagos-pim-compiler/scripts/run_full_pipeline.py:131-147,243-349,944-1087,1114-1161,1300-1385,1446-1610`；`flagos-pim-compiler/tests/test_genesim_simulation.py:1082-1189`；`genesim/src/main.py:817-818`；`genesim/src/scheduler/gene_sim_scheduler.py:2773-2777`；`flagos-pim-compiler/docs/design-qwen3-moe-20261105.md` §十.4。
　　**修改思路**：建立贯穿全流程的运行上下文，按架构、策略、执行语义和唯一运行号派生模型 IR、精化 IR、sidecar、trace、results 与日志目录；E 阶段临时配置同时写入本次 `output.pim_traces_dir` 与 `output.results_dir`，freshness、仿真 IR、trace 验收和 summary 读取统一从该配置解析路径，禁止继续硬编码共享目录。用本次独立空目录保证全量重编，删除对共享 `pim_traces` 的 `rmtree`，不要只把删除动作换一个目录名。增加同一 GeneSim 根下两种语义/策略交错执行及预置哨兵测试，断言另一任务产物不消失、每份 summary/trace 都属于本次运行；保留合法顺序执行与显式缓存复用路径。
### 问题3（中）: 证据检查丢失归属，导致错配结论仍放行
　　**问题说明**：round10 问题2要求实施数值与 summary 自动一致，并重算依赖这些值的差值和结论；实施 F48 称 summary 是唯一数值来源、历史值须显式声明。`check_document` 实际只把所有产物格式化值放进一个全篇 `allowed` 集合，再检查各值是否“在文档任意位置出现”（`scripts/check_implement_evidence.py:44-62`），既不把指标绑定到 dynamic/dense/alt/48l 标签，也不重算差值；高精度扫描只覆盖特定千分位格式（23-24 行），科学计数法表示的错误派生结论不会进入检查。本轮把 dynamic 与 dense 的时间、吞吐和 FLOPs 全部对调，并写入 `claimed difference=9.99e99`，返回仍为 `missing=[]、unknown=[]`（`/tmp/qwen3-review-round11/probe-evidence-checker.log`）。因此 round10 的“人工誊写”根因只收敛到数值是否存在，没有收敛到数值归属与结论正确性。
　　**根本原因**：证据检查以整篇文本的数值集合为模型，没有结构化的“运行身份 → 产物 → 指标 → 引用位置”关系；测试只覆盖单个数值抄错和合法历史值（`tests/test_implement_evidence.py:44-95`），没有标签互换、历史值冒充当前值、派生差值错误等反向用例。相同缺口会影响 dynamic/dense、替代策略、48 层与历史结果之间的错配。反向核对表明当前实施文档引用值本身正确，用本轮真实 summary 运行现有 checker 也通过；本问题是防复发机制与测试完备性不足，不是再次宣称当前文档誊错。
　　**涉及文件**：`flagos-pim-compiler/scripts/check_implement_evidence.py:23-62,86-113`；`flagos-pim-compiler/tests/test_implement_evidence.py:38-95`；`flagos-pim-compiler/docs/implement-qwen3-moe-20261105.md` §1.3、§7.1 round10 问题2、§8-§9；`flagos-pim-compiler/docs/review-qwen3-moe-20261111-round10.md` 问题2。
　　**修改思路**：用结构化证据清单或在实施文档中嵌入机器可读证据块，逐条记录运行标签、模型层数、当前/历史属性、命令、summary 路径与引用指标，由检查器从对应 summary 生成文档值，而不是全篇搜索允许值；派生差值、比值和结论必须由同一组指标重算，历史证据使用独立命名空间，不能仅靠 `--history` 放行一个裸数字。补 dynamic/dense 标签互换、4 层冒充 48 层、历史冒充当前、错误差值/比值及合法分栏正例，确保同类错配都会失败，同时不把当前已核实的合法文档误报为失败。
