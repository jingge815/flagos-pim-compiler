## 二、修改建议
### 问题1（严重）: PV未按相位取整，导致数值偏离契约
　　**问题说明**：request §2.1 P0-1/P0-4/P0-5 与 design §1.2 要求执行结果与 HF 对齐，`PIMOps.td` 的 `paged_attn` 进一步明确“点积 f32 累加后落 f16，softmax 五相各按自己的存储类型取整，每块的 value product 先落 f16 再加进 f32 输出”。`LowerPIMToEmitC.cpp:3027-3064` 却在块内以 f32 累加 `dot` 后直接计算 `acc * alpha + dot`，没有调用已有的 `roundF16`（同文件 1414 行，QK 相在 2940-2945 行已使用）；主机 `_host_paged_attention` 在 `runtime/kernels.py:1498-1503` 用返回 fp16 的 `matmul` 逐块累加，存储边界与设备不同。本轮用安装内 FlagTree 实跑：编译结果与“不做 PV 取整”的参考逐元素相同，与契约参考有 16 个元素不同、最大差 0.0001220703125（单块 0.00048828125），证明这是有效执行路径上的实际偏差，不是文字差异。多块历史下每次 RNE 取整都会改变后续累加输入，块数越多传播越大；相位表（`ExpandPhases.cpp:612-646`）又把 PV 相按 f32 累加器 `accBytes` 记，和契约要求的 f16 产品存储边界不一致，修复时要一并核对。
　　**根本原因**：相位存储边界没有由一份统一契约驱动，PV 这一相在手写单遍在线 softmax 时漏掉取整；`tests/test_opcompiler_ops.py:1451-1520` 的参考又按“未取整”的 f32 `dot` 手写，测试与实现共享同一错误假设；`tests/test_kernels.py:411-457` 用 `atol/rtol=1e-3` 把这一差异当成“各自的取整位置”放行。该根因影响所有相位（QK、掩码、指数、求和、PV、输出归一化），不是单个 PV 探针；只要新增相位继续手写算术，就会再次偏离。
　　**涉及文件**：`flagOS-installers/FlagTree/lib/Dialect/TritonPIM/Transforms/LowerPIMToEmitC.cpp:1414,2940-2945,3027-3064`；`flagOS-installers/FlagTree/lib/Dialect/TritonPIM/Transforms/ExpandPhases.cpp:612-646`；`flagOS-installers/FlagTree/include/triton/Dialect/TritonPIM/IR/PIMOps.td:1636-1639`；`flagos-pim-compiler/runtime/kernels.py:1457-1504`；`flagos-pim-compiler/tests/test_opcompiler_ops.py:1451-1520`；`flagos-pim-compiler/tests/test_kernels.py:411-457`；本轮 `logs/probe-paged-attn-r14b.log`、`logs/probe-paged-multiblock-r14b.log`。
　　**修改思路**：以一份相位存储边界表统一 lowering、主机参考与测试，逐相写明每相写回/读回的存储类型；按已声明契约在块 PV 写回 f32 累加器前完成 f16 取整，并核对 QK、掩码、指数、求和、PV 与最终输出的取整点。测试参考必须独立于被测 lowering，覆盖单块、多块、尾块和会产生不同 RNE 的数值，既做逐元素对拍，也在 lit 中约束对应的取整调用；`test_sdpa_fused_paged_attn_tracks_the_host_path` 的容差不能继续掩盖契约要求的边界差。若确要改成 f32 PV 语义，应先回设计确认并同步修改算子契约与主机路径，不能继续用当前自洽测试代替确认。

### 问题2（严重）: 负槽号直接寻址，导致缓存越界
　　**问题说明**：分页注意力的正确性依赖块表项指向合法物理槽，非法项不能与槽 0 混同。`LowerPIMToEmitC.cpp:2889-2900` 的注释声称表尾 `-1` 会夹到槽 0，实际只判断有符号 `slot < poolSlots`，没有 `slot >= 0`；生成的 C 中 `v35 = v33 < 4`、`v37 = v35 ? v33 : 0`，`slot=-1` 时条件为真，随后 `kBase/vBase = kOff/vOff + (-1) * slotElems`，在默认偏移下落到缓存之前，可读错数据也可造成内存故障。大于等于 `poolSlots` 的项被静默换成槽 0，同样把非法输入算成另一物理槽；主机 `_iter_kv_blocks`（`runtime/kernels.py:1540-1556`）对负项明确报“未分配”，但**不检查上界**，`slot=poolSlots` 会越过槽池读取，两条执行路径的合法集合互补错位。本轮探针确认：主机 `negative=REJECTED`、`zero/last_legal=ACCEPTED`、`upper_invalid=ACCEPTED`；设备对 `-1` 生成负偏移。
　　**根本原因**：块表有效性只做了单侧判断，注释、主机校验与设备 lowering 没有共享一份契约；测试 `test_paged_attn_matches_the_online_reference` 只用合法 `[1,3]` 乱序块表，未覆盖负值、上界、未分配项。相同根因同时影响 K/V 两个基址、任意负块号和上界非法项，不是单个 `-1` 探针的局部问题；槽 0 与 `poolSlots-1` 是合法边界，不能一刀切拒绝。
　　**涉及文件**：`flagOS-installers/FlagTree/lib/Dialect/TritonPIM/Transforms/LowerPIMToEmitC.cpp:2889-2900`；`flagos-pim-compiler/runtime/kernels.py:1425-1454,1540-1556`；`flagos-pim-compiler/tests/test_opcompiler_ops.py:1451-1520`；本轮 `logs/probe-paged-attn-r14b.log`、`logs/paged_attn_emitc.cpp`。
　　**修改思路**：在主机预检与设备 lowering 间统一块表不变式 `0 <= slot < poolSlots`，所有本次历史实际读取的项都必须满足；主机在启动/迭代前逐项校验并明确失败，设备侧不再用槽 0 替代非法项（由预检保证合法，或 emit 一个明确的失败路径）。共享同一校验函数或契约生成逻辑，并补主机/编译路径的负值、上界、未分配、槽 0、最后合法槽与多块尾块测试，同时检查 K/V 地址而不只检查最终是否崩溃。若产品确需允许 `-1` 哨兵进入计算，先回设计统一语义，再实现与参考一致的处理。

### 问题3（高）: 严格入口缺产物放行，导致复核失真
　　**问题说明**：design §十.4-5 要求显式严格开关或 sidecar 自报任一成立时，导出、skip-simulation、freshness、仿真 IR 与 trace 都按完整产物契约验收。`verify_sidecar_freshness`（`scripts/run_full_pipeline.py:1537-1574`）只有在 `ir_path` 存在时才调用共享验证器，`verify_sim_ir_matches_sidecar`（1577-1613）在没有 IR 或 sidecar 配置键时直接返回，`verify_trace_provenance`（1616-1714）在缺 IR 或 sidecar 文件时只检查来源白名单便返回；`_config_text`（1121-1130）还把配置文件缺失当成“没有可核对对象”返回 `None`。本轮实测配置显式严格时：删 sidecar 配置键，freshness/仿真 IR/trace 均 ACCEPTED；sidecar 文件缺失，trace 仍 ACCEPTED；删 IR 配置键，三者均 ACCEPTED；IR 文件缺失，freshness 仍 ACCEPTED；配置文件本身缺失时，`_config_text` 返回 `None`，用真实 GeneSim 根（`pim_traces` 含 10906 条旧 trace）复跑，三者同样 ACCEPTED。于是缺少同源核对所需的核心输入，独立复核仍能签发通过。
　　**根本原因**：旧式“无对象可比对就跳过”的兼容分支在读取严格性上下文之前执行，round12 只把 `strict_pimir` 传入已经到达共享验证器的路径，没有收敛这些提前返回；严格性又被当成“产物可选字段”的函数内推导，而不是入口级必需输入。相同根因影响三个复核入口及缺配置、缺 IR 键/文件、缺 sidecar 键/文件的全组合；导出与 skip-simulation 另有显式严格检查，直接 GeneSim 也会在生成 trace 前拒绝，因此不能把这两条路径误判为同样可绕行。
　　**涉及文件**：`flagos-pim-compiler/scripts/run_full_pipeline.py:1121-1130,1537-1574,1577-1613,1616-1714`；`flagos-pim-compiler/tests/test_genesim_simulation.py:131-137,1569-1632`；`docs/design-qwen3-moe-20261105.md` §十.4-5；本轮 `logs/probe-contracts-r14b.log`、`logs/probe-missing-config-r14b.log`。
　　**修改思路**：把配置解析和严格性判定提到所有兼容返回之前；严格模式下仿真配置本身、IR 配置键与文件、sidecar 配置键与文件均为必需输入，任一缺失都在 freshness、仿真 IR 与 trace 各自入口直接失败，再调用同一个完整验证器；只有调用方和产物都明确非严格时才允许无 sidecar 的旧式用法。按“配置严格/非严格 × sidecar 自报有/无 × IR 键/文件缺失 × sidecar 键/文件缺失”建立全入口矩阵，同时保留合法旧产物、纯放置与合法 host/边界正例，避免把兼容路径误伤。

### 问题4（高）: trace未绑定MLIR哈希，导致错产物放行
　　**问题说明**：design §十.4 要求 sidecar 的 `pimir_path/pimir_sha256` 与实际消费产物闭合，trace 验收要证明源 IR 应覆盖集合真实使用 pimir，absorbed 只接受已通过融合结构证明的空 trace。`verify_trace_provenance`（`scripts/run_full_pipeline.py:1644-1662,1689-1714`）只读取 `trace_source`、`op_id/parent_op_id` 与 tile 统计，既没有读取 trace 已写入的 `compile_signature.pimir_sha256`（该字段由 `gene_sim_scheduler.py:2897-2900` 用实际 pimir 内容哈希生成），也没有核对 trace 的 `op_type`、`expert_id` 或 `num_instructions`。本轮实测：正确哈希的 trace 接受后，把其中一条改成 64 个零、删掉哈希或改成错误 `op_type`，均返回 ACCEPTED；缺哈希的夹具同样被接受。只凭 `trace_source=pimir` 和父编号，不能证明这条 trace 是由 sidecar 指向的那份 MLIR 生成，也不能证明 absorbed 节点真的是空 trace。
　　**根本原因**：round04 的覆盖修复把“来源标签 + 父算子集合”当成完整 lineage，sidecar 文件哈希与 trace 编译签名分属两条未连接的校验链；现有 trace 夹具只写来源，未形成真实哈希正例，也没有空 absorbed trace 与错父编号反例。相同根因影响所有 pimir/absorbed trace、TP 分片回指和多块/多形状产物；“实际 4/48 层 trace 的哈希全部正确”只能说明当前产物没有错配，不能证明验收器能拒绝错产物。
　　**涉及文件**：`flagos-pim-compiler/scripts/run_full_pipeline.py:1644-1662,1689-1714`；`genesim/src/scheduler/gene_sim_scheduler.py:2858-2903,2990-3050`；`flagos-pim-compiler/tests/test_genesim_simulation.py:1544-1563,1670-1681`；本轮 `logs/probe-contracts-r14b.log`、`logs/audit4l.json`、`logs/audit48l.json`。
　　**修改思路**：把 trace 验收扩展为逐条 `(parent_op_id, op_type, pimir_sha256)` 与源 IR/sidecar 的联合核对：pimir trace 必须有可解析且在源 IR/sidecar 中的父编号、正确类型和与 sidecar 相同的非空编译签名哈希，TP 分片回指同一源条目；absorbed 只接受 `num_instructions=0` 且融合结构已证明的空 trace；缺哈希、错哈希、错父编号、错类型或拿另一形状/分块产物都必须失败，并继续执行来源与应覆盖集合检查。用真实带哈希产物作正例，增加删哈希、换哈希、换父编号、换类型、非空 absorbed 及合法多分片反例，避免只修来源标签。

### 问题5（中）: 正文标签归属不闭合，导致错配证据放行
　　**问题说明**：round10/round11/round12 要求建立“运行身份 → summary → 指标 → 正文语境”的绑定，并拒绝只交换正文、4/48 层互借、历史冒充 current 与错误比较结论。`_prose_context_problems`（`scripts/check_implement_evidence.py:384-418`）却允许数值属于所在块内任一前置标签，`check_document`（530-538）对必需值仍只做去掉证据块后的全篇字符串存在检查，`_check_comparisons`（421-439）也只比较两个数值大小而不核对左右运行身份；`_unknown_numbers`（457-464）与 `_allowed_tokens`（442-454）仍是全篇允许集合。本轮实测：原文通过；追加“dense_sim 与 dynamic_dispatch 中，前者的 88.483 s 低于后者的 91.012 s”这一语义对调句仍通过，因为两个标签和数值关系都分别合法；只把全部必需指标放在无标签前言、正文标签后不再给值也通过必需值检查；容量字节、通信字节等不在三项 summary 指标内的证据值也完全不在绑定范围。
　　**根本原因**：round12 用“块内前置标签集合”代替逐值归属，没有处理同块多运行的位置关系，也没有把必需值检查限定到对应运行锚点；比较器进一步丢失左右操作数身份，证据模型仍是“数值集合”而不是“值→运行→指标→正文位置”的关系。新增测试只覆盖单标签块和值完全缺失，未覆盖同块对调、无标签汇集、比较身份交换及非 summary 证据值，属于前一轮只让当时探针变绿而未收敛同类路径。
　　**涉及文件**：`flagos-pim-compiler/scripts/check_implement_evidence.py:288-344,384-439,442-464,530-538`；`flagos-pim-compiler/tests/test_implement_evidence.py:322-375`；`docs/implement-qwen3-moe-20261105.md` §4.1、§7.1 round12 问题2、§8.3；本轮 `logs/probe-contracts-r14b.log`。
　　**修改思路**：用显式证据引用锚点或由结构化证据块生成正文指标，建立每个值到唯一运行标签和指标的可机读对应，不允许无标签值满足 current 的必需引用；同块多运行必须按位置或显式锚点解析，比较结论同时核对左右运行身份与方向；容量、通信、trace 计数等证据值也纳入同一绑定或独立命名空间，不能只覆盖三项 summary 指标。补同块对调、无标签前言、值放在其它段落、比较身份交换、4/48 层互借、history/current 互借及非 summary 证据错值反例，以及合法多运行比较和分栏正例，避免为堵住绕过而误伤合法文本。
