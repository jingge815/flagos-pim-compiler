## 二、修改建议
### 问题1（严重）: B 路 pimir 按全局形状计费，导致 4L/48L 代价失真
　　**问题说明**：design §十.7 要求「当前 token 的逐元素、归一化、激活、视图类与专家乘加按 `Tq` 计费」，§十.6 与 §九 的 4L/48L `total_time_s`、`tokens/s` 是代价验收证据；requirement §2.1 P0-3/P0-4 与用户验收口径 2 要求专家乘加按 `moe_intermediate_size=768` 且与执行语义一致。实现里 B 路 pimir 在 `genesim_bridge/placement_export.py:1049-1050` 由**源 IR**（全局形状）构建，`_bpath_pimir`（`:327-362`）把 `Tq` 等符号维一律取 `_SYMBOLIC_DIM=128`；sidecar 的 B 路条目固定 `shards: []`、不带本地形状（`:511-515`）。GeneSim 的 TP 展开把 VECTOR_MUL/SILU 等按 4 台 DPU 拆成局部分片（`genesim/src/scheduler/gene_sim_scheduler.py:1850-1860`），并把源 pimir 原样继承给每个分片（`:2316-2337`，注释假设「分片和原算子的本地形状一致」）；但 `PIMVPU` 对 `_VECTOR_RUNTIME_OPS` 用**实际 Tq** 重复整条 trace（`genesim/src/vpu/vpu.py:488-495,604-608`），`execute_runtime` 直接乘重复次数（`genesim/src/backend/pim_backend.py:144-165`），trace 的相位字节却来自 128-token、全局 768 的 pimir。于是 tp4 下 local=192 的每个 VECTOR_MUL 分片执行一份 128×768 的 trace，再按实际 Tq 重复：宽度放大 4×、token 放大 128×，合计约 512×。
　　实证：本轮 4L dynamic 运行的 `pim_traces_pimir/op_10010_VECTOR_MUL.pim_trace` 输入形状为 `[Tq,192]`，但 `pimir.total_in_bytes=393216`、`total_out_bytes=196608`（=128×768×2）；父算子 2245 在 sidecar 里 `shards: []`、源 IR 形状 `[Tq,768]`（专家 42）。A 路 GEMM 的 `op_10000_GEMM.pim_trace` 的 pimir 是 local `n_extent=192`/`tile_n=128`，与 B 路口径不一致。`results_pimir/op_type_metrics.json` 的 VECTOR_MUL `latency_s=65.244`（dynamic）/`70.940`（dense）、`count=141312`；按 trace 每次 0.4617 ms、local 192/单 token 应约 0.0009 ms，约 512×。`/tmp/round10-fix/genesim-48l/results/op_type_metrics.json` 的 VECTOR_MUL 为 `782.930 s`（count 1695744），48L `total_time_s=566.863`、`tokens/s=1.402` 也建立在这条错误成本上。PAGED_ATTN 同样用 128 行 q 占位：trace `tokens=128`，`_block_loop_binding` 在 `tokens>1` 时把重复次数置 1（`:529-551`），本轮 4L 请求 prefill 输入 726 token（加 69 个 decode 共 795）的查询侧被低估约 5.7×（按实施文档 §9.2 的 795 口径约 6.2×）、decode 单 token 被高估 128×；GeneSim 的 paged-attn 文档已把它记为不足，但 Qwen3 实施文档 §9.2 用 88.483/91.012 的比值解释动态收益时未扣掉该偏差。
　　**根本原因**：B 路 pimir 在导出时按模型级源 IR 构建（全局宽度、128 占位），而 GeneSim 运行时绑定把 trace 当成 A 路 GEMM 的「单 token/单 tile」单位，乘实际 Tq 和本地宽度；sidecar 的 B 路条目没有本地形状，TP 展开的 pimir 继承注释只在 A 路 GEMM（本地 pimir）成立。严格产物校验只核路径/哈希/父编号，不核 trace 的 `tokens`/相位字节与运行时 `exec_input_shapes` 是否一致；测试夹具用 1-token pimir（`genesim/tests/sim/test_pimir_trace.py:93-107`、`test_vpu.py:566`），没有 tp4+Tq=795 的用例，因此 45/45 测试与 4L/48L 主链都没有暴露。同一根因还覆盖所有 B 路算子（VECTOR_MUL、SILU、RMSNORM、ROPE、SPLIT/TRANSPOSE/RESHAPE/CONCAT 等）、Llama2 TP 的 MLP VECTOR_MUL 以及直接 GeneSim 入口；round02 问题5/round04 问题1 的「代表形状不跟随算子」修复只落在精化侧 IR 系数，B 路 pimir/trace 仍按代表形状计费，属同类路径遗漏。
　　**涉及文件**：`flagos-pim-compiler/genesim_bridge/placement_export.py:180-251,327-362,481-515,1049-1050`；`genesim/src/scheduler/gene_sim_scheduler.py:488-495,529-551,604-608,1850-1860,2316-2337`；`genesim/src/vpu/vpu.py:276-293,456-527,604-608`；`genesim/src/backend/pim_backend.py:144-165`；`genesim/src/pim/pimir_trace.py:630-682,903-919`；`genesim/src/ir/model_ir.py:880-901`。证据：`/tmp/qwen3-review-round16/pipeline-dynamic/qwen3_moe_tp4_pp2_dynamic_dispatch_20261112-100948-3658110/{pim_traces_pimir/op_10010_VECTOR_MUL.pim_trace,artifacts/qwen3_moe_tp4_pp2_placement.json,results_pimir/op_type_metrics.json}`；`/tmp/round10-fix/genesim-48l/{pim_traces/op_100006_VECTOR_MUL.pim_trace,results/op_type_metrics.json}`。
　　**修改思路**：把 B 路 pimir 改为按**运行时单位**生成——`Tq=1`（或编译器实际 prefill 桶长）加每台 DPU 的 local width，并让 sidecar 的 B 路条目携带 local shapes 与 trace token 数；`_attach_bpath_pimir` 接收本次 strategy/local widths，`_expand_multi_shard_operators` 只在 local shape 一致时继承 pimir；`PIMVPU` 对 B 路用 `ceil(actual_tq / trace_tokens)` 并把相位字节按 local/global width 归一（或直接使用 local pimir）；PAGED_ATTN 同样用 Tq=1 的 trace 或按 `trace_tokens` 缩放查询侧字节。严格 trace 验收增加一条固定不变式：trace 的 `tokens`/`total_*_bytes` 必须等于运行时 `exec_input_shapes`/`exec_output_shapes` × 实际 Tq（含 TP 本地宽度），不满足即失败。补 tp4+Tq=795 的 VECTOR_MUL/RMSNORM/ROPE/视图用例与 prefill/decode PAGED_ATTN 用例，要求四个分片的合计成本等于模型级 768×Tq，而不是 4×768×128；修复后重新生成 4L/48L E 的 summary（A/BCD 可复用；若 pimir 文本变化则重跑 BCD），并在实施文档中更新或标注 §8.2/§9.2 的 total_time/tokens/s 与 1.029×。编译器执行期 A/B 1.148×/1.202× 不受本问题影响。

### 问题2（中）: A 阶段未核对 top_k，导致专家命中口径无法验收
　　**问题说明**：request §2.1 P0-1/P0-3 与用户验收口径 1 明确 30B-A3B 是 128 专家 **top-8**、专家宽 768；design §十.1 要求 MoE 身份由有效字段判定；implement §8.2 的 A 行把「128 专家 top-8、专家宽 768」列为 A 段证据。`scripts/run_full_pipeline.py:203-217` 的 A 段只比较 `ir["moe_num_experts"]` 与 config 的 `num_experts`，并检查 `expert_gemms == num_layers*experts*3` 与 `parameter_bytes == num_parameters*2`；`moe_top_k` 不进入权重字节，所以这三项都不会发现 top_k 被写成 7。`genesim_bridge/placement_export.py:855-859` 的 sidecar `moe_config.top_k` 直接取自 IR，`gene_sim_scheduler._validate_moe_config:768-800` 只比较 sidecar 与 IR，二者自洽即通过；GeneSim summary 也取 IR。因此把 top_k 写错的 IR/sidecar 可以一路通过 A/BCD/E，只改变动态分派比例（7/128 对 8/128）和 `MOE_ROUTE` 成本，链路不失败。本轮探针 `/tmp/qwen3-review-round16/probes/topk`：把 4L A IR 的 `moe_top_k` 改为 7、重算并回写 `model_fingerprint` 与 sidecar 的 `ir_fingerprint`/`moe_config.top_k` 后，`validate_sidecar_contract(..., strict_pimir=True)` **ACCEPTED**，`step_a` 的 num_experts/专家 GEMM 数/parameter_bytes 三项也全过；没有任何代码比较 IR 的 top_k 与 config 的 `num_experts_per_tok`。
　　**根本原因**：A 段的 MoE 身份校验按字段枚举，而不是按 config 派生完整期望四元组；`moe_num_experts` 被显式检查，`moe_top_k` 没有进入任何权重字节校验，只剩精化/仿真侧与 IR 自洽的比对。相同根因影响任何新增 MoE 标量字段（例如将来的 `norm_topk_prob`、共享专家数）以及直接 GeneSim/单独导出入口——它们只拿 IR/sidecar，无法独立核对 config。现有 `genesim/tests/sim/test_model_parser.py:216-225` 用 tiny config 断言 top_k=2，`tests/test_qwen3_30b_real.py:71` 断言的是编译器加载的 config，不是 GeneSim parser 对真实 30B 的 top_k。
　　**涉及文件**：`flagos-pim-compiler/scripts/run_full_pipeline.py:203-217`；`flagos-pim-compiler/genesim_bridge/placement_export.py:855-859`；`genesim/src/scheduler/gene_sim_scheduler.py:768-800`；`genesim/src/ir/model_ir.py:1446-1472`；`genesim/tests/sim/test_model_parser.py:216-225`；`tests/test_qwen3_30b_real.py:70-71`；探针 `/tmp/qwen3-review-round16/probes/topk`。
　　**修改思路**：在 `step_a_model_ir` 从 `config.json` 构造 `expected_moe = {num_experts, top_k, intermediate_size, execution}`，与 IR 四项逐项比较（宽度虽由 parameter_bytes 间接覆盖，也显式比较并给出期望/实际）；BCD 阶段把 sidecar 的 `moe_config` 同时对照 config，而不是只对照 IR；补一条链级反例测试（monkeypatch parser 输出 top_k=7，或直接构造 IR）要求 A 段失败，并保留真实 30B top-8/768 正例。这样同一根因覆盖的其它 MoE 标量字段也由同一份期望元组守护。

### 问题3（低）: 门控注释仍写 routing != 0，导致语义误读
　　**问题说明**：项目 CLAUDE.md 要求注释与实现一致；design §4.1/§十.6 已把命中条件定为 top-k 选中索引生成的布尔 `selected_mask`，round14 问题6 也把 GeneSim 测试与设计里的 `routing != 0` 改为 `selected_mask`。但本轮修改的 `contracts/dtypes.py:19` 仍写「MoE 门控掩码（`routing != 0`）以 bool 形式……」，实际代码 `backend/architectures.py:40-48` 用 `torch.zeros_like(probs, dtype=torch.bool).scatter(1, selected, True)` 生成 `selected_mask`，`runtime/exec_plan_gen.py:178-183` 的 dispatch 读 `selected_mask.any(dim=0)`；`routing` 是浮点权重，只参与加权。该注释会让读者以为命中由非零权重决定，正是 round06/07 严重问题（零权重选中专家被跳过）的旧语义。
