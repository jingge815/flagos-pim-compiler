## 二、兼容性问题

### 1. 系统版本校验只放行 22.04

四个安装脚本各自都有一份 `check_platform()`（脚本之间没有公共库，各自独立定义），
里面都是同一句硬判断：

```bash
[[ "${ID:-}" == ubuntu && "${VERSION_ID:-}" == 22.04 ]] || \
  die "需要 Ubuntu 22.04，当前为 ${PRETTY_NAME:-未知系统}。"
```

改成同时放行 22.04 和 24.04：

```bash
[[ "${ID:-}" == ubuntu && ( "${VERSION_ID:-}" == 22.04 || "${VERSION_ID:-}" == 24.04 ) ]] || \
  die "需要 Ubuntu 22.04 或 24.04，当前为 ${PRETTY_NAME:-未知系统}。"
```

`ID == ubuntu` 和紧接着的 `uname -m == x86_64` 两条判断保持原样，非 Ubuntu、非 x86_64
仍然照旧报错退出。24.04.4 LTS 的 `/etc/os-release` 里 `VERSION_ID` 就是 `24.04`
（小版本号只体现在 `VERSION` 和 `PRETTY_NAME`），所以精确匹配即可，不需要前缀匹配。

行为等价性：当 `VERSION_ID` 为 `22.04` 时，新条件的布尔结果与旧条件逐点相同，22.04
上的行为和改动前完全一致；唯一的差异是 `24.04` 从「拒绝」变成「放行」。

脚本 2 的 `--help` 里那句「目标机器需 Ubuntu 22.04 x86_64」也一并更新，否则帮助文本
和实际行为对不上。

### 2. Python 安装路径把版本号写死

脚本 0 和脚本 2 各自装一份独立 CPython，落盘目录名是 `python-3.10.20`，同时建一个
版本无关的符号链接 `python` 指向它。问题出在脚本 2 的 `sync_triton_to_pytorch()`：
它绕开了符号链接，直接拼接 `"$FLAGTREE_PREFIX/python-3.10.20/lib/python3.10/site-packages/triton"`，
等于在本脚本里重建脚本 0 的内部目录命名约定；`python3.10` 这一层也当字符串写死。

改成两步：

1. 新增 `find_unique_site_packages()`，在给定的 Python 安装根目录下 glob
   `lib/python3.*/site-packages`，要求恰好命中一个，否则直接报错退出（不做静默兜底）。
2. `sync_triton_to_pytorch()` 改走两个符号链接 —— FlagTree 侧用 `$FLAGTREE_PREFIX/python`，
   PyTorch 侧用 `$PYTHON_LINK` —— 再交给上面的函数推导 site-packages 路径。

生成 `env-pytorch.sh` 的那段也一样：原来在生成的文件里写死 `python3.10`，现在改成
在生成的脚本运行时 glob `python3.*`，且会把临时变量一并 `unset`。

注意：脚本里的 `PYTHON_ARCHIVE` / `PYTHON_URL` 是**故意**钉死在 `cpython-3.10.20` 的，
那是「下载哪个解释器」的版本选型，不是路径推导错误，这次没有动。

### 3. 24.04 的系统 Python 受 PEP 668 保护

这一条不是脚本的问题，是文档的问题：`README.md` 让甲方用
`python3 -m pip install -U "huggingface_hub[cli]"` 装 `hf` 命令行来下载 gated 的
Llama-2 模型。这条命令在 24.04 上必然失败，原因有两个：

| | 22.04 | 24.04 |
| --- | --- | --- |
| 系统 `python3` | 3.10 | 3.12 |
| `python3 -m pip` | 装了 `python3-pip` 才有 | 默认**没有** pip |
| `/usr/lib/python3.*/EXTERNALLY-MANAGED` | 无 | **有**，报 `error: externally-managed-environment` |

实测在裸 `ubuntu:24.04` 上：

```text
$ python3 -m pip --version
/usr/bin/python3: No module named pip
```

装完 `python3-pip` 后直接装包依然被 PEP 668 拒绝。正确做法是用独立 venv，22.04 上
同样可用：

```bash
sudo apt-get install -y python3-venv
python3 -m venv ~/.hf-cli
~/.hf-cli/bin/pip install -U "huggingface_hub[cli]"
```

已把这段写进两份文档（见第七节）。四个安装脚本本身不受影响——它们用的是自带的独立
Python 3.10.20，系统 `python3` 只在脚本 3 里做一次存在性检查。

## 三、24.04 上暴露出来的真实缺陷：CPU 版 torch 不带 triton

在容器里跑脚本 2 时撞上了这个报错：

```
错误：PyTorch wheel 未安装 Triton：/work/installed/pytorch/python/lib/python3.10/site-packages/triton
```

路径部分已经是对的（走的是 `python/lib/python3.10` 符号链接，不再是写死的 `python-3.10.20`），
真正的原因是：**CPU 版 torch wheel 的依赖里没有 triton**。

| torch wheel | 是否依赖 triton |
| --- | --- |
| `2.9.1+cu128`（CUDA 版） | 是，会拉 `triton==3.3.1` |
| `2.9.1+cpu`（CPU 版） | 否，依赖只有 filelock、fsspec、jinja2、networkx、sympy、typing-extensions |

而 `sync_triton_to_pytorch()` 原来的逻辑是「覆盖合并」：把 FlagTree 那侧的
`_C/libtriton.so`、`backends/pim_sidecar.py`、`backends/nvidia/compiler.py` 等拷到
PyTorch 侧的 triton 目录上。这在有卡机器上成立（CUDA 版 wheel 已经装了上游 triton），
纯 CPU 机器上 PyTorch 侧根本没有 triton，无处可覆盖。

修法是加一个分支：PyTorch 侧没有 triton 时，把 FlagTree 那份 triton 连同
`triton-*.dist-info` 整体装进 PyTorch 的 site-packages。带上 dist-info 是为了让 pip
知道 triton 已装好，后续步骤不会再去拉一份上游 triton 把它盖掉。

```bash
if [[ ! -d "$pytorch_triton" ]]; then
  note "PyTorch 侧没有 triton（CPU 版 wheel 不带），整体安装 FlagTree 的 PIM Triton"
  cp -r -- "$flagtree_triton" "$pytorch_triton"
  for dist_info in "$flagtree_site_packages"/triton-*.dist-info; do
    cp -r -- "$dist_info" "$pytorch_site_packages/"
  done
  return
fi
```

有卡机器的覆盖路径一行没动，走的是同一个 `if` 的另一个分支。

## 四、本仓的同类硬编码

`genesim_bridge/paths.py` 里有一个常量，把 FlagTree 的 triton 后端目录写成了
`"python/lib/python3.10/site-packages/triton/backends/nvidia"`，和安装脚本里是同一个毛病。
改成函数 `_flagtree_site_packages()`：在 `flagtree_prefix()/python/lib` 下 glob
`python3.*`，命中数不为 1 就抛 `RuntimeError` 并附带 `describe()` 的当前路径配置，方便定位。
`flagtree_nvidia_backend()` 改为基于它推导。

这个函数补了三个单测（唯一命中 / 一个都没有 / 命中两个），放在 `tests/test_paths.py`，
沿用该文件已有的 `_use_config` 写法。

### `scripts/export_gml.py` 里两处写死的开发机路径

导出脚本里两处校验把 GML 参考产物写成了开发机的绝对路径：

```python
ref = Path("/media/disk/fengjingge/src/xinfangzhou-resource/"
           "llama2_w4a8_decode_block_0/parser_output")
```

在别的机器上这两条路径恒不存在，于是：

- `_check_parser_families`（`--orchestrate` 时执行）打印「无参考目录，跳过」
- `_check_dtype_coverage`（默认执行）打印「无参考产物，跳过」

也就是说**校验会静默通过**——这正是「验证全部通过」里最容易骗人的那种通过。

而 `paths.json` 里本来就有 `gml_llama2_reference_dir`，指向的正是同一个目录。改成
`gml_llama2_reference_dir(required=False)` 取值：配了就真校验，没配才跳过。开发机上
`paths.json` 配的就是那个路径，行为逐字节不变。

改动前后在容器里的实际输出对比（容器里参考产物放在 `/work/ref`）：

| | 修复前 | 修复后 |
| --- | --- | --- |
| dtype 覆盖 | `[通过] GML dtype 覆盖: 无参考产物，跳过` | `[通过] GML dtype 覆盖（参考有则我方有）: 15 类算子，0 类缺 dtype` |
| 文件族（`--orchestrate`） | `[通过] parser_output 文件族: 无参考目录，跳过` | `[通过] 参考独有文件族都已产出: 缺 0 族，多 0 族` |

补了三个单测放在 `tests/test_export_gml_cli.py`：配了参考目录时要真的报出缺失的族、
没配时两条校验都要干净跳过。

## 七之二、GML 参考产物：谁提供、放哪里、要多少

这一节单独写，因为它是最容易在交付时踩空的一环。

**来源**：这两个键指向的不是 flagOS 任何组件的产物，而是**芯方舟底层编译器的标准输出样例**，
由甲方提供给我们做格式对标。所以交付文档里不能说"随交付物一起提供"——正确说法是
**甲方需要把这两个键指向他们自己保存这份样例的目录**。

**本机位置**：`/media/disk/fengjingge/src/xinfangzhou-resource`

**最小集合**：整个目录 814 MB，但当前代码实际只读其中三样，合计约 314 MB。实测只放这
三样，快速回归照样 714 passed：

| `paths.json` 键 | 需要的内容 | 体积 |
| --- | --- | --- |
| `gml_reference_dir` | `relay2gml_graph.gml`（ResNet50 的 GML 样例，只确定格式，非内容基准） | 184 KB |
| | `runtime_files/` | 68 MB |
| `gml_llama2_reference_dir` | `llama2_w4a8_decode_block_0/parser_output/`（GML + 3231 个 `.bin`） | 246 MB |

整目录里剩下的都是可以不带的东西：三个 `.zip`（131 MB + 159 MB + 34 MB）是上面这些
目录的压缩备份；两份 PDF、三张 jpg 和几份说明文档是人看的资料；`model_layers_0_decode_v2/`
（292 MB）见下。

**需要确认的一点**：`xinfangzhou-resource/README.md` 把
`model_layers_0_decode_v2/`（2026-09-21 新增）标为"**当前唯一有效标准**"，说
`llama2_w4a8_decode_block_0` 只是"历史对照"。但目前：

- `paths.json` 的两个键都指向 **v1**（`llama2_w4a8_decode_block_0`）
- 全仓 grep `model_layers_0_decode_v2`，代码、测试、配置里**一处引用都没有**

也就是说 v2 已经到了本地、还没接进验证链路。这不影响本次 24.04 适配的结论（用的还是

现在这套测试的对标基准就是过期的。这件事我没有动，留给熟悉这块的人定。

## 八、遇到的坑（记录备查）

1. **`cp -n` 在 24.04 上会告警**。脚本 0 解 sysroot 时用 `cp -an` 搬 deb 内容，24.04 的
   coreutils 会打印 "behavior of -n is non-portable"，只是告警，不影响结果。
   没有改成 `--update=none`：那个选项要 coreutils 9.3+，22.04 上的 8.32 没有，改了反而
   会把 22.04 弄坏。
2. **把宿主装好的 Python 整目录拷进容器会带坏 shebang**。`cmake`、`ninja` 这些 pip
   生成的包装脚本第一行写的是宿主绝对路径，在容器里执行会报 "required file not found"。
   这是验证方法本身的问题，不是安装脚本的问题——容器 B 从零装就没有这个现象。
3. **PyPI 直连很慢**，容器里改用清华源装非 torch 依赖、torch 仍走官方索引。
   这是验证环境的网络调整，安装脚本里的索引配置没有改动。
4. **脚本 2 的 Python 下载在自己的前缀下**（`<pytorch-prefix>/downloads/`），和脚本 0
   的 `<flagtree-prefix>/downloads/` 是两个目录。想省一次 42 MB 下载要两边都放。

## 九、当前不足

- 22.04 上的回归只做了推理和静态验证：新旧版本判断在 `VERSION_ID=22.04` 下逐点等价，
  PIM Triton 的覆盖分支在「PyTorch 侧已有 triton」时不进入新代码路径，但没有在真实
  22.04 + GPU 机器上重跑一遍四个脚本。
- 脚本 0 会给自己那份 Python 装 `torch==2.7.1+cu128`（供安装后验证和 FlagGems smoke
  test 用），**不区分有没有 GPU**，纯 CPU 机器上要多下约 2.5 GB 的 `nvidia-*`/`cuda-*`
  包。不影响正确性，已在两份文档里写明；要省掉改成 `2.7.1+cpu` 即可，但那是改默认
  配置，本次没有动。
- `scripts/verify_cpu_only.sh` 里的验证镜像仍固定 `ubuntu:22.04`。它是个容器内的
  GPU 隔离测试工具，和宿主机系统版本无关，本次没有改动。
- 容器里跑 7B 全量测试耗时 34 分钟，比宿主机明显慢，主要是模型反复加载所致。
- 导出脚本里那两处用 `gml_llama2_reference_dir` 替代写死路径后，`--orchestrate` 的
  文件族校验才开始真正执行。它在开发机上一直是真跑的，所以这次改动没有新增失败项，
  但**甲方那边会第一次真正跑这两项**——如果参考产物版本和当前代码不匹配，可能会暴露
  出新问题。建议甲方先单独跑一次 `export_gml.py --orchestrate` 确认。
