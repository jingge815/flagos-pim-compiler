379 个缺失文件全部是 `DEBUG_*` 前缀（含 `lut_debug`），是可选的对拍副本，不影响后端编译：

| 缺失族 | 数量 |
| --- | ---: |
| `DEBUG_input_buffer_float` / `_#_float` | 153 + 87 |
| `DEBUG_weight_buffer_float` | 73 |
| `DEBUG_div_value` | 32 |
| 其余 `DEBUG_*` / `lut_debug` | 34 |

**缺的是我方产物**（`/tmp/gml_full/`）：只有 7 个文件族、3339 个文件，且字段覆盖度 29/604 = 4.8%。详见 §6。

**第二层：`output_buffer` 字段在参考产物里是两种命名并存，不是单一规则。** 实测参考产物 GML 里 `output_buffer` 字段的指向：

| `output_buffer` 指向 | 次数 | 哪些节点 |
| --- | ---: | --- |
| `input_buffer_<消费者id>.bin`（**消费者命名，主规则**） | **157** | MatMul 64、Softmax 32、Mask 32、Gemm 7、布局类等 |
| `output_buffer_<自身id>.bin`（**自命名，例外**） | **38** | DynamicScaling 36 + Llama2ActivationDQ 1 + Split 1 |
| `weight_buffer_<下游id>.bin` | 2 | Split 26、Split 32（下游 MatMul 走权重通路） |

而我方 GML 里 `output_buffer` **1158 次全部指向 `input_buffer_*.bin`**，零次自命名。

**这个差异与上面的文件缺失是同一个根因**：我方 GML 里根本没有 DynamicScaling 节点（实测 `op_type "DynamicScaling"` 0 次、`rtl_version` 0 次、任何 `_phase_` 字段 0 次）。于是：

- `output_buffer_<id>.bin` 的 37 个里 36 个是 DynamicScaling 自命名的 → 没有该算子就没有这些文件
- `output_buffer_phase_*`、`Scaling_PS_buffer_phase_*`、`Scaling_buffer_phase_*`、`Bias_buffer_phase_*` 各 308 个全部是 phase 中间态 → 没有 phase 拆分就没有
- `Scaling_PS_buffer_file` / `Scaling_buffer_file` / `Bias_buffer_file` 的非 phase 部分（各 79–91 个）属 FPSU 配置 → 属甲档，规则已知可立即补（§6.4）

所以补齐路径不是「补几个文件族」，而是**先实现 DynamicScaling 与 phase 拆分**（§7.2 第 ④ 项）。

### 0.3 谁生成什么

**二次修订修改了三行归属**（标 ← 原「算子编译器」）。判据见 §2.12：GML 里的硬件字段
实测全部由 `(op_type, phase)` 唯一确定，无一按节点变化，属**常量表**而非排布结果。

| 信息类别 | 归属 | 落点 |
| --- | --- | --- |
| 图拓扑、形状、算子类型 | 图编译器 | GML 节点与边 |
| 量化位宽、scale/zp 数值、权重量化 | 图编译器 | GML 字段 + `.bin` |
| 算子融合、逐头展开、phase 拆分 | 图编译器 | GML 节点集合 + net.ini 层清单 |
| 权重布局（转置与否） | **图编译器常量表** ← 原算子编译器 | GML `weight_format`：由矩阵乘角色决定（QK^T 转置、PV 不转），**数学决定而非优化决定** |
| 功能单元绑定、数据通路模式 | **图编译器常量表** ← 原算子编译器 | GML `nmu_mode`/`fpsu_mode`/`kantor_mode`/`pooling_dtype`：按 op_type 固定 |
| 定标粒度、浮点指数范围 | **图编译器常量表** ← 原算子编译器 | GML `fpsu_spc/spg`、`flp_*`：按 (op_type, phase) 固定 |
| L2/DDR 物理地址、步幅对齐、缓冲区编号 | **算子编译器** | **仅在层参数文本**，不进 GML |
| 循环分块本身、片上复用策略 | 算子编译器 | 不外露（分块的**结果**体现为步幅） |
| 切分方案、设备映射 | 仿真器 | 不进交付物 |
| 张量并行、内存三区、KV cache 管理 | 图编译器 | 主机运行时，不进交付物 |

**后果：GML + bin（交付物一）不再阻塞于算子编译器**，图编译器可独立闭合。
算子编译器的职责收窄到层参数文本（交付物二）的地址与步幅。

**层参数文本的逐域归属实测**（251 个字段族去重）：

**二次修订重新测了归属**（判据：逐字段统计 `(layer type, phase)` → distinct 值集合；
同组恒为单值 = 算子模板常量，图编译器可填）：

| 归属 | 字段族数 | 占比 | 说明 |
| --- | ---: | ---: | --- |
| 图编译器可填（形状、拓扑、文件名、算子语义、DDR 形状） | **107** | 43% | 一次修订已确认 |
| **图编译器常量表可填**（调度 13 + 来源 5 + 单元 13 + 通路 6） | **约 37** | 15% | **← 本次从算子编译器移出** |
| **算子编译器必填**（DDR/L2 的 offset/size 22 + stride 12） | **约 34** | 14% | 收窄后的真实瓶颈 |
| 其余（按算子变化的单元/通路配置） | 约 56 | 22% | 多数可由算子语义推出 |
| 待确认（取值已查明，归属需对方确认） | 17 | 6% | |

**结论：层参数文本单靠图编译器填不满，单靠算子编译器也填不满，必须拼接。**
（注意这一结论只针对**层参数文本**；GML 侧图编译器可独立闭合，见上表。）
且**最终序列化必须由图编译器做** —— 序列化需同时掌握图拓扑（文件名、Residual、Graph I/O）与物理属性，而图编译器持有完整图，算子编译器只看到单个 kernel。逐域清单见 §3.6 与 `prepare_out生成规范.md` §3。

**拼接方式是图编译器两次介入**，不是单向交接：

```
① 图编译器：融合 + 逐头展开 + phase 拆分 + 量化
        ↓  硬件算子级 IR（200 节点）
② 算子编译器：在 IR 上标注地址、步幅、单元、调度（模块属性承载）
        ↓  带物理属性的 IR
③ 图编译器：序列化
        ├─→ relay2gml_graph.gml + *.bin   （交付物一）
        └─→ net.ini + txt_files/*.txt      （交付物二）
④ 图编译器：三方一致性校验
```

## 1. parser_output/ 各文件含义

### 1.1 relay2gml_graph.gml

硬件图 IR。参考产物由对方的 `relay2gml` 工具从 TVM Relay 子图翻译而来；
**我方由 pim-compiler 从 HF 模型的 fx 图直接生成同一份格式**（见 §1.4）。
文件名 `relay2gml_graph.gml` 是对方后端约定的固定名字，必须照用。

| 项 | 值 |
| --- | --- |
| 行数 | 16012 |
| 版本头 | `relay2gml_version "26.2.1"` |
| 节点 | 200（10 个 buffer/IO + 190 个算子） |
| 边 | 331 |
| 不同字段名 | 604（未归一化；折叠编号变体后为 **258 个字段族**，见 §7.5） |
| 引用的 `.bin` | 3464 个不同名字 |

**语法是 GML 变体，不是标准 GML**，读之前必须知道三条：

1. **同名键在一个 node 内可重复出现**。`residual_input_buffer` 每个输入槽出现一次。标准 GML 解析器会只保留最后一个，丢数据。必须按流式/有序方式解析。
2. **`id` ≡ `node_id`**（200/200 相同），`name` ≡ `label`（200/200 相同）。前者是 GML 保留字，后者是语义字段。
3. **`id` 顺序不是执行顺序**。算子链大多是"大 id → 小 id"。判断先后必须用 edge 或 `inputN_node_id`。

计算: RMSNorm → q/k/v_proj → RoPE → ScatterND(KV写入) → QK^T → /11.3137
      → +mask → softmax → PV → o_proj → 残差 → RMSNorm

输出: (hidden[1,1,4096], key_cache, value_cache)

**W4A8 量化契约**（参考产物记在 Relay 注解里，右列是我方的等价配置）：

| 项 | 参考产物的注解 | 我方量化配置 |
| --- | --- | --- |
| 激活 | `simulated_dynamic_quantize(-128f, 127f, spc=True, spg=True, axis=1, group_axis=-1, group_size=128)` | int8 对称、**动态**、per-channel + per-group、group_size=128 |

## 2. GML 字段语义

### 2.1 顶层与节点骨架

```
graph [
  directed 1
  relay2gml_version "26.2.1"
  node [ ... ]   x200
  edge [ ... ]   x331
]
```

节点有**两种形态**，写解析器和序列化器都要兼容：

| 形态 | 数量 | 特征字段 |
| --- | ---: | --- |
| buffer/IO 节点 | 10 | `is_buffer 1`，无 `op_type` |
| 算子节点 | 190 | 有 `op_type`，无 `is_buffer` |

buffer 节点内部又分两类：

| 子类 | node_id | 字段形态 |
| --- | --- | --- |
| 图输入（生产者） | 1–7 | `from_tvm 1` + `output_buffer` / `output_sf` / `output_zp` / `outputN_node_id` |
| 图输出（消费者） | 8, 199, 200 | 无 `from_tvm`，用 `input_buffer` / `input_count` / `inputN_node_id` |

### 2.2 标识与溯源类

| 字段 | 出现 | 含义 | 谁填 |
| --- | ---: | --- | --- |
| `id` | 200 | GML 主键，1–200 | 图编译器 |
| `node_id` | 200 | 语义节点号，恒等于 `id` | 图编译器 |
| `label` / `name` | 200 | 算子名。算子节点格式 `<算子路径>_qidx<N>_params_<node_id>`（190/190 成立）；buffer 为 `nprm_182_i<N>` 或 `output`/`key_cache_out`/`value_cache_out`。**我方 `<算子路径>` 取自 HF 模块路径**，见 §1.4 | 图编译器 |
| `original_name` | 10 | 图级 I/O 张量名，仅 buffer 节点有。参考产物用对方前端的内部名；**我方用 HF 语义名**（`hidden_states`/`key_cache`…） | 图编译器 |
| `is_buffer` | 10 | =1 表示缓冲节点 | 图编译器 |
| `from_tvm` | 7 | 字段名带 tvm，**实际语义是「这是图输入 buffer」**。7 个图输入全置 1 | 图编译器 |
| `is_mask` | 1 | 仅 node 6，标记 attention mask | 图编译器 |
| `op_type` | 190 | 硬件算子类型，见 §2.6 | 图编译器 |
| `rtl_version` | 37 | RTL 版本 `"1.4"`。**只出现在 phase 型算子**（36 DynamicScaling + 1 Llama2ActivationDQ） | 算子编译器 |
| `idx` | 197 | **本节点输出挂在消费者的第几个输入端口**。实测 197/197 满足 `consumer.input<idx>_node_id == self.node_id` | 图编译器 |

`idx` 是最容易误读的字段。它不是"第几个输出"，而是"在下游的哪个端口"。例：Split 26（k）与 Split 32（v）都是 `idx=1`，因为它们都挂在 MatMul 的 `input1`。

### 2.3 数据流连接类

数据流被**冗余记录三次**，三者实测完全一致：

| 记录方式 | 边数 |
| --- | ---: |
| `edge [source/target]` | 331 |
| 生产者的 `outputN_node_id` | 331 |
| 消费者的 `inputN_node_id` | 331 |

三个集合**逐边相等**（集合差为空）。所以下游可以任选一种遍历方式，生成时也必须三份都写且保持一致。

| 字段 | 含义 |
| --- | --- |
| `input0_node_id` … `input31_node_id` | 第 N 个输入的生产者 node_id |
| `output0_node_id` … `output31_node_id` | 第 N 个输出的消费者 node_id |
| `residual_input_buffer` | 与同位置 `inputN_node_id` **数值完全相同**（193/193 节点的列表逐项相等） |
| `residual_output_buffer` | 与同位置 `outputN_node_id` 数值相同（197/197） |
| `input_count` | 登记的输入个数。**MatMul 少记 1**，见下 |
| `A` | 矩阵 A 操作数来源。实测 71/71 恒等于 `input0_node_id` |

**`input_count` 的坑**：全图 `Σ input_count = 267`，而 `Σ edge = 331`，差值恰好 **64 = MatMul 节点数**。原因是 64 个 attention MatMul 各有两个 operand 引用（`input0_node_id` + `input1_node_id`），但 `input_count` 只记 1——第二个 operand 走**权重通路**（`MatMul_input_as_weight 1`）。生成时不能仅凭 `input_count` 分配 operand。

**键名 bug，必须容错**：端口号 ≥10 时键名变成 `residual_input_buffer_`（末尾多下划线、端口号丢失），实测 `residual_input_buffer_` 22 次、`residual_output_buffer_` 88 次。要与后续的 `inputN_node_id` 按顺序配对，不能把 `_` 当有效后缀。

### 2.9 动态量化的数学（完整实测推导）

以节点 12（`dynamic_quantization_params_12`，输入 `[1,1,1,4096]` fp16）为例，group_size=128 → 32 组。四个 phase 的产物：

| 文件 | 元素 | 含义 | 实测关系 |
| --- | ---: | --- | --- |
| `output_buffer_phase_0_12.bin` | 32 fp16 | 每组统计量 | **= 2 × per-group absmax**（32/32 精确成立） |
| `output_buffer_phase_1_12.bin` | 32 fp16 | 反量化 scale | **= phase_0 / 256** |
| `output_buffer_phase_2_12.bin` | 32 fp16 | 量化倒数 scale | **= 1 / phase_0** |
| `kantor_A_scale_buffer_file_phase_3_12.bin` | 32 fp16 | 同 phase_2 | 逐元素等于 phase_2 |
| `kantor_A_Shift_buffer_file_phase_3_12.bin` | 32 int8 | 移位量 | 恒 **-8**（即 ÷2⁻⁸ = ×256） |
| `output_buffer_12.bin` | 4096 int8 | 量化结果 | **= round(x × kA × 256)**，4096/4096 在 ±1 内 |
| `output_sf_12.bin` | 32 fp16 | 输出 scale | **逐元素等于 phase_1** |

即完整公式（g 为组号）：

```
absmax[g] = max(|x[i]|), i ∈ group g          # phase 0：global_pooling 求统计量
scale[g]  = 2 * absmax[g] / 256               # phase 1：反量化 scale（= 输出 output_sf）
inv[g]    = 1 / (2 * absmax[g])               # phase 2：量化倒数（= kantor_A_scale）
q[i]      = clamp(round(x[i] * inv[g] * 256), -128, 127)   # phase 3：kantor fp2int
```

`× 256` 由 `kantor_A_Shift = -8` 编码（2⁸=256）。等价地 `q[i] = round(x[i] / scale[g])`（实测同样 4096/4096 通过）。

**`×2` 与 `/256` 的由来（二次修订用硬件规范解释清楚）**：Ceva-NeuPro-M 规范 §4.3.4 说
Pooling 块做动态量化时「算 abs(max(x))（对称 DR），再算前导零并据此**左移** DR」——
左移 1 位就是 ×2。两步代入后：

```
q[i] = x[i] × (1/p0[g]) × 256 = x[i] × 256/(2·absmax[g]) = x[i] × 128/absmax[g]
```

**即 absmax 正好映射到 128 —— int8 的满量程**，等价地 `output_sf[g] = absmax[g]/128`
（实测 **32/32 组**吻合，量化结果用满 `[-128,127]`）。

> 所以一次修订「分母是 256 而不是 127，牺牲约 0.5 bit 动态范围」的说法**不准确**：
> 真实满量程分母是 **128**。与理论最优 127 只差 1 个 LSB，那是二补数 int8 固有的
> 不对称（负侧多一格），不是精度损失。int4 权重侧同理，除数是 **8** 而非 7 ——
> 实测 15000 个权重组里 7801 组含 `q = -8`，除数为 7 时这在数学上不可能出现。

这一节的公式此前在 pim-compiler 文档中列为"无法确认"（`docs/gml-lowering-20260914.md` 第 10.2 节）。现在已实测确认。

### 2.10 phase 流水线

phase 是硬件把一个大算子拆成的**顺序子流水级**，每级有独立的输入/输出缓冲、scaling、模式配置。

| 算子 | phase 数 | 各级职能（实测） |
| --- | ---: | --- |
| `DynamicScaling` (36) | 0–3 | p0: `global_pooling_*` 求组统计量；p1: LUT + `flp(10,17,3)` + `activation_mode=1`；p2: LUT + `flp(15,15,0)` + `special_operators=4`；p3: `kantor_mode="fp2int_converter"` 输出 int8 |
| `Softmax` (32) | 0–4 | 每级有 `nmu_output_type_phase_#`；p1: LUT+`flp(9,16,3)`；p3: LUT+`flp(15,15,0)`+`special=4`；无 `global_pooling_*` |
| `Llama2ActivationDQ` (1) | 0–3 | 与 DynamicScaling 同构（RoPE 后接动态量化） |

每级的字段族（`#` 为级号 0–4）：

```
input_buffer_phase_#          output_buffer_phase_#
input_buffer_dtype_phase_#    output_buffer_dtype_phase_#
input_data_extensions_phase_#  output_data_extensions_phase_#
fpsu_mode_phase_#  fpsu_spc_phase_#  fpsu_spc_axis_phase_#
fpsu_spg_phase_#   fpsu_spg_axis_phase_#  fpsu_spg_group_size_phase_#
Scaling_buffer_phase_#  Scaling_PS_buffer_phase_#  Bias_buffer_phase_#
kantor_mode_phase_#     pooling_dtype_phase_#
nmu_output_type_phase_#           （仅 Softmax）
global_pooling_*_phase_#          （仅 DQ 的 phase 0）
LUT_phase_#  flp_min_exp_phase_#  flp_max_exp_phase_#  flp_mantisa_phase_#
activation_mode_phase_#  activation_special_operators_phase_#
kantor_A_*_phase_#                （仅 fp2int 的 phase 3）
```

**Softmax 五相的语义（二次修订完整反推）**：

| 相 | 运算 | 验证 |
| ---: | --- | --- |
| 0 | `-max(x)` | fp16 读高半 = -max(x) 精确吻合 |
| 1 | `exp(x - max)` | max(p1)=1.0（max 元素处 exp(0)=1）；LUT 近似，相对误差 mean 4.8% |
| 2 | `Σ exp` | **4 字节按 fp32 读 = 84.875 = Σ(p1) 精确吻合** |
| 3 | `1 / Σ` | 与 `1/fp32(p2)` 差 1 fp16 ULP 内 |
| 4 | `exp × (1/Σ)` | **与 p1×p3 逐元素 1024/1024 吻合**；Σ(p4)=0.99975 |

对应 Ceva-NeuPro-M 规范 §4.2「Self-Attention (Softmax Support)」明列的
numerator / denominator / final 三层，多出的两相是 max 减法与倒数（规范 §4.3.3 把 `1/x`
列为 Activation 的 complex operation）。

**归约相的字节宽度**：DQ 的 phase0/2 是 `2 × 组数` 字节（每组一个 fp16）；
**Softmax 的 phase0/2 是 4 字节的单个 fp32**（与 `fpsu_mode_phase_3 = floating_point_32` 一致）。

**关键区分：编译期常量 vs 运行时归约落点。** 这三族 phase 定标文件里，有两个不是常量：

| 文件 | 性质 | 判据 |
| --- | --- | --- |
| `Bias_buffer_phase_0`（DQ） | **编译期常量 2⁻⁶³** | 36/36 节点字节相同；位于首相，无前序归约可承接。作用是避免全零组取倒数溢出 |
| `Bias_buffer_phase_1`（Softmax） | **运行时归约落点**（= phase0 的 `-max`） | 与 `output_buffer_phase_0` **32/32 节点逐字节相同** |
| `Scaling_buffer_phase_4`（Softmax） | **运行时归约落点**（= phase3 的 `1/Σ`） | 与 `output_buffer_phase_3` **32/32 节点逐字节相同** |

参考产物里 `Bias_buffer_phase_1` 解出 -30.75，那只是其合成输入的 max 使然。
**生成时不要硬编码 -30.75**，按 4 字节分配、让 phase0 写入即可。
硬件依据：FPSU 的 bias 操作数就是前一相的归约输出（规范 §4.3.2）。

### 2.11 LUT 表结构

139 个 LUT 文件（138 个 `LUT_phase_*` + 1 个 `activation_lut_file`）实测**只有 4 种不同内容**：

| md5 前缀 | 文件数 | 出现在 | `activation_mode` | `special_operators` | `flp min/max/mantisa` |
| --- | ---: | --- | ---: | ---: | --- |
| `17d2387467` | 69 | DQ phase2 / Softmax phase3 | 0 | 4 | 15/15/0 |
| `9e077580ba` | 37 | DQ phase1 | 1 | 0 | 10/17/3 |
| `4fc44231e4` | 32 | Softmax phase1 | 0 | 0 | 9/16/3 |
| `c133ac07eb` | 1 | Gemm 195 融合 SiLU | 0 | 0 | 10/17/3 |

**表内部结构由硬件规范确定**。Ceva-NeuPro-M 规范 §4.3.3：「PWL LUT 支持 **32 段**，
每段由一个 **slope** 和一个 **intercept** 定义」。实测布局与之精确吻合：

```
[0:32]     32 个 fp16 —— slope     A[i]   （第 32 项恒 0，实际用 31 段）
[32:64]    32 个 fp16 —— intercept B[i]
[64:104]   40 个 fp16 —— 未初始化残留，非参数（写 0 即可）
[104:144]  40 个 fp16 —— 填充
```

求值形式 **`y = A[i]·x + B[i]`**。

**`[64:104]` 是残留不是参数**：恒等表这 40 项全为 0 却能正常工作；exp 表该区是
`00bd ffff ffff…` 的填充模式；三张表该区互不相同且数值横跨 -31696…64448。
所以生成时**写 0 即可**，不必拷贝。

**倒数表已完整破解 —— 每段是 `1/x` 的切线**（不是弦线）。过点 `p` 的切线为
`y = -x/p² + 2/p`，故 `A = -1/p²`、`B = 2/p`，两者满足 **`A = -B²/4`**（31 段全满足，
fp16 精度内即精确）。段索引取 fp16 尾数高 5 位，指数单独处理。

**自行合成的表比参考产物更接近硬件输出**：在 5 个 DQ 节点上对拍硬件实测输出，
合成表平均偏差 **0.032%–0.049%**，参考产物的表 0.368%–0.666%。

`LUT_phase_1_12.bin`（DQ phase1）只有 index 0 非零且为 **1.0** —— 一张**恒等表**，
说明 DQ 的 phase1 走 LUT 通路但不做非线性变换。**按此合成与参考产物字节完全相同。**

**这一族已不再是硬阻塞**（此前判定如此）：

| 表 | 文件数 | 方案 |
| --- | ---: | --- |
| 恒等 | 37 | 合成，**字节级复现** |
| 倒数 | 69 | 合成，**精度优于参考产物** |
| SiLU | 1 | 合成（定域 `[-4,4)` 为拟合最优，非实测确认）；也可直接拷 |
| exp | 32 | 拷参考产物一次（与模型无关，全模型 32 层共用）；段索引规则仍未反推 |

合成代码见 `GML字段与bin映射策略.md` §13（已验证）。**注意**：表与
`flp_min_exp / flp_max_exp / flp_mantisa` 三元组强绑定，写表时必须同时写对。

逐族统计 `(op_type, phase)` → distinct 值集合，结果是**除一个字段外全部为单值**，
无一按节点变化：

## 3. prepare_out/ 各文件含义

### 3.1 它是交付物，不是中间产物

这一点容易误判（pim-compiler 文档记录过这次更正）。判据是 `net.ini.orig` 里的原始路径：

```
net.ini.orig:
  dumps_bin_path = vbu_L2_analyzer_python_sim\files\scaleNshift
  dumps_txt_path = txt_files
```

`vbu_L2_analyzer_python_sim` 是**对方 L2 分析器的仿真目录**（Windows 路径分隔符 `\`）。说明 `net.ini` + `txt_files/` 是**喂给它的输入**，对方是消费者。

实测 `net.ini` 与 `net.ini.orig` 各 435 行，**diff 只有这 2 行**，其余 433 行逐字节相同：

```
10,11c10,11
< dumps_bin_path = vbu_L2_analyzer_python_sim\files\scaleNshift     ← orig
< dumps_txt_path = txt_files
---
> dumps_bin_path = llama2_w4a8_decode_block_0/parser_output          ← net.ini
> dumps_txt_path = llama2_w4a8_decode_block_0/prepare_out/txt_files
```

所以 `net.ini.orig` 的作用就是**路径模板**：生成流程是「产出 orig 结构 → 改写这 2 行 → 得到 net.ini」。生成器可以直接输出最终的 `net.ini`，同时保留一份 orig 以对齐参考产物。

内容本身也是证据：每层有 13 处以上 L2 物理地址、9 处以上 DDR 地址。**只有做过内存规划的一方能填这些数值。**

### 3.2 net.ini

435 行，两个 section。**行尾是 CRLF**（实测 433 个 `\r\n`），注意被改写的两行 `dumps_*_path` 只有 LF——生成时统一用 CRLF 即可。

```ini
[general]
is_seq_test = 0
seq_tunneling = 0
test_update_buffer = 0
input_line_stride = 8
input_map_stride = 4
output_line_stride = 12
output_map_stride = 5

dumps_bin_path = <指向 parser_output>
dumps_txt_path = <指向 txt_files>

seq_output_bin_file = /net.bin
[layers]
layer = RMSNorm_params_25
layer = dynamic_quantization_params_24_gp_dq_phase1_params_213
... 共 422 行
```

| `[general]` 字段 | 值 | 含义 |
| --- | --- | --- |
| `is_seq_test` | 0 | 是否序列测试模式 |
| `seq_tunneling` | 0 | 序列隧道 |
| `test_update_buffer` | 0 | 测试更新缓冲 |
| `input_line_stride` / `input_map_stride` | 8 / 4 | 推测：全局输入步幅对齐参数 |
| `output_line_stride` / `output_map_stride` | 12 / 5 | 推测：全局输出步幅对齐参数 |
| `dumps_bin_path` / `dumps_txt_path` | 路径 | 二进制与文本的查找目录 |
| `seq_output_bin_file` | `/net.bin` | 序列输出文件名 |

那 4 个 stride 参数是全局对齐配置，取值依据未知（§9 问题 2）。它们**不随层变化**，所以即使含义不明也能照抄常量先跑通。

**格式细节**：`[general]` 与 `[layers]` 之间无空行；`[general]` 内部有 2 个空行（分隔路径块与 `seq_output_bin_file`）；赋值格式为 `key = value`（等号两侧各一空格）。

**net.ini 由图编译器独立生成，不需要算子编译器参与。** 理由：`[general]` 全是常量或部署路径，`[layers]` 是「图遍历顺序 + §4.2 展开规则」的直接产物 —— 两者都不涉及物理地址或硬件执行方式。**这是 prepare_out 里唯一不依赖算子编译器的部分，可以先做。**

`[layers]` 段是 **422 行、按执行顺序**排列的层名。实测 422 个层名全部唯一，且**每一行都有对应的 `txt_files/<层名>.txt`**（零缺失、零多余）。

**层的排列顺序即执行顺序**，实测顺序为：
```
RMSNorm(25) → DQ(24) 4级 → v_proj(36) → k_proj(31) → RoPE_k(30) 3级
→ q_proj(23) → RoPE_q(22) 3级 → RoPE_q 的 DQ 4级
→ [head0: matmul1(20) → mask(19) → softmax(18) 5级 → DQ(17) 4级 → matmul2(16)]
→ [head1 ... head31 同构]
→ DQ(12) 4级 → o_proj(11) → add_1(10)
→ RMSNorm(197) → DQ(196) 4级 → gate(195) → up(198) → mul(194)
→ DQ(193) 4级 → down(192) → add_2(9)
```

注意 **head0 的 DQ(17)+matmul2(16) 排在 head1 的 matmul1 之前**，之后每个 head 是 `matmul1 → mask → softmax(5) → DQ(4) → matmul2` 的完整块。这个交错顺序需要精确复现。

#### 第四类：DDR（主存）地址分配

```

DDR Input start Map 0: 0          DDR Input stride X 0: 1024

```

**`DDR * Orig Buffer Name` 是一个独立的 DDR 缓冲区索引空间**，不是 node id。实测：

| 名字形式 | 出现 | 含义 |
| --- | ---: | --- |
| `buffer<N>` | 356 | DDR 缓冲区编号。**144 个不同值，范围 1–189，稀疏（有空洞）** |
| `<层名>_dequant_buff` | 108 | DQ 的 per-group scale 缓冲，1:1 对应 `output_buffer_phase_1_<id>.bin` |
| `nprm_182_i<N>` | 72 | 图输入张量，沿用 GML buffer 节点名 |
| `<层名>_mul_cos_buffer` 等 | 8 | RoPE 中间缓冲 |
| `output` | 1 | 图输出 |
| `buffer24_map21` 等 | 3 | 带 map 偏移的子视图 |

**`buffer<N>` 与 `.bin` 文件是严格 1:1**（实测 195 个名字→195 个不同 bin，零多对一；反向仅 1 例一对多，是 RoPE 的 sin 常量被两个名字引用）。但 `buffer<N>` 的 N **不等于产生它的节点 id**（实测 0/175 匹配）——它是独立编号。

例：`buffer176 → input_buffer_184.bin`，`buffer3 → output_buffer_phase_3_12.bin`，`buffer11 → input_buffer_0_19.bin`。

这意味着生成器需要**自己维护一张 DDR 缓冲区分配表**，为每个跨层张量分配编号。参考产物的具体编号无需复现（只要自洽），但 `buffer<N>` ↔ bin 的 1:1 关系必须保持。

`DDR * buffer offset` / `buffer size` 实测大量为 0——推测是留给后端 L2 分析器自己算，或表示"由上层分配"。

#### 第五类：L2（片上）地址分配

这是**算子编译器职责最集中的一类**，每层 13 处以上。

```
L2 qman buffer offset: 536805376      L2 qman buffer size: 65536
L2 input num of buffers 0: 1          L2 input buffer offset 0: 0
L2 input buffer size 0: 2048          L2 input num of maps 0: 1
L2 input slice maps offset 0: 0       L2 input slice num of maps 0: 1
L2 input for DMA height 0: 1          L2 input for DMA width 0: 1024
L2 output buffer offset: 2112         L2 output buffer size: 2080
L2 fpsu buffer offset 0: 536791040    L2 fpsu buffer size: 7168
L2 weights buffer offset 0: 8256      L2 weights buffer size: 32768
L2 weights use partial buffer: 1      L2 weights use double buffer: 1
L2 weights buffers per engine: 4      L2 weight scale buffer offset 0: 536645600

**地址空间是两段**（实测 1146 个高位偏移 + 735 个低位偏移）：

| 段 | 范围 | 例 |
| --- | --- | --- |
| 低段 | 0 … 约 10⁶ | `L2 input buffer offset 0: 0`、`L2 output buffer offset: 2112` |
| 高段 | 接近 2³⁰ | `536805376 = 2²⁹ − 65536`、`536641440 = 2²⁹ − 229472` |

`L2 qman buffer offset` 恒为 **536805376 = 2²⁹ − 65536**，大小恒 65536——即 qman 队列固定在 512 MB 地址空间的**最后 64 KB**。高段偏移都是从 2²⁹ 往下分配的。

**缓冲区编号（buffer id）是硬件资源槽位**，实测取值高度受限：

| 字段 | 取值分布 |
| --- | --- |
| `L2 input buffer id 0` | `4` ×252（唯一值） |
| `L2 input buffer id 1` | `5` ×41（唯一值） |
| `L2 output buffer id` | `6` ×85，`7` ×64，`5` ×71 |
| `L2 weights buffer id` | `6` ×64，`w2` ×7，`w1` ×2（**数字与 `w` 前缀混用**） |
| `L2 fpsu buffer id` | `f1` ×71，`f2` ×117，`f3` ×96，`f4` ×69，`f5` ×69 |
| `L2 data scale buffer id` | `5` ×71（唯一值） |

**source 字段是数据来源标识，不是布局**：

| 字段 | 取值 | 推测含义 |
| --- | --- | --- |
| `Weights source` | 3 ×358，0 ×64 | 从哪一级存储取权重。64 个 0 恰好是 MatMul 数（权重来自另一个张量而非常量） |
| `Fpsu source` | 3 ×262，1 ×160 | 定标系数来源 |
| `Data scale source` | 0 ×71（唯一值） | 数据 scale 来源 |

**恒定字段**（全 422 层相同）：`Bytes in cycle internal memory read/write: 64`、`L2 qman buffer offset/size`。

## 5. 谁生成什么：责任划分

### 5.1 判据

一项工作是否影响交付物，取决于交付物有没有承载它的字段。

```
图编译器的工作
    │
    ├─ GML 有对应字段？ ──是──► 直接影响：字段值由它决定
    │                           （量化、融合、拓扑、形状）
    ├─ 没有但改变节点集合？ ──► 间接影响：改变图的形状
    │                           （常量折叠、死代码消除、CSE、图分割）
    └─ 都不是 ──────────────► 不影响：属于主机运行时
                                （张量并行、内存三区、KV cache 管理、通信计划）
```

### 5.2 完整归属表

| 信息 | 归属 | 落点 | 我方当前 |
| --- | --- | --- | --- |
| 计算图拓扑与形状 | 图编译器 | GML 节点/边/dims | **已有** |
| 量化位宽选择 | 图编译器 | 各 buffer 的 dtype 字段 | **已有** |
| 量化参数数值（sf/zp） | 图编译器 | `.bin` + 字段 | **部分**（缺 zp、输出侧） |
| 权重量化与 per-group scale | 图编译器 | `weight_buffer` / `weight_sf` | **已有** |
| 算子融合（Gemm+SiLU） | 图编译器 | `contraction` 嵌套块 | 否 |
| 注意力逐头展开 | 图编译器 | 节点集合（32 头 × 4 节点） | **否**（当前批量表达） |
| DynamicScaling phase 拆分 | 图编译器 | phase 字段族 + 阶段 bin | 否 |
| net.ini 层清单与顺序 | 图编译器 | net.ini | 否 |

### 7.2 逐项说明

#### ① 甲档字段与二进制补齐

无阻塞，性价比最高。约 20 个文件族。要点：

- zp 全零、`Scaling_buffer_file` = fp16(1.0)、`Scaling_PS` = u8(0)、`Bias` = fp32(0.0)
- `output_sf` 从下游 `input_sf` 反推，或对 phase 型节点等于 `output_buffer_phase_1_<id>.bin`
- **命名大小写必须精确**：`Scaling_buffer_file`、`Scaling_PS_buffer_file`、`Bias_buffer_file` 首字母大写。当前 `contracts/gml_names.py` 的 `fpsu_scale/fpsu_post_shift/fpsu_bias` 已经用了正确大小写
- **`contracts/gml_names.py` 里有三个函数产出参考产物中不存在的名字**：`bias_buffer()` → `bias_buffer_<id>.bin`（小写，参考产物 0 个）、`bias_scale()`、`bias_zero_point()`，以及 `activation_input()` 系列 → `Relu_input_<id>.bin`（参考产物 0 个）。实测参考产物既没有小写 `bias_buffer_*` 也没有任何 `Relu_input*` 文件，GML 里也没有这两个字段。**这几个函数要么对应本 block 用不到的算子，要么是从别的参考产物推的规则** —— 用之前需确认，否则会产出后端不认识的多余文件
- `input_data_extensions` 由 dtype 推导，但要保留 Split 21 那个 float16→1 的例外可能性
- DEBUG 族可以完全跳过（参考产物自己就有 379 个悬空 DEBUG 引用），但**跳过时不要在 GML 里写引用**，否则不如参考产物干净

#### ② 算子融合

需要的融合模式（实测参考产物用到的）：

| 融合 | aten 算子 → 硬件节点 |
| --- | --- |
| RMSNorm | `aten.pow`+`mean`+`add`+`rsqrt`+`mul`+`mul` → 1 个 `RMSNorm_vpu`（含 `vpu_params` 嵌套块 + `RMSNorm_Add_Const`） |
| Gemm+SiLU | `aten.linear`+`aten.silu` → 1 个 `Gemm` + `contraction[fused_Silu_act]` |

## 8. 验证框架：五层校验

生成这些文件后怎么确认正确？本节把校验分五层，从「数量对不对」到「数值是否真的来自 Llama2-7B」。**每一层都给出参考产物上的实测基线**，可直接作为断言实现。

### 8.0 一个必须先讲清的前提：参考产物用的是合成数据

这是本次验证工作最重要的发现，它决定了整个校验策略。

**参考产物 `parser_output/*.bin` 里的数值不是来自真实 Llama2-7B 权重，而是随机/占位数据。** 四条独立证据，每条都不依赖张量布局假设（因此不受「转置了没有」这类歧义影响）：

| # | 检验对象 | 实测结果 | 真实数据应当是 |
| ---: | --- | --- | --- |
| 1 | `weight_buffer_25.bin` / `_197.bin`（RMSNorm，int8，**1-D、per-tensor、无布局歧义**） | **4096 个值全部为 127**，scale=1/127，反量化后**恒为 1.0** | 真实 `input_layernorm.weight` 是 0.0297、0.0136、0.0020…（量级 0.01–0.8） |
| 2 | RoPE 的 cos / sin 输入（`input_buffer_2_30.bin` / `_1_30.bin`，**解析形式已知**） | 取值范围 **[-2.27, +2.49]**，超出 [-1,1] | cos/sin 必须落在 [-1,1] |
| 3 | attention mask（`input_buffer_1_190.bin`） | **968 个不同值，50.2% 为正数**，范围 [-3.01, +2.98] | 因果掩码只应有 0 与大负数两种值 |
| 4 | int4 权重与真实权重的相关性 | 约 **0**（-0.028，与随机基线 -0.003 无区别）；扫遍 32 层全部约 0 | 应接近 ±1 |

**证据 1 是决定性的**：RMSNorm 权重是一维、per-tensor 量化，不存在转置、分组轴、行列错位任何一种歧义。它全为 127 就意味着「原始张量是全 1 的占位数组」，而非真实权重。

**方法学教训（两条，都踩过）**：

1. **int4 反量化不能用逐元素相对误差判定。** 我最初用 `|deq−real|/|real|`，得到 97% 元素误差 >15%，据此连试 8 种布局假设全部"失败"。错在判据：int4 量化下接近 0 的权重被量化成 0，逐元素相对误差必然接近 100%，**即使量化完全正确**。正确判据是**峰值相对误差** `max|deq−real| / max|real|`，int4 理论值约 7%。仓库里 `scripts/verify_gml_artifact.py` 用的就是这个，我绕了一圈才回到它。

2. **任何比对指标都要先用阳性对照验证有效性。** 我把真实 q_proj 权重按 W4A8 规则自行量化，再用同一套指标测量：相关性 **+0.91**、峰值相对误差 **7.12%**（正好是 int4 理论值）。同一指标测参考产物得到 **-0.03**。有了这个对照，才能确定"是数据的问题，不是指标的问题"——否则永远在怀疑自己的读取代码。

**对校验策略的三个直接影响**：

| 影响 | 说明 |
| --- | --- |
| **不能拿参考产物做数值基线** | 参考产物只能校验**结构、格式、命名、字段取值范围、跨文件一致性**（§8.1–§8.4）。逐字节比对数值毫无意义 |
| **数值正确性只能在我方产物内部验证** | 拿我方产物 ↔ 真实模型比（§8.5）。这一层参考产物帮不上忙 |
| **反过来是好事** | 说明参考产物是对方用**随机输入跑通流程**的产物，重点在验证格式与流程。我方只要格式对齐、数值自洽，就能被后端接受 |

### 8.4 第四层：与量化契约的一致性

校验产物内部的量化数值是否自洽 —— 这一层**不需要真实模型**，纯自洽回读。

```
# 动态量化四阶段（§2.9，实测 32/32 组、4096/4096 元素通过）
assert phase_0 == 2 × per-group absmax(input)
assert phase_1 == phase_0 / 256
assert phase_2 == 1 / phase_0            且 == kantor_A_scale
assert kantor_A_Shift == -8

**「每组 max|q| ∈ {7,8}」这一条特别有用**：它不需要真实模型，却能**定位分组轴**。实测参考产物沿跨步轴分组时 512/512 组满足（100%），沿连续轴只有 59% —— 由此判定权重是转置存储。我方产物可以用同一条断言自查分组轴写对了没有。

模型可用：`paths.json` 的 `llama2_7b_model_dir` 指向 `Llama-2-7b-hf`（safetensors + config.json 齐全）。
